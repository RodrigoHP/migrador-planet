# SYSTEM PURPOSE


The system migrates legacy document rendering systems (PlanetPress) to modern HTML templates.

Instead of manually rewriting hundreds of templates, the system **reverse engineers the layout
and logic directly from the PDF output**.

INPUT

• Example PDFs (3‑5 examples per layout)
• XSD schema describing the data structure

OUTPUT

• reusable HTML template
• loops for collections
• conditional blocks
• formatting filters

Example template:

Cliente: {{cliente}}

{% for item in documentos %}
<tr>
<td>{{item.data}}</td>
<td>{{item.valor | currency}}</td>
</tr>
{% endfor %}



# CORE CONCEPTUAL MODEL


The system converts documents through multiple abstraction levels.

PDF
↓
Layout Skeleton
↓
Logical Layout Model
↓
HTML Template

The early pipeline extracts **geometry and structure**.
The later pipeline extracts **semantics and logic**.



# REAL WORLD CONTEXT


Organizations using PlanetPress typically have:

• ~200 layouts
• PDFs containing hundreds or thousands of pages
• conditional logic embedded in the rendering engine
• dynamic tables (statements, invoices, transactions)
• optional blocks based on business rules
• formatted values such as CPF, CNPJ, currency and dates
• schemas that define most fields as simple strings

Therefore the platform must infer:

• layout structure
• field meaning
• loops
• formatting rules

# PIPELINE MACRO PHASES


The system pipeline is divided into three macro phases.

PHASE 1 — DOCUMENT UNDERSTANDING
PHASE 2 — LAYOUT INTELLIGENCE
PHASE 3 — TEMPLATE GENERATION



# PHASE 1 – DOCUMENT UNDERSTANDING


Goal: Extract physical document structure.

Steps:

PDF Parsing
↓
Layout Skeleton Builder
↓
Page Layout Clustering
↓
Representative Page Selection
↓
Layout Fingerprint
↓
Layout Registry Lookup

Libraries recommended:

PyMuPDF

Skeleton Builder extracts:

• text blocks
• bounding boxes
• candidate table areas
• page zones

Clustering reduces large PDFs into representative pages.



# MULTI‑EXAMPLE LAYOUT ANALYSIS


Multiple example PDFs allow the system to differentiate between labels and values.

Example:

PDF A
Cliente: João

PDF B
Cliente: Maria

Inference:

Cliente = label
value = dynamic field

This step is critical for correctly detecting dynamic fields.



# LAYOUT STABILITY ANALYSIS


Each block in the layout is classified as:

STABLE
VARIABLE
OPTIONAL

Example:

Cliente → stable
CPF → stable
Aviso atraso → optional



# VARIANT DETECTION


Some documents contain conditional blocks.

Example:

if saldo < 0
display warning message

Variant detection compares example PDFs to discover optional blocks.

The resulting template uses conditional logic.



# STRUCTURAL LAYOUT NORMALIZATION


PDF layout is converted into logical zones.

Zones include:

HEADER
BODY
TABLE
FOOTER

Normalization removes page dependency and prepares the document
for template generation.



# TABLE INTELLIGENCE


The system must correctly detect tables.

Key capabilities:

Table Identity Detection
Multiple Table Detection
Table Continuation Detection
Multi‑Page Table Detection

Important rule:

Tables must be detected BEFORE anchor detection.
Otherwise table headers may be incorrectly interpreted as fields.



# VISION INTERPRETATION


Vision models interpret semantic meaning.

Vision identifies:

• labels
• values
• table semantics
• document meaning

Vision operates AFTER layout structure is known.



# VISION SELF CHECK


Vision outputs are validated for consistency.

Checks include:

• field alignment
• label‑value matching
• table structure validation

If inconsistencies are detected:

Vision may reprocess the page with additional context.



# SCHEMA INTELLIGENCE


The schema (XSD) is NOT used during layout detection.

Instead it is applied AFTER Vision interpretation.

Pipeline:

Vision → detected fields
↓
Field Intelligence Mapping (uses schema)

This prevents forcing incorrect mappings.



# FORMAT DETECTION


Although schema fields may be strings, the system detects formats.

Examples:

12345678900 → CPF
1000.50 → currency
2023‑01‑01 → date

The template may include formatting filters:

{{cpf | cpf}}
{{valor | currency}}



# CONFIDENCE SCORING


Each detected element receives a confidence score.

Rules:

confidence ≥ 0.8 → automatic
0.6‑0.8 → optional review
< 0.6 → human review required



# HUMAN IN THE LOOP


Operators review low confidence results.

Corrections are stored by the Learning Engine.

Future documents automatically benefit from these corrections.
