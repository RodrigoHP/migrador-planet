# Story 30.3 — Parser HTML completo para reconstrução de árvore

## Story
**Como** operador editando o código HTML diretamente no code editor,
**Quero** que adicionar, remover ou reposicionar um `[data-node-id]` reflita na árvore de nós,
**Para** manter código e árvore sincronizados sem precisar reprocessar o PDF.

## Status
Done

## Business Value
`syncHtmlToTree` (codeStore) detecta apenas text/data-field de nós já existentes.
Após esta story:
- Nó adicionado no HTML → nó criado no templateStore com mesmo ID e posição
- Nó removido do HTML → `templateStore.removeNode` chamado
- Posição/tamanho CSS alterado no HTML → `moveElement`/`resizeElement` chamados

**Estimativa:** 3 story points (L)

## Scope

**IN:**
- `templateStore.addNodeFromSync(node, parentId)` — insere TreeNode com ID específico sem gerar novo ID
- `syncHtmlToTree` expandido: fases de add, remove, position sync
- Guard de segurança: sem `[data-node-id]` no HTML → só sincronizar text/data-field (evitar remoção em massa no scaffold simplificado)
- Testes: add detected, remove detected, position sync, safety guard

**OUT:**
- CSS complexo (calc, var, %)
- Nós estruturais sem data-node-id (header/footer)
- Sync bidirecional de binding/formatString

## Risks

| Risco | Probabilidade | Impacto | Mitigação |
|-------|--------------|---------|-----------|
| Remoção em massa quando HTML é scaffold simplificado | Alta | Alto | Safety guard: só processar add/remove se HTML tiver ≥ 1 `[data-node-id]` |
| Loop code→tree→code | Média | Alto | `_isSyncing` flag existente cobre; `watch(documentTree, {if _isSyncing return})` já existe |
| Iteração sobre flatNodes enquanto removendo | Baixa | Médio | Coletar remoções em array, processar após forEach |

## Context

**Situação atual em `syncHtmlToTree`:**
- Itera sobre `templateStore.flatNodes`
- Para cada nó, busca `[data-node-id="${nodeId}"]` no HTML
- Sincroniza text e data-field se encontrado
- Nós sem elemento no HTML: ignorados (não removidos)
- Nós novos no HTML: ignorados (não adicionados)

**Nova arquitetura:**
```
Phase 1: Build htmlMap (data-node-id → Element)
Phase 2: Safety check — if htmlMap.size === 0, skip add/remove
Phase 3: Sync existing (text, data-field, position)
Phase 4: Collect removals (in store, not in htmlMap)
Phase 5: Process removals — templateStore.removeNode(id)
Phase 6: Process additions (in htmlMap, not in store) — templateStore.addNodeFromSync
```

**`addNodeFromSync` — novo método em templateStore:**
```typescript
function addNodeFromSync(newNode: TreeNode, parentId: string): boolean {
  if (!documentTree.value) return false
  const parent = flatNodes.value.get(parentId)
  if (!parent) return false
  // NOT calling pushUndoSnapshot — sync is non-interactive
  parent.children.push(newNode)
  buildFlatMap(newNode, flatNodes.value)
  mutationVersion.value++
  useGenerationStore().patchAddNode(newNode, parentId)
  return true
}
```

**Parse de posição CSS:**
```typescript
function parsePxValue(style: string, prop: string): number | null {
  const m = style.match(new RegExp(`${prop}\\s*:\\s*([\\d.]+)px`))
  return m ? parseFloat(m[1]) : null
}
```

## Dev Notes

**Por que `addNodeFromSync` não chama `pushUndoSnapshot`:**
O sync do código HTML para a árvore é uma operação de reconciliação, não uma ação do usuário.
O undo stack deve refletir intenções do usuário (drag, resize, etc.), não reflexos automáticos.

**Por que a safety guard é necessária:**
Quando `generationStore.templateDraft?.html` NÃO está setado (nenhum backend HTML carregado),
`fileContents.html` = scaffold simplificado gerado por `generateHtmlFromStore()` — sem `data-node-id`
nos elementos individuais. Processar remoção nesse contexto removeria TODOS os nós do store.
