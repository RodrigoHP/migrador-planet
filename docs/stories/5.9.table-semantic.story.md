# Story 5.9: Blocos 4-5: Table Detection + Semantic Intelligence

## Status
Ready for Review

## Story
**As a** blocos do pipeline,
**I want** detectar e estruturar tabelas (bloco 4) e analisar significado semântico dos blocos de texto (bloco 5),
**so that** tabelas sejam propriamente identificadas antes da detecção de anchors e blocos de texto tenham contexto semântico.

## Acceptance Criteria
1. Stage 13 — Table Detection: identificar regiões de tabela a partir de linhas de grid, blocos de texto alinhados, padrões repetitivos
2. Stage 14 — Table Structuring: extrair headers, linhas, colunas; detectar tabelas multi-página (continuação)
3. Stage 15 — Semantic Analysis: classificar blocos de texto como: label, value, title, header, footer_text, page_number, table_header, table_cell
4. Table detection executa ANTES de anchor detection (decisão arquitetural: evita interpretar headers de tabela como campos de formulário)
5. Tabelas multi-página ligadas entre páginas
6. Todos os estágios registrados no orchestrator, emitindo SSE progress
7. Output: tables[] com { headers[], rows[][], column_widths[], is_multi_page, continuation_pages[] }, semantic_labels por text_block
8. Testes cobrem: precisão de detecção de tabelas, linking multi-página, classificação semântica

## Dev Notes

### Decisão Arquitetural: Table Detection ANTES de Anchors
- Architecture v5.0: tabelas detectadas antes de anchor detection
- Razão: headers de tabela (ex: "Data", "Valor", "Descrição") seriam falsos positivos como labels de formulário
- Com tabelas já identificadas, o matching engine sabe que esses TextBlocks são `table_header`, não `label`

### Detecção de Tabelas — Abordagem Combinada
- Grid lines sozinhas não são suficientes (muitas tabelas sem grid)
- Alinhamento de texto é forte indicador mas tem falsos positivos
- Combinação das 3 fontes com scoring ponderado dá melhor resultado

### Tabelas Multi-Página
- Comuns em extratos bancários (centenas de linhas)
- Detecção: tabela termina perto do footer → verificar se próxima página inicia igual
- Linking: manter referência cruzada entre páginas
- Dados contínuos: rows de todas as páginas formam uma única tabela lógica

### Classificação Semântica → Matching Engine
- Labels classificados aqui alimentam diretamente o matching (Story 5.11)
- `label` adjacente a `value` → par label-valor candidato para mapeamento
- `table_header` + `table_cell` → estrutura de tabela para `foreach` binding

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: LOW — Stage 17 (Table Detection) e Stage 18 (Table Structuring) comunicam via `context["tables"]` serializado (list of dicts). Stage 19 (Semantic Analysis) lê `context["tables"]` e `context["parsed_documents"]`. Não há dependência de objetos Python entre stages — tudo passa por serialização/deserialização via dicts, o que é o padrão correto de isolamento entre stages.
- Cohesion: HIGH — Separação entre detecção (Stage 17), estruturação (Stage 18) e classificação semântica (Stage 19) é arquiteturalmente sólida. Table Detection foca em identificar *se* há uma tabela; Table Structuring foca em *como* ela é estruturada; Semantic Analysis foca em *o que significa* cada bloco de texto. As três responsabilidades são orthogonais.
- Patterns: Decisão arquitetural central desta story — Table Detection executa ANTES de anchor detection — está corretamente implementada (stages 17-18 no Bloco 5, anchor detection em bloco posterior). Isso evita a classe de bugs onde headers de tabela ("Data", "Valor") são erroneamente classificados como labels de formulário. A `_TableIndex` em `semantic_analysis.py` é uma estrutura de lookup limpa que encapsula a lógica de "bloco pertence a qual tabela".
- Scalability: `_TableIndex._table_for_block()` é O(m×t) onde m=blocos e t=tabelas por página. Para documentos com muitas tabelas (> 20 por página), isso pode ser um gargalo. Na prática, documentos business raramente têm > 5 tabelas por página. Aceitável para o domínio atual.

### Issues Found
- [medium] **`_build_cell_map()` divide colunas em buckets de tamanho igual** — `table_structuring.py` linha 88: `step = (x_max - x_min) / max(col_count, 1)`. Esta abordagem assume colunas de largura uniforme. Tabelas com colunas de proporções muito díspares (ex: coluna de descrição com 60% da largura + 3 colunas de valores com 13% cada) terão células atribuídas incorretamente. Issue de precisão, não de corretude funcional. Recomendação para @dev: substituir por clustering de posições X (similar ao `_cluster_positions()` já implementado em `table_detection.py`) em vez de divisão uniforme de range.
- [medium] **`_structure_rows()` sempre trata linha 0 como header quando n_rows >= 2** — `table_detection.py` linhas 282-287: heurística simplista. Tabelas de dados sem linha de header (ex: listas de transações sem cabeçalho) terão sua primeira linha de dados incorretamente promovida a header. Stage 18 corrige parcialmente via `_header_row_index()` (detecção por fonte bold), mas apenas quando `existing_headers` está vazio. Recomendação para @dev: Stage 17 deve deixar `headers=[]` por padrão e delegar a decisão de header inteiramente ao Stage 18, que tem acesso aos metadados de fonte.
- [low] **Magic constant `700.0` em `_link_multi_page()`** — `table_detection.py` linha 356: `if tbl.bbox[3] < 700.0: continue`. Este threshold assume página A4 (842pt) e que tabelas que terminam abaixo de y=700 (83% da altura) estão "perto do rodapé". Não funciona corretamente para páginas de formato diferente (Letter, A3, etc.). Recomendação: calcular threshold dinamicamente como `page_height * 0.83` ou receber `page_height` como parâmetro. Por ora, o hardcode de DEFAULT_PAGE_HEIGHT=842 no Semantic Analysis cobre o caso A4 corretamente.
- [low] **`DetectedTable` serializado via `model_dump()` (Pydantic) enquanto outros modelos usam `to_dict()` (dataclass)** — Inconsistência de padrão de serialização. `table_detection.py` e `table_structuring.py` chamam `t.model_dump()`, sugerindo que `DetectedTable` é um modelo Pydantic enquanto os demais modelos do pipeline são dataclasses Python com `to_dict()`. Esta heterogeneidade não causa bugs mas cria inconsistência na API de serialização. Verificar se `DetectedTable` deve migrar para dataclass (padrão do projeto) ou se a adoção de Pydantic para modelos com validação de dados é uma decisão arquitetural intencional.

### Technical Debt Registered
- `_build_cell_map()` com divisão uniforme de range X: algoritmo simplista que funcionará bem para 80% dos casos mas falhará em tabelas com colunas de proporções muito assimétricas. Monitorar feedback de produção; refatorar se taxa de erros de estruturação de tabela for > 10%.
- Threshold hardcoded `700.0` em `_link_multi_page()`: funciona para A4 mas não para outros formatos de página. Se o sistema for expandido para suportar outros formatos, este threshold deve ser parametrizado.
- Heterogeneidade de serialização (`model_dump()` vs `to_dict()`): investigar e padronizar em Epic 6 ou quando `DetectedTable` for refatorado.

### Decision Log
- **Table Detection ANTES de Anchor Detection**: decisão arquitetural mais importante desta story. Correta e bem fundamentada. A decisão elimina uma categoria inteira de falsos positivos no Matching Engine (Story 5.11) ao garantir que `table_header` e `table_cell` sejam classificados semanticamente antes do processo de mapeamento campo-label.
- **Abordagem combinada de 3 evidências para table detection** (grid lines + alignment + pattern): design defensivo correto. Nenhuma fonte isolada é suficientemente confiável para documentos business reais. O scoring ponderado com redistribuição de pesos quando grid_info está ausente é arquiteturalmente sólido.
- **Serialização via context dict entre Stage 17 e 18** (vs passar objetos Python diretamente): correta para o padrão de pipeline. Garante que cada stage possa ser testado de forma isolada e que o estado do pipeline seja serializável para debug/replay.
- **`_TableIndex` como classe interna de Stage 19**: decisão de encapsulamento correta. A lógica de "qual tabela contém este bloco?" é específica do stage de classificação semântica e não deve ser exposta a outros stages.
