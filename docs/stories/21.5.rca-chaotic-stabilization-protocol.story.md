# Story 21.5 — Chaotic Domain Stabilization Protocol (Fase 0.5)

## Story
**Como** investigador enfrentando um bug classificado como Chaotic,
**Quero** um protocolo concreto de estabilizacao (Fase 0.5) com steps executaveis,
**Para** que "stabilize first" seja uma acao definida e nao apenas texto vago.

## Status
Done

## Context

### Problema
O Cynefin classifica bugs Chaotic como "act first, sense later" — o sistema esta instavel e precisa ser contido antes de investigar. A metodologia atual diz "stabilize first, then full pipeline" mas nao define: o que significa estabilizar? Quais acoes tomar? Quando considerar estavel?

### Design
Fase 0.5 — Stabilization Protocol:
1. **Contencao imediata** (escolher 1+):
   - Rollback para ultimo commit estavel (`git revert` ou deploy anterior)
   - Feature flag: desabilitar funcionalidade afetada
   - Hotfix minimo: guard/try-catch no ponto de crash (band-aid explicitamente temporario)
2. **Observacao** (5-15 min):
   - Sistema esta respondendo normalmente apos contencao?
   - Novo sintoma apareceu?
   - Usuarios impactados reduzidos?
3. **Criterios de estabilidade** (todos devem ser true):
   - Sistema operacional para usuarios nao-afetados
   - Crash/erro nao esta se propagando
   - Dados nao estao sendo corrompidos
4. **Transicao**: quando estavel → prosseguir para Fase 1 com nota "CHAOTIC: contencao aplicada via {metodo}"

## Acceptance Criteria
- [ ] Fase 0.5 documentada no investigate.md entre Fase 0 e Fase 1
- [ ] 3 opcoes de contencao definidas com quando usar cada uma
- [ ] Periodo de observacao com checklist de estabilidade
- [ ] Criterios de transicao para Fase 1 (quando considerar estavel)
- [ ] Fast track de Chaotic atualizado: 0→0.5→1→...→9 (em vez de 0→1)
- [ ] Workflow YAML atualizado com step de stabilization
- [ ] Nota obrigatoria no relatorio sobre metodo de contencao usado
