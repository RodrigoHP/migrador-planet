# Story 5.11: Bloco 7: Matching Semântico — Field Mapping, Format Detection, Confidence Scoring

## Status
Ready for Review

## Story
**As a** bloco do pipeline,
**I want** realizar matching semântico entre conteúdo PDF e campos XSD (bloco 7), incluindo mapeamento de campos, detecção de formatos e scoring de confiança multi-fator,
**so that** o bloco de validação possa verificar a qualidade dos mapeamentos e gerar o template draft.

## Acceptance Criteria
1. Stage 19 — Field Matching: mapear blocos de texto do PDF para campos XSD usando similaridade semântica (Gemini 2.0 Flash via OpenRouter) + contexto (labels, posição, formato)
2. Stage 20 — Format Detection: detectar formatos de campo (moeda BRL, datas, CPF, CNPJ, telefone, porcentagem) e gerar funções de normalização
3. Stage 21 — Confidence Scoring: calcular confiança 5-fatores por Layout Type: layout stability, anchor detection, grid quality, field variability, vision agreement (Claude Sonnet via OpenRouter)
4. Quando múltiplos candidatos para mesmo texto PDF → flag como "ambiguous" para resolução pelo operador (FR5)
5. Format detection inclui: "R$ 1.234,56"→1234.56, "15 de Janeiro de 2025"→"15/01/2025" (FR6)
6. Output parcial: field_mappings[], confidence_scores{}, ambiguous_fields[], format_functions[]
7. Testes cobrem: precisão de matching, detecção de formato, cálculo de confiança

### Design Assessment
- Coupling: LOW. Os três stages (23, 24, 25) são independentes entre si no runtime: Stage 24 enriquece `field_mappings` in-place (padrão correto para pipeline linear), Stage 25 lê `visual_analysis` de Stage 22 via contexto sem import direto. O único ponto de acoplamento de design é a chave `"field_mappings"` compartilhada — adequado para pipeline de dados.
- Cohesion: HIGH. Stage 23 = matching semântico exclusivamente, Stage 24 = detecção de formato por regex puro sem I/O, Stage 25 = scoring multi-fator com LLM opcional. Responsabilidades bem separadas e testáveis de forma isolada.
- Patterns: Padrão StageRegistry correto. `_call_with_retry` reutilizado via import local de `openrouter_client` — evita replicação de lógica de retry. Degradação graceful implementada nos três stages (fuzzy fallback em Stage 23, weighted average em Stage 25 quando sem API key).
- Scalability: Stage 24 é O(n) linear com regex compilada, sem I/O — correto. Stage 23 faz no máximo uma chamada LLM por job (não por campo), limitando custo. Stage 25 usa LLM apenas uma vez por job para scoring global — decisão de design correta para controle de custo.

### Issues Found

**[MEDIUM] `_find_adjacent_label` usa `blk["bbox"]` sem `.get()` — KeyError potencial**
- Se qualquer `text_block` chegar sem a chave `bbox` (ex: bloco gerado por estágio anterior com schema diferente), gera `KeyError` que aborta o Stage 23 inteiro. A correção defensiva seria `blk.get("bbox", [0, 0, 0, 0])` na linha 90 de `field_matching.py`.
- Severity: MEDIUM (resiliência de pipeline)
- Ação sugerida para @dev: corrigir antes de integração end-to-end.

**[LOW] `vision_agreement` normalização corrigida em v1.3, mas o fix merece comentário inline**

### Decision Log
- A escolha de `difflib` como fallback fuzzy para field matching (sem API key) é adequada: sem dependências externas, O(n·m) aceitável para conjuntos pequenos de campos XSD (<200 paths).
- Format Detection (Stage 24) implementado como regex puro sem LLM é a decisão correta para formatos brasileiros conhecidos e estruturados (CPF, CNPJ, moeda BRL). LLM seria over-engineering para este subproblema.
- A separação de Stage 24 em arquivo próprio (não embutido em Stage 23) aumenta testabilidade e está alinhado com o padrão de responsabilidade única do projeto.
- Claude Sonnet escolhido para confidence scoring global é adequado: é analítico, custo moderado, e chamado apenas uma vez por job.
