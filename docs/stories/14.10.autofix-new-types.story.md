# Story 14.10 — AutoFix Novos Fix Types (F12)

## Story

**Como** operador do editor de templates,
**Quero** que o AutoFix IA detecte e sugira correções de bordas, backgrounds, alinhamento de texto e z-order,
**Para** refinar a fidelidade visual do template gerado comparando o CSS produzido pelo pipeline com as propriedades visuais extraídas do PDF original.

## Status

Done

## Context

### Problema

O AutoFix atual (story 9.4) possui 5 fix types: `spacing`, `alignment`, `font`, `binding`, `position`. Esses tipos cobrem ajustes estruturais (espaçamento, posição, fonte), mas **não cobrem refinamentos visuais** que dependem da comparação entre propriedades visuais extraídas do PDF e o CSS gerado pelo pipeline Stage 5.2. Especificamente:

1. **Bordas:** O pipeline extrai `drawn_elements` (linhas e retângulos vetoriais) do PDF, mas o Stage 5.2 nem sempre gera `border` CSS correto — bordas faltantes, espessura errada, cor diferente, estilo incorreto (solid vs dashed)
2. **Backgrounds:** Retângulos preenchidos (`rects` com fill color) no PDF nem sempre resultam em `background-color` CSS correspondente — background não detectado ou cor diferente
3. **Alinhamento de texto:** A posição x do texto no PDF indica alinhamento real (right, center) mas o CSS gerado frequentemente defaulta para `text-align: left` — necessita tolerância de 5px para detecção
4. **Z-order:** Sobreposições visuais entre elementos não resolvidas pelo pipeline — elementos que se sobrepõem sem `z-index` explícito, causando renderização incorreta

### Solução Necessária

Expandir o sistema AutoFix com 4 novos fix types de **refinamento visual**:

| Fix Type | Comparação | Propriedade CSS Alvo |
|----------|-----------|---------------------|
| `border-refine` | `drawn_elements` do PDF vs `border` CSS | `border`, `border-width`, `border-color`, `border-style` |
| `background-refine` | `rects` preenchidos vs `background-color` CSS | `background-color` |
| `text-align` | posição x do texto no PDF vs `text-align` CSS | `text-align` |
| `z-order` | sobreposições visuais detectadas | `z-index` |

Os novos tipos são **refinamentos**, não criação — assumem que os elementos já existem no template e comparam o estado CSS atual com as propriedades visuais do PDF original.

## Acceptance Criteria

1. **AC1 — Tipo `border-refine`:** O AutoFix detecta quando um `drawn_element` vetorial do PDF (linha/retângulo de borda) não tem correspondência CSS `border` no elemento mais próximo do template, ou quando espessura/cor/estilo divergem. Sugere a propriedade `border` correta (ex: `1px solid #333`)
2. **AC2 — Tipo `background-refine`:** O AutoFix detecta retângulos preenchidos (`rects` com `fill_color`) no PDF que não possuem `background-color` correspondente no CSS do elemento sobreposto, ou quando a cor difere. Sugere `background-color` correto
3. **AC3 — Tipo `text-align`:** O AutoFix compara a posição x do texto no PDF com o `text-align` CSS do elemento. Se o texto está alinhado à direita ou centro no PDF (tolerância de 5px) mas o CSS tem `text-align: left`, sugere a correção. Tolerância configurável
4. **AC4 — Tipo `z-order`:** O AutoFix detecta sobreposições visuais entre elementos (bboxes que se intersectam) sem `z-index` explícito definido. Sugere valores de `z-index` para resolver a sobreposição na ordem visual correta
5. **AC5 — FixType expandido:** O tipo `FixType` no frontend inclui os 4 novos valores. O `propMap` em `acceptCurrent()` mapeia corretamente cada novo tipo para a propriedade CSS correspondente
6. **AC6 — Prompt backend expandido:** O prompt do backend em `auto_fix.py` inclui instruções para os 4 novos fix types com critérios de detecção claros (comparação PDF vs CSS)
7. **AC7 — UI diferenciada:** O `AutoFixPanel.vue` exibe ícone/badge diferenciado para os novos tipos de fix (visual distinto dos 5 tipos originais). O operador pode filtrar sugestões por tipo
8. **AC8 — Dados do PDF no request:** O `runAutoFix()` envia dados do PDF (drawn_elements, rects, posições de texto) junto com o `template_state` para que o backend possa fazer a comparação
9. **AC9 — Undo Integration:** Todos os novos fix types participam do undo stack via `templateStore.pushUndoSnapshot()`, consistente com os fix types existentes
10. **AC10 — Testes:** Cobertura mínima de 80% para código novo. Testes unitários para cada fix type no backend e frontend. Testes de integração para o fluxo completo (request → sugestão → accept → undo)

## Dev Notes

### Abordagem de Implementação: Rule-Based Helpers (NÃO LLM)

Os 4 novos fix types são implementados como **funções determinísticas rule-based** (pattern matching + CSS transform), **não** como correções baseadas em LLM. O autofix engine utiliza um registry de funções de regra, onde cada função-alvo trata um tipo específico de discrepância visual:

- **`_detect_border_issues()`** — compara `drawn_elements` vetoriais com propriedades `border` CSS via pattern matching geométrico
- **`_detect_background_issues()`** — compara `filled_rects` com `background-color` CSS via comparação de cor hex por canal RGB
- **`_detect_text_align_issues()`** — calcula alinhamento real do texto via posição x relativa ao container width (thresholds configuráveis)
- **`_detect_zorder_issues()`** — detecta sobreposições via interseção de bboxes e atribui `z-index` incremental

Estas funções helper são executadas no backend **antes** da chamada ao LLM. O LLM (Claude Sonnet) continua sendo usado apenas para os 5 fix types originais (spacing, alignment, font, binding, position) onde a análise requer raciocínio semântico. Os novos tipos de refinamento visual são puramente determinísticos porque dependem de comparações geométricas/numéricas precisas entre dados extraídos do PDF e CSS gerado.

### Padrões Existentes a Seguir

**Accept flow (autoFixStore.ts):**
1. `acceptCurrent()` chamado pelo operador
2. `templateStore.pushUndoSnapshot()` — snapshot antes de mutação
3. `templateStore.updateNodeProperty(element_id, propKey, suggested_value)` — aplica fix
4. `appliedFixes.push(suggestion)` — registra
5. `_advance()` — próxima sugestão

Os novos fix types devem seguir **exatamente** este fluxo. A única mudança é no `propMap` e na UI.

- Prompt único com instruções claras por tipo
- Response format: JSON array de `FixSuggestion`

### Riscos

1. **Qualidade do prompt:** Os novos fix types dependem de prompt engineering eficaz — a IA precisa entender a comparação PDF vs CSS. Mitigação: testes com fixtures reais de PDFs do Planet Express
2. **Dados do PDF insuficientes:** Se `drawn_elements` ou `filled_rects` não estiverem no pipeline result, será necessário ajustar estágios anteriores. Mitigação: verificar disponibilidade dos dados antes de implementar
3. **Performance:** Enviar dados do PDF (potencialmente grandes) no request pode impactar latência. Mitigação: truncar dados como já feito para template_state (8000 chars)
