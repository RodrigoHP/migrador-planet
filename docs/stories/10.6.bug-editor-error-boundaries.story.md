# Story 10.6: Hardening Preventivo do Editor

## Status
Ready for Dev

## Story
**As a** operador,
**I want** que falhas inesperadas ao carregar o resultado da análise no editor sejam capturadas e reportadas claramente, e que a troca de PDF no editor não cause race condition,
**so that** o editor nunca fique em estado inconsistente silencioso — eu sempre vejo uma mensagem de erro útil ou o editor abre corretamente.

## Acceptance Criteria
1. Se qualquer store falhar dentro de `loadFromPipelineResult`, o erro é capturado, `session.error` recebe mensagem descritiva com o nome da store que falhou, e `analysisCompleted` NÃO é setado para `true` (usuário não navega para editor com estado parcial)
2. Se qualquer store falhar dentro de `loadFromSavedProject`, o erro é capturado e um erro descritivo é lançado para o chamador (com nome da store que falhou)
3. Em `PDFReference.vue`, `onDocumentChange` aguarda o carregamento anterior terminar antes de iniciar novo — sem renders simultâneos do mesmo canvas
4. `vitest run` passa sem erros
5. `npm run build` passa sem erros

## Bugs Identificados

### Bug A — ALTO: `loadFromPipelineResult` sem try/catch — estado parcial silencioso
- **Causa:** `loadFromPipelineResult` em `session.ts` chama 6 stores em sequência sem try/catch. Se qualquer store lançar exceção (ex: `loadLayoutTypes` recebendo array malformado), as stores seguintes não são carregadas, `analysisCompleted` permanece `false`, e o router guard bloqueia o editor — mas o usuário não vê mensagem de erro, fica preso na AnalyzingPage sem feedback.
- **Sintoma:** Análise aparece completa (todos stages verdes), mas o editor nunca abre. Sem mensagem de erro.
- **Arquivo:** `frontend/src/stores/session.ts` — `loadFromPipelineResult()` linhas 62-108
- **Fix:** Envolver o bloco de stores em try/catch. No catch: setar `this.error = \`Falha ao carregar ${storeName}: ${e.message}\`` e NÃO setar `analysisCompleted = true`. Chamar a função de cada store individualmente com try/catch isolado para identificar qual falhou.

### Bug B — MÉDIO: `loadFromSavedProject` sem try/catch — falha silenciosa ao abrir projeto salvo
- **Causa:** Mesma ausência de try/catch, mas no fluxo de abrir arquivo JSON salvo. Se `editorStore.$patch` receber dados inválidos de `editorState`, ou se `loadLayoutTypes` lançar com `layoutTypes` corrompido, a função falha sem retornar erro ao chamador.
- **Sintoma:** Usuário tenta abrir projeto salvo, aparentemente nada acontece, ou o editor abre com estado parcialmente restaurado.
- **Arquivo:** `frontend/src/stores/session.ts` — `loadFromSavedProject()` linhas 115-181
- **Fix:** Envolver em try/catch com lançamento de erro descritivo ao chamador.

### Bug C — MÉDIO: Race condition em `PDFReference.vue` — `onDocumentChange` não-awaited
- **Causa:** `onDocumentChange()` chama `loadSelectedDoc()` sem await. Se o usuário trocar entre PDFs rapidamente, dois `loadPdf()` correm em paralelo no mesmo canvas. O resultado é imprevisível — o PDF exibido pode ser o anterior, ou o canvas pode travar.
- **Sintoma:** Troca rápida de PDF exibe PDF errado ou trava o canvas.
- **Arquivo:** `frontend/src/organisms/PDFReference.vue` — função `onDocumentChange` (linha ~166)
- **Fix:** Adicionar flag `isLoadingPdf: ref<boolean>(false)`. Em `onDocumentChange`: se `isLoadingPdf.value === true`, debounce ou ignorar nova chamada até o carregamento atual terminar. Alternativa mais simples: usar flag para cancelar render anterior (setar flag antes de await, checar depois do await se ainda é válido).
