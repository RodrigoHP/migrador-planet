# Story 16.2 — Timeout por Step

## Story
**Como** operador que executa workflows em `yolo_continuous`,
**Quero** que cada step tenha um timeout configuravel que aborta a execucao se o subagente travar,
**Para** que o engine nunca fique preso indefinidamente em um step que nao responde.

## Status
Draft

## Context

### Problema

No modo `yolo_continuous`, o engine spawna subagentes via Task tool sem timeout. Se um subagente travar (loop infinito, espera externa, API bloqueante), o engine espera indefinidamente. O state file so eh atualizado APOS o step completar, entao nao ha recovery possivel sem intervencao manual.

### Referencia

- Engine: `.aios-core/development/tasks/run-workflow-engine.md` (v3.0)
- Story anterior: `16.1.engine-yolo-continuous.story.md`

### Design Proposto

Tres niveis de timeout com precedencia: step > workflow > engine default.

```
Precedencia: step.timeout > workflow.default_step_timeout > ENGINE_DEFAULT (300s)
```

**Comportamento ao expirar:**
1. Marcar step como `timeout` no state
2. Tratar como falha → entra no fluxo `step_failed()`
3. Se `on_failure` definido → rota para target (com loop guard)
4. Se nao → ABORT com relatorio incluindo "timeout_exceeded"

**Configuracao no workflow YAML:**
```yaml
metadata:
  default_step_timeout: 600  # 10 min (override global)

steps:
  - id: implement_and_test
    timeout: 900  # 15 min (step pesado)
  - id: dedup_check
    timeout: 60   # 1 min (step leve)
```

**Configuracao no engine:**
```
ENGINE_DEFAULT_TIMEOUT = 300  # 5 minutos
```

## Acceptance Criteria

- [ ] AC1: Engine define timeout default de 300s para todos os steps em `yolo_continuous`
- [ ] AC2: Workflow YAML aceita campo `default_step_timeout` em metadata (override global)
- [ ] AC3: Cada step aceita campo `timeout` (override do workflow e do default)
- [ ] AC4: Precedencia respeitada: step > workflow > engine default
- [ ] AC5: Step que excede timeout eh marcado como `timeout` no state e tratado como falha via `step_failed()`
- [ ] AC6: Timeout respeitado em `on_failure` routing (loop guard + timeout combinados)
- [ ] AC7: Final Report inclui steps que deram timeout com duracao e limites
- [ ] AC8: Modo step-by-step NAO afetado (timeout so aplica em `yolo_continuous`)

## Complexity

**T-shirt size:** S (Small)
**Estimativa:** Modificacao de 1 arquivo existente (run-workflow-engine.md), logica de timeout no spawn + state tracking.

## Scope

**IN:**
- `.aios-core/development/tasks/run-workflow-engine.md` — timeout no spawn, state tracking, precedencia
- Timeout como parametro do Task tool call
- State field `step_results[step_id].timeout_triggered`

**OUT:**
- Nao alterar workflows existentes (campo opcional)
- Nao alterar modo step-by-step
- Nao implementar heartbeat (futuro)

## Risks

- Task tool pode nao suportar timeout nativo como parametro. Fallback: implementar via polling com abort manual se timeout excedido.
- Timeout muito curto (ex: 30s) pode abortar steps legitimamente lentos. Mitigacao: defaults conservadores (300s) e override por step.

## Implementation Notes

### Subtasks

1. Adicionar constante `ENGINE_DEFAULT_TIMEOUT = 300` no engine
2. No init do `yolo_continuous`, resolver timeout: ler `workflow.metadata.default_step_timeout`, guardar em state
3. Antes de cada spawn, resolver timeout final: `step.timeout || state.default_step_timeout || ENGINE_DEFAULT_TIMEOUT`
4. Passar timeout como parametro no Task tool call
5. Tratar resultado `timeout` como `step_failed()` → rota normal de falha
6. Adicionar campo `timeout_triggered: true/false` e `timeout_limit` ao `step_results`
7. Atualizar Final Report para listar steps com timeout
8. Testar: step com timeout curto (10s) deve abortar e gerar relatorio
