# Story 17.6 — Barrier Analyst Agent

## Story
**Como** investigador que encontrou a causa raiz,
**Quero** que o sistema analise sistematicamente TODAS as defesas que deveriam ter pego o bug mas falharam,
**Para** que o fix nao seja apenas corrigir o codigo, mas tambem fortalecer as camadas de defesa para prevenir recorrencia.

## Status
Ready

## Context

### Problema

Hoje o RCA encontra a raiz e aplica o fix. Mas nao pergunta: "Por que nossos testes nao pegaram? Por que o CI deixou passar? Por que o monitoring nao alertou?" Resultado: o mesmo TIPO de bug acontece de novo porque as defesas continuam com os mesmos buracos.

O modelo **Swiss Cheese** (James Reason) mostra que incidentes acontecem quando os buracos de multiplas camadas de defesa se alinham. Barrier Analysis identifica e fecha esses buracos.

### Inspiracao

- **Barrier Analysis**: Identifica defesas que falharam/estavam ausentes
- **Swiss Cheese Model** (James Reason): Camadas de defesa com buracos
- **Google SRE Postmortem**: "Contributing factors" inclui defense failures
- **Defense in Depth**: Principio de seguranca — multiplas camadas

### Design Proposto

**Barrier Analyst** — analisa camadas de defesa do projeto:

```
Input: root_causes confirmados + fix proposto

Camadas de defesa analisadas:
  1. CODE LEVEL
     - Type system (TypeScript strict, Python type hints)
     - Assertions e guards no codigo
     - Input validation
     → Status: worked | failed | bypassed | absent

  2. TEST LEVEL
     - Unit tests para funcao afetada
     - Integration tests para fluxo afetado
     - E2E tests para cenario do usuario
     → Status + coverage %

  3. STATIC ANALYSIS
     - Linter rules que deveriam pegar
     - Type checker (tsc, mypy, pyright)
     - Custom rules (ESLint, Ruff)
     → Status + config check

  4. CI/CD LEVEL
     - Quality gates no pipeline
     - Pre-commit hooks
     - CodeRabbit review
     → Status + historico de runs

  5. MONITORING & ALERTING
     - Error tracking (Sentry, etc.)
     - Health checks
     - Log aggregation
     → Status + coverage

  6. PROCESS LEVEL
     - Code review humano
     - QA gate
     - Story acceptance criteria
     → Status + evidence

Output:
  barrier_analysis:
    layers:
      - name: "Code Level"
        barriers:
          - barrier: "isinstance guard em stage 5"
            status: absent
            recommendation: "Adicionar guard + registrar anti-pattern"
          - barrier: "Type hints no retorno de _summarize_extraction"
            status: absent
            recommendation: "Adicionar return type annotation"
      - name: "Test Level"
        barriers:
          - barrier: "Unit test para stage 5 com input dict"
            status: absent
            recommendation: "Criar teste parametrizado dict/str/None"
          - barrier: "Unit test para stage 3 retorno"
            status: absent
            recommendation: "Criar teste validando tipo de retorno"
      - name: "Static Analysis"
        barriers:
          - barrier: "Linter rule para isinstance antes de .get()"
            status: absent
            recommendation: "Criar custom rule ou registrar em audit-patterns"

    swiss_cheese_summary:
      layers_analyzed: 6
      barriers_checked: 18
      barriers_failed: 2
      barriers_absent: 5
      barriers_worked: 11

      alignment: "Code guard absent + test absent + no linter rule = bug reached production"

    recommendations:
      immediate:
        - "Adicionar isinstance guard (code level)"
        - "Criar 2 unit tests (test level)"
      short_term:
        - "Registrar anti-pattern em known-anti-patterns.md"
        - "Adicionar custom linter rule para .get() sem guard"
      long_term:
        - "Aumentar coverage de stage 3-5 para > 80%"
```

## Acceptance Criteria

- [ ] AC1: 6 camadas de defesa analisadas: Code, Test, Static Analysis, CI/CD, Monitoring, Process
- [ ] AC2: Cada barreira classificada: worked / failed / bypassed / absent
- [ ] AC3: Swiss Cheese summary mostra como buracos se alinharam para permitir o bug
- [ ] AC4: Recomendacoes geradas por camada: immediate / short_term / long_term
- [ ] AC5: Coverage de testes verificado para funcoes afetadas
- [ ] AC6: Linter/type checker config verificado para regras relevantes
- [ ] AC7: Output integrado ao relatorio final do RCA
- [ ] AC8: Recomendacoes "absent" alimentam automaticamente o backlog (stories de melhoria)
- [ ] AC9: Integrado no workflow apos Hypothesis Challenger, antes do fix

**OUT:**

- Nao implementar verificacao de CI/CD pipeline config automatica — manual review
- Nao implementar auto-fix de barreiras (apenas recomendacoes)

## Risks

- Verificacao automatica de barreiras pode gerar falsos positivos (relatar barreira "absent" quando na verdade existe em forma diferente da esperada). Mitigacao: exibir evidencia da verificacao, permitir override.
- Recomendacoes "long_term" podem ser excessivamente ambiciosas para o escopo do projeto. Mitigacao: categorizar por urgencia; apenas "immediate" geram action items automaticos.

## Implementation Notes

### Subtasks

1. Definir checklist de barreiras por camada (6 camadas x N barreiras)
2. Implementar verificacao automatica: grep testes, check type hints, check linter config
3. Classificar cada barreira: worked / failed / bypassed / absent
4. Gerar Swiss Cheese summary: quais buracos se alinharam
5. Gerar recomendacoes por camada e urgencia
6. Integrar recomendacoes "absent" com backlog (gerar stories de melhoria)
7. Adicionar step barrier_analyst ao workflow
8. Testar: bug que passou por CI sem testes deve identificar "test level: absent"
