# Story 16.6 — State Locking & Corruption Prevention

## Story
**Como** operador que pode acidentalmente executar o mesmo workflow em duas sessoes,
**Quero** que o engine detecte e previna corrupcao de state por acesso concorrente,
**Para** que o progresso de um workflow nunca seja sobrescrito silenciosamente por outra sessao.

## Status
Draft

## Context

### Problema

O state file eh lido e salvo sincronamente apos cada step, sem locking. Se duas sessoes Claude Code executam o mesmo workflow simultaneamente:
1. Sessao A le state, completa step 1, salva
2. Sessao B le state (versao de A), completa step 1 (diferente), salva → sobrescreve A
3. Progresso de A eh perdido silenciosamente

Nao ha mecanismo de deteccao de conflito. O campo `updated_at` existe mas nao eh validado.

### Referencia

- Engine: `.aios-core/development/tasks/run-workflow-engine.md` (v3.0)
- State file: `.aios/` (YAML, runtime)

### Design Proposto

**Optimistic Locking** — version counter + session token:

```yaml
# State file additions
_version: 1              # incrementado a cada save
_session_id: "uuid-abc"  # unico por sessao
```

**Validacao no save:**
```
FUNCTION save_state(state):
  on_disk = read_from_disk(state.instance_id)
  IF on_disk._version > state._expected_version:
    → Conflito detectado!
    IF yolo_continuous: ABORT "state_conflict"
    ELSE: avisar usuario
  state._version = on_disk._version + 1
  write_atomically(state)
```

**Validacao no resume:**
```
FUNCTION validate_state_on_resume(state):
  completed_count = count(step_results WHERE status == completed)
  expected_count = current_step_index
  IF mismatch: warning + ask user
```

## Acceptance Criteria

- [ ] AC1: State file contem `_version` (integer, incrementado a cada save) e `_session_id` (UUID)
- [ ] AC2: Antes de salvar, engine le versao atual do disco e compara com versao esperada
- [ ] AC3: Se versao no disco > versao esperada → conflito detectado
- [ ] AC4: Em `yolo_continuous`, conflito causa ABORT com relatorio "state_conflict"
- [ ] AC5: Em step-by-step, conflito causa warning e pergunta ao usuario
- [ ] AC6: Write atomico via temp file + rename (previne corrupcao parcial)
- [ ] AC7: Resume (`continue` action) valida consistencia: step_results count vs current_step_index
- [ ] AC8: Audit trail: `state.concurrency_events[]` registra conflitos detectados

## Complexity

**T-shirt size:** S (Small)
**Estimativa:** Optimistic locking (version check), atomic write (temp+rename), validation no resume.

## Scope

**IN:**
- `.aios-core/development/tasks/run-workflow-engine.md` — version check, atomic write, resume validation
- State fields: `_version`, `_session_id`, `concurrency_events`

**OUT:**
- Nao implementar file locking do OS (complexo, cross-platform)
- Nao implementar merge de conflitos (abort eh mais seguro)
- Nao alterar workflows existentes

## Implementation Notes

### Subtasks

1. Adicionar `_version: 1` e `_session_id: uuid` ao state init
2. Antes de cada save: ler state do disco, comparar `_version`
3. Se conflito: ABORT em yolo_continuous, warning em step-by-step
4. Implementar write atomico: escrever em temp file, rename para destino
5. No `continue` action: validar consistencia step_results vs current_step_index
6. Adicionar `concurrency_events: []` ao state para audit trail
7. Testar: simular conflito (modificar state file manualmente entre steps)
