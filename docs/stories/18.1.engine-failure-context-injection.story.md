# Story 18.1 — Failure Context Injection

## Story
**Como** operador que executa workflows yolo_continuous,
**Quero** que quando um step falha e o engine faz retry via on_failure, o prompt do retry inclua o contexto estruturado da falha anterior (motivo, outputs, feedback do QA),
**Para** que o subagente saiba exatamente o que corrigir em vez de reimplementar do zero.

## Status
Draft

## Context

### Problema

Hoje quando um step falha (QA REJECT, execution_failed, timeout), o engine faz loop para o step definido em `on_failure`. O subagente e re-spawnado com **exatamente o mesmo prompt** da primeira tentativa. Nao recebe informacao sobre o que deu errado.

Isso causa:
1. O subagente pode cometer o mesmo erro
2. Tokens desperdicados reimplementando do zero
3. Multiplos retries identicos antes do abort

### Exemplo Concreto

```
Step: implement_and_test (@dev)
  Tentativa 1: Implementa mas esquece testes para edge case null
  QA REJECT: "Faltam testes para _job === null"

  Tentativa 2 (hoje): @dev recebe mesmo prompt → pode esquecer de novo
  Tentativa 2 (proposto): @dev recebe prompt + "QA rejeitou porque faltam testes para _job === null"
```

### Design

#### Nova template variable: `{{FAILURE_CONTEXT}}`

Adicionar ao `subagent-step-prompt.md`:

```markdown
{{#if FAILURE_CONTEXT}}
## FAILURE CONTEXT (Tentativa {{RETRY_ATTEMPT}} de {{MAX_RETRIES}})

**Motivo da falha anterior:**
{{FAILURE_REASON}}

**Feedback especifico:**
{{FAILURE_FEEDBACK}}

**IMPORTANTE:** Corrija ESPECIFICAMENTE os pontos acima antes de prosseguir.
O resto da implementacao anterior estava correto — nao refaca do zero.
{{/if}}
```

#### Coleta do failure context

No Sequence Advancer, quando `step_failed()` retorna true e `on_failure` existe:

```
failure_context = {
  reason: failure_reason(parsed_output),      # "qa_gate_rejected" | "execution_failed" | "timeout"
  feedback: extract_feedback(parsed_output),  # qa_report.findings, error message, etc
  attempt: state.loop_guard.current_loops[target] + 1,
  max_attempts: max_loops,
  previous_outputs: summarize(parsed_output.outputs, max_chars=500)
}
state.failure_contexts[target_step_id] = failure_context
```

#### Injecao no prompt

No Subagent Prompt Builder, ao construir prompt para um step:

```
IF state.failure_contexts[step.id] exists:
  context = state.failure_contexts[step.id]
  Set {{FAILURE_CONTEXT}} = format_failure_context(context)
  Set {{RETRY_ATTEMPT}} = context.attempt
  Set {{MAX_RETRIES}} = context.max_attempts
  Set {{FAILURE_REASON}} = context.reason
  Set {{FAILURE_FEEDBACK}} = context.feedback
ELSE:
  Set {{FAILURE_CONTEXT}} = ""  # No failure context (first attempt)
```

#### Token budget

Failure context limitado a **max 500 tokens** para nao inflar o prompt:
- Reason: ~20 tokens
- Feedback: max 400 tokens (truncate se necessario)
- Attempt info: ~30 tokens
- Template text: ~50 tokens

## Acceptance Criteria

- [x] AC1: Quando step falha e on_failure rota para retry, o state armazena failure_context com reason, feedback, attempt, max_attempts, e previous_outputs
- [x] AC2: No retry, o subagent prompt inclui secao "FAILURE CONTEXT" com o motivo e feedback especifico da falha
- [x] AC3: Na primeira tentativa (sem falha anterior), a secao FAILURE_CONTEXT nao aparece no prompt
- [x] AC4: Failure context respeita token budget de 500 tokens (trunca feedback se exceder)
- [x] AC5: QA gate REJECT extrai findings/recommendations do qa_report como feedback
- [x] AC6: Execution failure (status: failed) extrai error message como feedback
- [x] AC7: Timeout extrai duracao e limite como feedback
- [x] AC8: Parse failure (handled por 16.5) NAO usa failure context (continua usando FORMAT_REMINDER separado)
- [x] AC9: failure_contexts persiste no state file para recovery entre sessoes
- [x] AC10: Zero regressao nos workflows existentes (rodar sem failure produz comportamento identico ao v4.0)

## Technical Notes

- `failure_contexts` eh um novo campo no engine_state schema (mapa step_id → context)
- Backward compatible: state files antigos sem failure_contexts funcionam normalmente
- O extract_feedback() precisa ser inteligente: para QA rejects, extrair `outputs.findings` ou `outputs.qa_report`; para execution failures, extrair `outputs.error` ou a mensagem de status
