## Story

**As a** template developer,
**I want** the system to automatically generate realistic synthetic JSON data from an uploaded XSD schema,
**so that** I can preview and test templates without needing real production data.

## Acceptance Criteria

- [x] Service `xsd_synthetic_generator.py` parseia XSD e gera JSON de exemplo
- [x] Valores coerentes por tipo: `xs:string` -> texto legivel, `xs:date` -> data valida, `xs:decimal` -> numero formatado
- [x] Tipos BR: CPF, CNPJ, CEP, telefone com formato real (validos mas ficticios)
- [x] Arrays geram 3-5 elementos por padrao
- [x] Resultado disponivel como `exemplo.js` no pipeline result
- [x] testDataStore pode usar dados gerados automaticamente

## Scope

**IN:**
- Novo service `xsd_synthetic_generator.py` no backend
- Geracao de JSON sintetico a partir de field descriptors do XSD
- Heuristicas para tipos brasileiros (CPF, CNPJ, CEP, telefone)
- Integracao com pipeline result (gerar `exemplo.js`)
- Integracao com `testDataStore` para auto-carregamento
- Testes unitarios completos

**OUT:**
- Validacao de dados reais contra XSD (fora do escopo)
- Suporte a XSD com imports/includes complexos (extensao futura)
- UI para configurar quantidade de elementos em arrays (usar default 3-5)
- Geracao de dados para tipos customizados complexos (simpleType restrictions apenas)
- Biblioteca externa de fake data (Faker) — usar geradores internos simples

## Dependencies

- `backend/services/xsd_parser.py` — `XSDParser` classe existente que parseia XSD e retorna field descriptors
- `frontend/src/stores/testDataStore.ts` — store que gerencia dados de teste no editor
- Pipeline orchestrator — ponto de integracao para salvar `exemplo.js` no resultado

## Risks

| Risco | Impacto | Mitigacao |
|-------|---------|-----------|
| Heuristicas de tipo BR podem nao cobrir todos os nomes de campo | Medio | Manter lista extensivel de patterns (regex) e fallback para tipo base |
| XSD com estruturas recursivas pode causar loop infinito | Alto | Limitar profundidade de recursao (max 5 niveis) |
| Dados sinteticos podem nao ser "realistas" o suficiente | Baixo | Usar templates de texto legivel (lorem ipsum BR) e formatos corretos |

## Dev Notes

- **XSD Parser existente:** `backend/services/xsd_parser.py` ja faz o parsing e retorna lista de dicts com `name`, `type`, `min_occurs`, `max_occurs`, `description`. Reutilizar este output como input para o gerador sintetico.
- **Heuristicas BR:** Detectar pelo nome do campo (case-insensitive): `cpf`, `cnpj`, `cep`, `telefone`, `fone`, `celular`, `inscricao_estadual`. Gerar valores ficticios mas com formato valido (digitos verificadores corretos para CPF/CNPJ).
- **Formato `exemplo.js`:** Deve ser um arquivo JS que exporta o objeto JSON, compativel com o formato que o `testDataStore` espera. Verificar formato existente em `testDataStore.ts`.
- **Estrutura de services:** Seguir padrao existente em `backend/services/` — classe com metodo principal, sem dependencias externas pesadas.
- **Testes:** Seguir padrao em `backend/tests/` com pytest fixtures. Referencia: `backend/tests/test_xsd_parsing.py`.
- **Implementação (@dev):**
  - `backend/services/xsd_synthetic_generator.py`: Classe `XSDSyntheticGenerator` com `generate()`, `generate_from_dict()`, `generate_exemplo_js()`, `generate_exemplo_js_from_dict()`. Seed determinístico, array bounds configuráveis, max recursion depth 5.
  - Pipeline: `stage5_template_generation.py` → `_step_5_6_pipeline_result` agora inclui `synthetic_data` e `synthetic_exemplo_js` no result_json quando field_tree disponível.
  - Frontend: `testDataStore.ts` → novo método `loadSyntheticData()` aceita `synthetic_data` do pipeline result e cria um Dataset automaticamente.
  - BR heuristics: CPF (dígitos verificadores válidos), CNPJ (dígitos verificadores válidos), CEP, telefone, nome, cidade, estado, endereço, email, inscrição estadual.
  - 38 testes passando (pytest): tipos básicos, tipos BR, arrays, exemplo.js, store compatibility, edge cases, check digit validation.
