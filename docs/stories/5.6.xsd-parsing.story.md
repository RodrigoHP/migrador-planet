# Story 5.6: XSD Parsing + Field Tree — Árvore Hierárquica de Campos

## Status
Ready for Review

## Story
**As a** estágio do pipeline,
**I want** parsear o arquivo XSD e construir uma árvore hierárquica de campos com tipos e flags required/optional,
**so that** o motor de matching tenha nomes canônicos de campos para geração de data-bind.

## Acceptance Criteria
1. Parse XSD usando lxml, extrair todos os elementos com: name, type (string/decimal/date/integer/boolean), minOccurs, maxOccurs
2. Construir árvore hierárquica suportando paths aninhados (ex: cliente.endereco.cidade)
3. Detectar arrays: maxOccurs="unbounded" ou maxOccurs > 1 → campo array
4. Detectar opcionais: minOccurs="0" → campo opcional
5. Output: FieldTree com nós contendo { name, path, type, required, is_array, children[] }
6. Suportar complex types e estruturas aninhadas
7. Registrar no orchestrator, emitir SSE progress
8. XSD sintaticamente inválido gera erro bloqueante com mensagem indicando a natureza do erro (ex: "Erro de parse XSD: tag não fechada na linha 42"); pipeline marca estágio como failed
9. Testes cobrem: XSD simples, XSD aninhado, arrays, campos opcionais, complex types, XSD inválido

### Nomes Canônicos
- Nomes dos campos XSD tornam-se canônicos no data-bind
- Exemplo: `<xs:element name="nome" type="xs:string"/>` → `data-bind="text: cliente.nome"`
- Paths são dot-separated: `cliente.endereco.cidade`

### Exemplo de Estrutura XSD
```xml
<xs:schema>
  <xs:element name="documento">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="cliente">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="nome" type="xs:string"/>
              <xs:element name="cpf" type="xs:string"/>
              <xs:element name="endereco">
                <xs:complexType>
                  <xs:sequence>
                    <xs:element name="cidade" type="xs:string"/>
                  </xs:sequence>
                </xs:complexType>
              </xs:element>
            </xs:sequence>
          </xs:complexType>
        </xs:element>
        <xs:element name="movimentos" maxOccurs="unbounded">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="data" type="xs:date"/>
              <xs:element name="valor" type="xs:decimal"/>
            </xs:sequence>
          </xs:complexType>
        </xs:element>
      </xs:sequence>
    </xs:complexType>
  </xs:element>
</xs:schema>
```

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED

### Design Assessment
- Coupling: LOW — `xsd_parser.py` imports only `models/field_tree.py` and `lxml`. O `execute()` se comunica exclusivamente via context dict (padrão do pipeline). Nenhum acoplamento lateral com outros stages.
- Cohesion: HIGH — `field_tree.py` contém exclusivamente modelos de domínio (FieldNode, FieldTree, map_xsd_type). `xsd_parser.py` contém exclusivamente lógica de parsing + executor de stage. Separação clara e justificada.
- Patterns: O StageRegistry pattern está seguido corretamente: `register()` exposto no módulo, `execute()` async com assinatura `(context) -> dict`, registro idempotente via `remove_stage(29)` antes de `register_stage`. A escolha de stage_number=29 (fora da sequência 1–28 do pipeline original) é tecnicamente correta mas introduz uma lacuna numérica que deve ser documentada no registry — ver nota abaixo.
- Scalability: Adequado para o domínio. XSDs típicos de documentos business raramente excedem 500 elementos. `build_flat_paths()` usa travessia iterativa com stack (sem recursão no loop principal), o que é seguro para profundidades moderadas. `find_by_path()` com pré-checagem `in flat_paths` é uma otimização válida para evitar travessias desnecessárias.

### Issues Found
- [low] `build_flat_paths()` usa `stack.pop(0)` + reconstrução de lista a cada iteração, resultando em complexidade O(n²) na travessia. Para XSDs muito grandes seria ineficiente, mas é aceitável no domínio atual. Considerar substituição por `collections.deque` com `popleft()` em futuras iterações se o domínio expandir.
- [low] Single-wrapper unwrapping (promoção dos filhos do elemento raiz para root_nodes) é um comportamento implícito documentado apenas em "Completion Notes". Esta decisão de design deve ser formalmente documentada na docstring de `_XsdParser.parse()` pois impacta todos os consumidores do FieldTree (Matching Engine 5.11, FieldNavigator Epic 6, VisibilityControl Epic 7).

### Technical Debt Registered
- Stage 29 cria uma lacuna numérica no pipeline (stages 1–28 são sequenciais, 29 é uma extensão). A numeração de stages não é parte de nenhum protocolo de ordenação execução — a ordem é determinada pelo `block_id` — portanto a lacuna não causa problema funcional. Monitorar se futuras stories adicionam stages no bloco 1 para evitar colisões.

### Decision Log
- `stage_number=29` escolhido para evitar conflito com Pipeline Result (stage 28): decisão correta, solução adequada. O refactoring do QA (ISSUE-1) tornou o registro idempotente e seguro.
- Single-wrapper unwrapping: decisão pragmática que alinha os paths com a expectativa dos consumidores downstream (ex: `cliente.nome` em vez de `documento.cliente.nome`). Arquiteturalmente sólida desde que documentada.
- lxml como dependency exclusiva para parsing XML/XSD: escolha correta. lxml é a biblioteca de referência para parsing XML em Python production, com suporte completo a namespaces e excelente performance.
