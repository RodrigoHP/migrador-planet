# Story 30.4 — patchNodeVisibility para visibility=false no canvas

## Story
**Como** operador ajustando a visibilidade de um campo no Inspector,
**Quero** que ao mudar `visibility` para `false` o elemento desapareça imediatamente no canvas,
**Para** ter feedback visual instantâneo da regra de visibilidade sem precisar reprocessar o PDF.

## Status
Done

## Business Value
`updateNodeProperty('visibility', false)` atualiza a árvore mas não tem patch de DOM — o
elemento permanece visível no canvas até o próximo `loadTemplateDraft`. Esta story
fecha o gap adicionando `patchNodeVisibility(nodeId, visible)` em `generation.ts` e
conectando-o ao `updateNodeProperty` quando `path === 'visibility'`.

**Nota sobre binding/formatString/styleRules:**
- `binding` e `formatString` são metadados sem impacto visual imediato — nenhum patch necessário
- `styleRules` / `borderOverrideCss` já é injetado via CSS gerado em `HTMLCanvas.vue` — também não precisa de patch de DOM

**Estimativa:** 2 story points (S)

## Scope

**IN:**
- `patchNodeVisibility(nodeId, visible: boolean)` em `generation.ts`:
  adiciona/remove `display:none` no elemento via DOMParser
- Conexão em `updateNodeProperty`: quando `path === 'visibility'` e `value` é `false`/`true` booleano
- Testes unitários: patchNodeVisibility + integração com updateNodeProperty
- Decisão documentada sobre binding/formatString/styleRules no Dev Notes

**OUT:**
- patch para `binding`, `formatString` (sem impacto visual — documentado)
- Novo sistema de CSS injection para `styleRules` (borderOverrideCss já cobre)
- Animação ou transição de visibilidade
- Visibilidade condicional por dados (VisibilityConfig com conditions — escopo diferente)

## Risks

| Risco | Probabilidade | Impacto | Mitigação |
|-------|--------------|---------|-----------|
| `visibility` como propriedade booleana vs VisibilityConfig object | Média | Médio | Guard: só aplicar patch se `typeof value === 'boolean'`; VisibilityConfig é usado por `applyOptionalVisibility` (path diferente) |
| `display:none` conflita com style inline existente | Baixa | Baixo | Usar setAttribute para sobrescrever o atributo style completo com display:none no final |

## Context

**Situação atual em `updateNodeProperty`:**

```typescript
mutationVersion.value++
if (path === 'text' && typeof value === 'string') {
  useGenerationStore().patchNodeText(nodeId, value)
}
// visibility, binding, formatString, styleRules → sem patch de DOM
```

**Como `patchNodeGeometry` manipula o style:**
```typescript
el.setAttribute('style', `position:absolute;left:${x}px;...`)
const patched = root.innerHTML
```

**Abordagem para visibility:**

```typescript
// Adicionar/remover display:none mantendo o style existente
const existingStyle = el.getAttribute('style') ?? ''
if (!visible) {
  // Preservar style atual + adicionar display:none
  const withoutDisplay = existingStyle.replace(/display\s*:\s*[^;]+;?/g, '').trim()
  el.setAttribute('style', withoutDisplay + (withoutDisplay ? ';' : '') + 'display:none')
} else {
  // Remover display:none
  const cleaned = existingStyle.replace(/display\s*:\s*none\s*;?/g, '').trim()
  el.setAttribute('style', cleaned)
}
```

**Arquivos a modificar:**
- `frontend/src/stores/generation.ts` — nova função `patchNodeVisibility`
- `frontend/src/stores/templateStore.ts` — `updateNodeProperty` conecta ao patch
- `frontend/src/stores/__tests__/templateStore.actions.spec.ts` — testes

## Dev Notes

**Decisão sobre binding/formatString:**
Estes são metadados usados pelo Knockout.js no template final gerado pelo backend.
No editor, não têm representação visual própria no canvas — são exibidos apenas no Inspector.
Aplicar patch de DOM para eles seria um no-op visual e adicionaria complexidade sem benefício.
**Decisão: nenhum patch de DOM para binding e formatString.**

**Decisão sobre styleRules:**
`borderOverrideCss` em `HTMLCanvas.vue:277` injeta CSS gerado a partir de `styleRules` de
todos os nós via `generateAllBorderOverrides(templateStore.flatNodes)`. Como é um `computed`
reativo, muda automaticamente quando `flatNodes` muda. **Nenhum patch de DOM adicional necessário.**

**Cuidado com VisibilityConfig:**
`node.properties.visibility` pode ser um `VisibilityConfig` object (para nós opcionais) ou
um `boolean` simples. O patch deve ser aplicado somente quando `typeof value === 'boolean'`.
