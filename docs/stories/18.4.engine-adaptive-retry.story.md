# Story 18.4 — Adaptive Retry Strategy

## Story
**Como** operador que executa workflows yolo_continuous,
**Quero** que o engine use estrategias progressivamente diferentes em cada retry (contexto → simplificacao → decomposicao) em vez de repetir o mesmo prompt,
**Para** que a taxa de abort seja reduzida porque abordagens diferentes sao tentadas antes de desistir.

## Status
Draft

## Context

### Problema

Hoje o engine tem 3 camadas de retry, mas todas usam a mesma estrategia — re-spawn com lembretes:
- Parse failure: re-spawn + FORMAT_REMINDER (max 2)
- Output missing: re-spawn + OUTPUT_REMINDER (max 2)
- Loop guard: re-spawn com mesmo prompt (max 3)

E como falar mais alto com alguem que nao entende a lingua. Se a primeira tentativa falhou, repetir o mesmo pedido tem baixa probabilidade de sucesso.

### Design

#### 3 Niveis de Retry

**Nivel 1 — Context Retry (tentativa 2):**
Mesmo prompt + failure context (Story 18.1). O subagente recebe o motivo da falha e tenta corrigir.

```
Prompt = original_prompt + {{FAILURE_CONTEXT}}
```

**Nivel 2 — Simplification Retry (tentativa 3):**
Prompt simplificado que reduz scope. Em vez de "implemente todos os ACs", foca nos ACs que falharam.

```
Prompt = simplified_prompt(original_prompt, failure_context)
  - Remove ACs ja satisfeitos (baseado em outputs anteriores)
  - Foca nos ACs que causaram a falha
  - Adiciona: "Foque APENAS nos pontos pendentes. NAO refaca o que ja funciona."
```

**Nivel 3 — Decomposition Retry (tentativa 4, se max_loops >= 4):**
Decompoe o step em sub-steps. Spawna o agente com um scope menor, depois completa o resto.

```
sub_steps = decompose_step(step, failure_context)
  - Sub-step A: "Primeiro crie/atualize os testes para os cenarios que falharam"
  - Sub-step B: "Agora implemente o codigo que faz os testes passarem"
Spawn sub_steps sequencialmente, acumular outputs
```

#### Configuracao

```yaml
# No workflow ou no engine_state:
retry_strategy:
  level_1: context        # Tentativa 2: adiciona failure context
  level_2: simplification # Tentativa 3: reduz scope
  level_3: decomposition  # Tentativa 4: decompoe em sub-steps
  fallback: abort         # Apos todas tentativas: abort com report
```

Workflows podem override por step:
```yaml
- step: implement_and_test
  retry_strategy:
    level_1: context
    level_2: context      # Override: manter context em vez de simplificar
    level_3: abort        # Override: abortar em vez de decompor
```

#### Logica no Sequence Advancer

```
FUNCTION get_retry_strategy(step, state, attempt):
  config = step.retry_strategy or workflow.retry_strategy or DEFAULT_RETRY_STRATEGY

  IF attempt == 1: RETURN "context"         # level_1
  IF attempt == 2: RETURN "simplification"  # level_2
  IF attempt == 3: RETURN "decomposition"   # level_3
  RETURN "abort"

FUNCTION build_retry_prompt(step, state, strategy, failure_context):
  SWITCH strategy:
    "context":
      RETURN original_prompt + format_failure_context(failure_context)

    "simplification":
      pending_acs = extract_pending_acs(failure_context)
      RETURN simplify_prompt(original_prompt, pending_acs)

    "decomposition":
      sub_prompts = decompose_into_sub_steps(step, failure_context)
      RETURN sub_prompts  # Array — engine spawns each sequentially

    "abort":
      RETURN null  # Signal to abort
```

#### Interacao com loop_guard

O loop_guard default sobe de 3 para 4 quando adaptive retry esta habilitado (para acomodar os 3 niveis + original). Configuravel:

```yaml
loop_guard:
  max_loops_per_target: 4  # Was 3, now 4 to accommodate 3 retry levels
```
