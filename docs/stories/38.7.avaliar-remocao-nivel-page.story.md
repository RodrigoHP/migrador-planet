## Story

**As a** template developer,
**I want** the structural tree hierarchy to be evaluated for removing the intermediate `page` level,
**so that** the document tree is simpler (`document > header/flow/footer > elementos`) without unnecessary nesting, or an ADR documents why `page` must be kept.

## Acceptance Criteria

1. [ ] Avaliar impacto em: `usePagination.ts`, `HTMLCanvas.vue`, `stage5_template_generation.py`
2. [ ] Se seguro aplanar: remover nível `page` → `document > header/flow/footer > elementos`
3. [ ] Se não seguro: documentar ADR explicando por que `page` é necessário
4. [ ] Árvore exibe hierarquia conforme decisão (com ou sem page)
5. [ ] Nenhuma regressão em paginação ou Canvas

## Dev Notes

### Contexto do Gap (I14)

A árvore estrutural gerada pelo `stage3_structural_analysis.py` inclui um nível intermediário `page` entre `document` e os blocos `header/flow/footer`. A hierarquia atual é:

```
document > page > header/flow/footer > elementos
```

A proposta é avaliar se este nível `page` é necessário ou se pode ser aplainado para:

```
document > header/flow/footer > elementos
```

### Pontos Críticos de Avaliação

1. **Paginação:** `usePagination.ts` pode usar `page` nodes para controlar navegação entre páginas no Canvas. Se sim, remoção requer alternativa.
2. **Canvas:** `HTMLCanvas.vue` renderiza elementos — verificar se `page` boundaries são usados para layout.
3. **Template Generation:** `stage5_template_generation.py` pode emitir page breaks HTML baseados no nível `page`.
4. **Multi-page PDFs:** Documentos com múltiplas páginas podem precisar de `page` para manter a separação.

### Source Tree Relevante

```
backend/
  pipeline/stage3_structural_analysis.py  — gera árvore estrutural
  pipeline/stage5_template_generation.py  — consome árvore para gerar template
frontend/
  src/composables/usePagination.ts        — lógica de paginação
  src/organisms/HTMLCanvas.vue            — renderização Canvas
  src/organisms/StructureTree.vue         — exibição árvore sidebar
```
