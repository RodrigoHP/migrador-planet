# Story 13.1 — Storage Gateway: Abstração + Implementações Supabase/Local

## Story
**Como** pipeline de migração,
**Quero** persistir artefatos (PDFs, screenshots, imagens, thumbnails, resultados) via abstração de storage,
**Para** que o pipeline funcione tanto em produção (Supabase Storage) quanto em desenvolvimento (disco local) sem acoplamento direto.

## Status
Done

## Context

### Problema
O pipeline atual salva TUDO em `/tmp/jobs/{jobId}/` com TTL de 1 hora. Problemas:

| Problema | Impacto |
|----------|---------|
| **Volatilidade** | Dados perdidos em restart/deploy/crash |
| **Sem escala horizontal** | 2 instâncias = job not found |
| **Assets sem cleanup** | `/tmp/templates/{id}/assets/` acumula infinitamente |
| **Sem versionamento** | Impossível rastrear qual pipeline gerou qual resultado |
| **Pipeline v3 piora** | Mais artefatos: thumbnails pHash, LLM, multi-PDF |

### Estado Atual

Todos os arquivos usam `TMP_BASE = Path(os.environ.get("JOBS_DIR", "/tmp/jobs"))`:
- `backend/routers/upload.py` — `create_job_dir()` / `get_job_dir()`
- `backend/routers/analyze.py` — lê PDFs de `/tmp`
- `backend/routers/assets.py` — CRUD de assets em `/tmp`
- `backend/services/stages/screenshot_generator.py` — salva PNGs em `/tmp/{job_id}/screenshots/`
- `backend/services/stages/image_extraction.py` — salva em `/tmp/{job_id}/assets/`
- `backend/services/stages/pipeline_result.py` — salva result_json (Supabase já existe parcial)

### Solução
Criar `StorageGateway` (ABC) com 2 implementações + factory. Configuração por `STORAGE_MODE` explícito.

## Acceptance Criteria

1. `StorageGateway` ABC com 10 métodos abstratos:
   - `upload_pdf(job_id, index, content) → str`
   - `upload_screenshot(job_id, page_key, png_bytes) → str`
   - `upload_asset(job_id, filename, content) → str`
   - `upload_thumbnail(job_id, page_key, png_bytes) → str`
   - `get_local_path(job_id, filename) → Path`
   - `get_signed_url(bucket, path, expires_in) → str`
   - `save_result(job_id, result_json) → None`
   - `save_clusters(job_id, clusters) → None`
   - `cleanup_local(job_id) → None`
   - `delete_job(job_id) → None`

2. `SupabaseStorageGateway` funcional:
   - Upload para Supabase Storage (bucket `jobs`)
   - Download para cache local (PyMuPDF precisa de Path)
   - Signed URLs para frontend
   - save_result e save_clusters via Supabase DB
   - delete_job remove Storage + DB (cascade)

3. `LocalStorageGateway` funcional:
   - Encapsula comportamento atual de `/tmp/jobs`
   - `get_signed_url` retorna `/api/files/{path}`
   - save_result salva JSON local
   - save_clusters salva JSON local

4. Factory `create_storage_gateway()`:
   - `STORAGE_MODE=supabase` → `SupabaseStorageGateway`
   - `STORAGE_MODE=local` → `LocalStorageGateway`
   - Sem config → **ERRO** na inicialização (obriga definir)
   - **NÃO faz fallback automático** — se cloud falha, pipeline falha (checkpoint)

5. SQL migrations para Supabase:
   - Tabela `job_clusters` (job_id FK, cluster_id, pages, representative, confidence)
   - Tabela `templates` (id, name, result_json, created_at, updated_at)
   - Bucket policies para `jobs` e `templates`

6. `StorageMode` enum com `SUPABASE` e `LOCAL`

7. Configuração via `STORAGE_MODE` no `.env` / settings

8. Testes unitários para ambas implementações (mock Supabase)

### Cardinal Rule Verification
CONFIRMED: No silent fallback from Supabase to local storage exists anywhere in the code. The SupabaseStorageGateway propagates all Supabase errors (delete_job catches, logs, then re-raises). The factory raises ConfigurationError if STORAGE_MODE is missing or if supabase credentials are absent. The __init__.py docstring and gateway.py docstring both explicitly document this rule.

### Minor Observations (non-blocking)
1. The architecture pseudocode's `delete_job` deletes files one-by-one in a loop; the implementation batches the remove call. This is a valid improvement -- no issue.

3. The `upload_asset` in LocalStorageGateway does not set content-type. Acceptable for local dev mode.
