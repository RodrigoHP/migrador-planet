## Status

## Story
**As a** bloco do pipeline,
**I want** validar a consistência dos mapeamentos do bloco 7 e gerar um draft HTML/CSS completo para o Canvas,
**so that** o editor possa carregar com um template completo auto-populado.

1. Stage 22 — Layout Consistency Validation: validar cruzado skeleton vs resultado final, verificar todos campos XSD contabilizados, verificar que não há mapeamentos órfãos

3. Coverage calculado: elementos mapeados vs total detectado (FR29)
4. Pipeline result JSON: { document_structure, field_mappings[], confidence_scores{}, coverage{}, layout_types[], template_draft{ html, css }, ambiguous_fields[], format_functions[] }
5. Resultado armazenado no Supabase (jobs.result_json) e disponível via GET /api/analyze/{job_id}/result
6. Testes cobrem: regras de validação, estrutura do template draft, pipeline result JSON

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: LOW. Stage 26 lê `field_mappings`, `field_tree`, `parsed_documents` e `tables` sem acoplamento a implementações específicas. Stage 27 gera HTML/CSS puramente a partir de contexto — sem dependências de I/O ou LLM. Stage 28 é um consolidador terminal que nunca lança exceção (fail-safe correto para último stage do pipeline).
- Cohesion: HIGH. Stage 26 = validação cruzada apenas, Stage 27 = geração de artefatos HTML/CSS, Stage 28 = consolidação e persistência. A separação em três stages distintos (em vez de um mega-stage) segue o princípio de responsabilidade única e facilita debugging.
- Patterns: Padrão StageRegistry seguido. O pattern de persistência fail-safe no Stage 28 (`_persist_to_supabase` com `except Exception`) é correto para garantir que falha de rede não aborte o pipeline após todo o processamento. O template HTML usa Knockout.js `data-bind` e `<!-- ko foreach -->`, alinhado com o motor existente do Canvas.
- Scalability: Stage 27 é geração in-memory de strings — adequado para documentos de tamanho esperado (documentos financeiros/fiscais brasileiros). Não há limitação arquitetural para o volume previsto. Stage 28 faz apenas uma operação de escrita no Supabase por job.

### Issues Found

**[LOW] `layout_types` duplicado no result_json do Stage 28**
- Confirmado pelo QA (CONCERN-2). O schema de `result_json` em `pipeline_result.py` inclui `layout_types` tanto dentro de `document_structure.layout_types` quanto como chave top-level. O AC-4 especifica ambas as chaves, portanto está correto conforme spec — mas cria redundância que pode causar inconsistência se editado em apenas um lugar. Sugere-se consolidar em Sprint futura revisando o AC para permitir referência por ponteiro ao invés de duplicação.
- Severity: LOW

**[LOW] `register_bloco9` nomeia Bloco 9 mas registra stages em block_id=8**
- Inconsistência nominal na função de registro. Não tem impacto funcional mas viola convenção de naming do projeto (register_blocoN → N = block_id dos stages registrados).
- Severity: LOW

**[LOW] Stale comments em dois arquivos**
- `register_all.py` linha 19: docstring `register_bloco1()` cita "stage 28" incorretamente.
- `analyze.py` linha 71: docstring `_run_pipeline` diz "27-stage pipeline" (deveria ser 28).
- Severity: LOW (documentação interna)
- Ação sugerida para @dev: corrigir como follow-up.

**[OBSERVATION] Template Draft não incorpora fontes extraídas do PDF**
- O AC-2 menciona "Fontes extraídas do PDF (Story 5.5)" no CSS. A implementação atual usa `Arial, sans-serif` hardcoded como fallback. Se `context["layout_types"]` ou `context["parsed_documents"]` contiverem metadados de fonte, esses não são consumidos pelo Stage 27. Não é um bug (o template é um draft), mas é um gap funcional a documentar.
- Severity: LOW (gap de feature, não de design)

### Decision Log
- A decisão de Stage 28 nunca lançar exceção (fail-safe Supabase) é arquiteturalmente correta: o pipeline já completou toda computação e não deve falhar por problemas de persistência. O resultado está disponível em `context["result_json"]` independentemente do Supabase.
- Stage 26 reporta warnings e errors separadamente (não mistura) — correto para que o consumidor possa tratar com granularidade diferente (warnings = informativo, errors = problema de integridade de mapeamento).
- A escolha de não usar LLM no Stage 26 (validação puramente determinística) é decisão correta: validação deve ser previsível e auditável, não probabilística.
