# Story 10.19: Bug — Canvas exibe layout linear em vez de posicionado como o PDF original

## Status
Done

## Story
**As a** operador,
**I want** que o canvas do editor reproduza aproximadamente o posicionamento espacial dos campos conforme estão no PDF original,
**so that** eu possa visualizar o template gerado com fidelidade ao layout do documento e identificar rapidamente campos fora de posição antes de editar.

## Acceptance Criteria
1. O canvas reproduz aproximadamente as posições (X, Y) dos campos conforme estão no PDF original — campos que no PDF aparecem lado a lado não devem ser empilhados verticalmente no canvas
2. Campos com coordenadas `bbox` disponíveis nos `field_mappings` usam `position: absolute; left: {x}px; top: {y}px` no HTML gerado pelo Stage 27
3. Campos sem coordenadas (fallback — `bbox` ausente ou nulo) continuam usando o fluxo linear atual (`display: flex` em `.flow`) sem quebrar o canvas
4. O CSS gerado inclui escala adequada para converter coordenadas de pontos PDF para pixels no canvas: escala A4 (595×842 pt → 794×1123 px)
5. `pytest backend/tests/` passa sem erros após as alterações

## Análise Técnica

### 1. O que `text_extraction.py` já extrai

O Stage 2 (`text_extraction.py`) usa PyMuPDF (`fitz`) e já extrai coordenadas completas por span:

```python
x0, y0, x1, y1 = span["bbox"]
blocks.append(
    TextBlock(
        text=text,
        bbox=(x0, y0, x1, y1),   # (x0, y0, x1, y1) em pontos PDF
        ...
    )
)
```

O modelo `TextBlock` (em `backend/models/parsed_document.py`) define:
```python
bbox: Tuple[float, float, float, float]  # (x0, y0, x1, y1) in PDF points
```

**Conclusão:** As coordenadas já existem nos `text_blocks` desde o Stage 2, em pontos PDF (pt), onde (0,0) é o canto superior esquerdo da página. Para A4: largura = 595 pt, altura = 842 pt.

### 2. O que `field_matching.py` propaga

O Stage 23 (`field_matching.py`) usa o `_make_mapping()` para construir os `field_mappings`. A função atual **não inclui `bbox`** — ela registra apenas `pdf_text`, `label_text`, `xsd_field_path`, `confidence`, `page_number` e `pdf_index`.

O bloco iterado em `execute()`:
```python
for blk in all_blocks:
    # blk tem: text, bbox, font_name, font_size, page_number, pdf_index, semantic_label
    value_text = blk.get("text", "").strip()
    label_text = _find_adjacent_label(blk, all_blocks) or ""
    # ... _make_mapping() chamado sem bbox
```

**Conclusão:** As coordenadas estão disponíveis em `blk["bbox"]` mas NÃO são propagadas para `field_mappings`. Este é o elo ausente da cadeia.

### 3. O que Stage 27 precisa receber

Para gerar `position: absolute; left: {x}px; top: {y}px`, o Stage 27 precisa:
- `mapping["bbox"]` = `(x0, y0, x1, y1)` em pontos PDF, OU
- `mapping["x_px"]` e `mapping["y_px"]` já convertidos para pixels

A abordagem preferida é propagar `bbox` do bloco de valor (coordenada do campo no PDF) e deixar o Stage 27 aplicar a conversão de escala.

### 4. Cálculo de escala PDF pt → px canvas

PDF A4 em pontos: 595 × 842 pt
Canvas A4 em pixels: 794 × 1123 px (equivalente a 96 DPI)

```
scale_x = 794 / 595  ≈ 1.3345
scale_y = 1123 / 842 ≈ 1.3337

x_px = x0_pt * scale_x
y_px = y0_pt * scale_y
```

Para PDFs com dimensões diferentes do A4 padrão, a escala deve ser derivada das dimensões reais da página (disponíveis via `fitz.Page.rect`). Inicialmente, usar escala A4 como padrão.

### 5. O que precisa mudar

**Arquivo 1 — `backend/services/stages/field_matching.py` (Stage 23):**
- `_make_mapping()`: adicionar parâmetro `bbox: Optional[Tuple]` e incluí-lo no dict retornado
- `execute()`: passar `blk.get("bbox")` ao chamar `_make_mapping()`
- O `bbox` da label adjacente também pode ser registrado como `label_bbox` (opcional, para referência)

**Arquivo 2 — `backend/services/stages/template_draft.py` (Stage 27):**
- `_generate_field_element()`: quando `mapping.get("bbox")` está presente, gerar `style="position: absolute; left: {x}px; top: {y}px;"` no `div.field-group`
- `_generate_page_html()`: quando qualquer campo tem `bbox`, o `.flow` deve usar `position: relative` (não `absolute` + `overflow: hidden`) para conter os campos posicionados absolutamente
- Constantes de escala A4: `SCALE_X = 794 / 595`, `SCALE_Y = 1123 / 842`
- Fallback: campos sem `bbox` continuam como hoje (fluxo linear)

**Arquivo 3 — CSS em `template_draft.py`:**
- `.flow` com campos posicionados: remover `overflow: hidden` ou mudar para `overflow: visible`
- Adicionar `.field-group.positioned { position: absolute; }` para campos com coordenadas

### 8. Pseudocódigo do fix em `template_draft.py`

```python
SCALE_X = 794 / 595   # A4: 595pt → 794px
SCALE_Y = 1123 / 842  # A4: 842pt → 1123px

def _bbox_to_style(bbox):
    """Convert PDF bbox (x0, y0, x1, y1) in pt to CSS absolute positioning."""
    if not bbox or len(bbox) < 2:
        return None
    x_px = round(bbox[0] * SCALE_X)
    y_px = round(bbox[1] * SCALE_Y)
    return f"left: {x_px}px; top: {y_px}px;"

def _generate_field_element(mapping, field_tree):
    ...
    bbox = mapping.get("bbox")
    style = _bbox_to_style(bbox)

    if style:
        class_attr = 'class="field-group positioned"'
        style_attr = f'style="{style}"'
    else:
        class_attr = 'class="field-group"'
        style_attr = ""

    return f'<div {class_attr} {style_attr}>\n  ...\n</div>'
```

### Escala e dimensões
- PDF A4 em pontos: 595 × 842 pt (72 DPI)
- Canvas A4 em pixels: 794 × 1123 px (96 DPI equivalente)
- `scale_x = 794 / 595 ≈ 1.3345`
- `scale_y = 1123 / 842 ≈ 1.3337`
- Coordenadas PyMuPDF: origin (0,0) no canto superior esquerdo, Y cresce para baixo — compatível com CSS `top`

### Coordenada do campo: usar x0, y0 do bloco de VALOR
A `bbox` propagada em Stage 23 é do bloco de valor (não do label). O x0, y0 do bloco de valor é o canto superior esquerdo desse campo no PDF, que é a posição onde o `div.field-group` deve ser renderizado. O label visual (`<span class="label">`) ficará à esquerda do valor no flow normal do flex dentro do `div`.

Para campos com `bbox` disponível, o ideal seria usar `x0` do label (se existir) como posição inicial do `div`, já que o label precede o valor. Isso é uma melhoria futura — na primeira implementação, usar `x0` do bloco de valor é aceitável.
