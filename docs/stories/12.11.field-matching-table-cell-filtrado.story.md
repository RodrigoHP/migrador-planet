# Story 12.11 — Bug CRÍTICO: table_cell filtrado em field_matching

## Story
**Como** usuário que analisa boletos bancários,
**Quero** que os campos nas tabelas do boleto sejam mapeados ao XSD,
**Para** que coverage e campos não fiquem sempre em 0%.

## Status
Done

## Context

### Este é o bug mais importante do Epic 12

Após confirmar que o XSD é sempre fornecido, a investigação profunda revelou que:

1. ✅ Stage 29 (XSD Parser) está registrado corretamente em Block 1
2. ✅ `register_all()` é chamado no startup — stages são injetados
3. ✅ `schema.xsd` é salvo em `/tmp/jobs/{id}/schema.xsd` (upload.py)
4. ✅ Stage 29 encontra e lê o arquivo — `field_tree` é populado
5. ✅ `flat_paths` tem os campos do XSD

**MAS:**

6. ❌ Stage 19 (Semantic Analysis) classifica blocos dentro de tabelas como `semantic_label = "table_cell"`
7. ❌ Stage 23 (Field Matching) tem `_STRUCTURAL_LABELS = frozenset({"table_cell", ...})`
8. ❌ Blocos com `semantic_label = "table_cell"` são **completamente ignorados** no field matching

### Por que isso destrói os resultados com boletos

Um boleto bancário tem estrutura **quase inteiramente tabular**:

```
┌──────────────────────────────────────────────────────┐
│ Tabela principal (todos os campos são "table_cell"): │
│  Beneficiário | Valor | Nosso Número | Vencimento    │
│  Agência      | Data  | N° Documento | Pagador       │
└──────────────────────────────────────────────────────┘
```

Todos esses campos (Beneficiário, Valor, Nosso Número, etc.) são detectados como `table_cell` pelo Stage 18 (Table Structuring) e confirmados pelo Stage 19 (Semantic Analysis).

**Resultado**: Stage 23 processa **0 blocos** → `field_mappings = []` → **Coverage = 0/N = 0%**

### Evidência no Código

```python
# backend/services/stages/field_matching.py linha 38-47
_STRUCTURAL_LABELS = frozenset({
    "header",
    "footer_text",
    "page_number",
    "title",
    "table_header",
    "table_cell",    # ← TODO OS CAMPOS DO BOLETO CAEM AQUI
    "label",
    "image",
})

# linha 258-262 (execute)
for blk in all_blocks:
    if blk.get("semantic_label", "") in _STRUCTURAL_LABELS:
        continue  # ← SKIP SILENCIOSO — sem log, sem alerta
```

### Por que `table_cell` foi colocado em _STRUCTURAL_LABELS?

Provavelmente por design inicial onde table_cells eram tratados separadamente (Stage 18 já estrutura as tabelas). Mas o pipeline nunca implementou matching específico para cells de tabela — `context["tables"]` existe mas não é processado pelo field matching.

### Solução

#### Opção A (Simples — recomendada agora): Remover `table_cell` de _STRUCTURAL_LABELS

```python
_STRUCTURAL_LABELS = frozenset({
    "header",
    "footer_text",
    "page_number",
    "title",
    "table_header",
    # "table_cell",  ← REMOVER — deve ser processado como campo
    "label",
    "image",
})
```

E adaptar `_find_adjacent_label()` para células de tabela:
- Célula adjacente na mesma linha com `table_header` = label
- Célula na posição `(row, col-1)` = possível label

#### Opção B (Robusto — futuro): Matching específico para tabelas

```python
# Adicionar lógica específica para tabelas estruturadas
async def _match_table_cells(table: Dict, flat_paths: List[str]) -> List[Dict]:
    """Para cada coluna da tabela, tenta mapear cabeçalho → XSD path."""
    mappings = []
    for row in table.get("rows", []):
        for i, cell in enumerate(row.get("cells", [])):
            header = table.get("headers", [])[i] if i < len(table.get("headers", [])) else ""
            # Match header text → XSD path
            candidates = await _llm_match(header, cell["text"], flat_paths)
            if candidates:
                mappings.append(_make_mapping(
                    pdf_text=cell["text"],
                    label_text=header,
                    xsd_field_path=candidates[0]["path"],
                    ...
                ))
    return mappings
```

**Para esta story: implementar Opção A** (remove `table_cell` de _STRUCTURAL_LABELS).
