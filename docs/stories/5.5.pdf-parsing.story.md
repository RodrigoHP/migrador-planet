# Story 5.5: Bloco 2: PDF Parsing — Extração de Texto, Fontes, Imagens e Grid

## Status
Ready for Review

## Story
**As a** estágio do pipeline,
**I want** extrair texto (com reconstrução), fontes, imagens e estrutura de grid de cada PDF carregado,
**so that** os estágios subsequentes tenham dados estruturais completos para trabalhar.

## Acceptance Criteria
1. Stage 2a — Text Extraction: extrair TextBlocks com bbox, font, font_size, conteúdo de texto de cada página de cada PDF
2. Stage 2b — Text Reconstruction: unir spans fragmentados ("Cl"+"iente"→"Cliente") usando proximidade Y, fonte similar, espaçamento X
3. Stage 2c — Font Extraction→CSS: extrair metadados de fonte por span, normalizar para CSS (font-family, font-size, font-weight)
4. Stage 2d — Image Extraction: extrair imagens embarcadas (logos, selos, ícones), salvar em Supabase Storage /assets/{job_id}/
5. Stage 2e — Grid Detection: clusterizar coordenadas X/Y para detectar colunas e linhas, output grid info { columns: N, rows: M, coordinates }
6. Screenshots de página (PNG) gerados para Vision AI (stage 5.10)
7. Todos os estágios registrados no orchestrator (5.4) e emitindo SSE progress
8. Output: ParsedDocument por PDF com pages[], cada contendo text_blocks[], images[], fonts[], grid_info, screenshot_path
9. PDFs protegidos por senha são detectados no início do estágio; pipeline marca o PDF como failed com mensagem "PDF protegido por senha — remova a proteção e faça upload novamente"
10. PDFs com mais de 500 páginas: processar todas para text extraction, mas screenshots gerados apenas para páginas amostradas (~50 páginas distribuídas uniformemente)
11. Testes cobrem: precisão da reconstrução de texto, mapeamento de fontes, extração de imagens, detecção de grid, PDF protegido

## Dev Notes

### Biblioteca Principal
- PyMuPDF (fitz) 1.24+ para todas as operações de extração
- Instalação: `pip install PyMuPDF`

### Text Reconstruction — CRÍTICO
- Sem reconstrução, anchors e field matching falham
- PDFs frequentemente fragmentam texto em spans individuais por caractere ou sílaba
- O algoritmo de merge precisa ser robusto para:
  - Diferentes tamanhos de fonte na mesma linha
  - Espaços entre palavras vs fragmentação
  - Texto em múltiplas colunas (não merge entre colunas)

### Mapa de Normalização de Fontes
```python
FONT_MAP = {
    "Helvetica": "Arial",
    "Helvetica-Bold": "Arial",
    "Helvetica-Oblique": "Arial",
    "Times-Roman": "Times New Roman",
    "Times-Bold": "Times New Roman",
    "Courier": "Courier New",
    "Courier-Bold": "Courier New",
}
```

### Grid Detection
- Gap-analysis determina número natural de clusters (evita overfitting)
- scikit-learn KMeans com fallback sem sklearn (gap-based partition)
- Grid detection alimenta table detection (Story 5.9)

### Screenshots
- PyMuPDF renderiza página como pixmap
- Resolução: 150 DPI (equilíbrio qualidade/tamanho para Vision AI)
- Fallback local: /tmp/{job_id}/screenshots/

### Supabase Storage
- Imagens: `/assets/{job_id}/img_{page}_{index}.{ext}` (fallback: /tmp/{job_id}/assets/)
- Screenshots: `/screenshots/{job_id}/page_{N}.png` (fallback: /tmp/{job_id}/screenshots/)
- Resultados ficam em memória (passados entre estágios via context["parsed_documents"])

### Issues Found

**[MEDIUM] BUG — Fallback de PDF discovery quebrado em text_extraction.py**
- Arquivo: `backend/services/stages/text_extraction.py`, linhas 110-112
- Descrição: O fallback quando `pdf_files` é vazio constrói um generator expression e chama `.__class__()` sobre ele, o que resulta em uma lista vazia em vez de busca recursiva. O `rglob("*.pdf")` nunca é executado.
- Severidade: MEDIUM (afeta somente jobs com estrutura de diretório não-padrão, mas o fallback é silenciosamente ineficaz)
- Suggested owner: @dev

**[LOW] Inconsistência de path — image_extraction.py e screenshot_generator.py ignoram tmp_base do contexto**
- Arquivo: `backend/services/stages/image_extraction.py` L100; `backend/services/stages/screenshot_generator.py` L94
- Descrição: `assets_dir` e `screenshots_dir` são construídos como `Path("/tmp") / job_id / ...` em vez de `tmp_base / job_id / ...`. Isso faz com que os caminhos sejam sempre `/tmp/{job_id}/...` independente do `tmp_base` configurado no contexto, quebrando ambientes de teste e deployments com tmp configurável.
- Severidade: LOW (funcional em produção Linux com /tmp, mas inconsistente e quebra testes com tmpdir customizado)
- Suggested owner: @dev

**[MEDIUM] AC 6 / AC 8 — screenshot_generator não registrado no pipeline padrão**
- Arquivo: `backend/services/stages/register_all.py` (register_bloco2)
- Descrição: `register_bloco2()` registra apenas os 5 stages (2-6). O `screenshot_generator` possui `register_as_stage()` mas não é chamado em `register_bloco2`. O campo `screenshot_path` permanecerá `None` em todos os `ParsedPage` a menos que o consumidor chame `screenshot_generator.execute()` manualmente. AC 6 e AC 8 (campo screenshot_path) ficam dependentes de integração manual não documentada.
- Severidade: MEDIUM (AC parcialmente não-atendido na integração padrão do pipeline)
- Suggested owner: @dev

**[LOW] AC 7 — SSE progress não emitido pelos stages**
- Descrição: Nenhum dos stages (2-6) chama função de SSE/progress durante execução. O orchestrator pode emitir eventos por conta própria baseado nos retornos, mas o AC exige que os estágios "emitam SSE progress". Sem ver o orchestrator (Story 5.4), esta pode ser uma responsabilidade do orchestrator já implementada, mas não é verificável pelo código dos stages.
- Severidade: LOW (possivelmente já tratado pelo orchestrator de Story 5.4 — requer confirmação)
- Suggested owner: @dev (confirmar com @architect se orchestrator já cobre)

**[LOW] Ausência de testes para image extraction (AC 4)**
- Arquivo: `backend/tests/test_pdf_parsing.py`
- Descrição: Nenhum dos 19 testes cobre `_extract_images_from_pdf` ou o executor `image_extraction.execute()`. AC 11 exige cobertura de "extração de imagens" mas os testes existentes não a exercitam.
- Severidade: LOW (ausência de teste, não um bug de implementação)
- Suggested owner: @dev

**[LOW] Patching frágil em test_encrypted_pdf_raises_value_error**
- Arquivo: `backend/tests/test_pdf_parsing.py`, linhas 241-272
- Descrição: O teste usa três camadas de patch (patch do atributo do módulo com create=True, patch de sys.modules, patch de builtins.__import__) para interceptar o `import fitz` lazy dentro de `_extract_text_from_pdf`. Esta abordagem é frágil — se o módulo `fitz` já estiver em `sys.modules` de um teste anterior, o patch pode não ser eficaz. O padrão recomendado é injetar a dependência diretamente (parâmetro opcional) ou usar `importlib.reload` com patch de sys.modules somente (como já feito em test_encrypted_pdf_stage_records_error).
- Severidade: LOW (teste pode passar na maioria dos casos mas é não-determinístico em sequência de testes)
- Suggested owner: @dev
