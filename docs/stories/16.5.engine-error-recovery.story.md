# Story 16.5 — Retry Inteligente para Parse Failures

## Story
**Como** operador que executa workflows em `yolo_continuous`,
**Quero** que parse failures (subagente retorna output fora do formato esperado) sejam retried automaticamente com format reminder,
**Para** que falhas transientes de formatacao nao abortem o workflow inteiro.

## Status
Done

## Context

### Problema

Quando `step_failed()` detecta `parsed_output is null` (parse failure), o engine trata como falha definitiva. Se nao ha `on_failure` definido, o workflow aborta imediatamente. Porem, parse failures sao frequentemente transientes — o subagente produziu output util mas fora do formato YAML esperado. Um retry com format reminder resolveria a maioria dos casos.

Atualmente, parse failures e execution failures (status: failed) sao tratados identicamente. Nao ha retry especifico para problemas de formato, e o subagente nao recebe feedback sobre o que deu errado.

### Referencia

- Engine: `.aios-core/development/tasks/run-workflow-engine.md` (v3.0)
- `step_failed()` function: trata null como falha

### Design Proposto

**Separar parse failures de execution failures:**

```
FUNCTION handle_step_result(parsed_output, step, state):
  IF parsed_output is null:
    → parse_failure_retry(step, state)  # retry com format reminder
  ELSE IF parsed_output.status == "failed":
    → execution_failure_route(step, state)  # rota on_failure existente
```

**Retry com format reminder:**
```
FUNCTION parse_failure_retry(step, state):
  retries = state.parse_retries[step.id] or 0
  max = workflow.global_error_handling.max_retries_per_phase or 2

  IF retries < max:
    state.parse_retries[step.id] = retries + 1
    prompt = original_prompt + FORMAT_REMINDER
    re_spawn(step, prompt)
  ELSE:
    IF step.on_failure: route to on_failure
    ELSE: ABORT "parse_failure_after_retries"
```

**Format Reminder** adicionado ao prompt no retry:
```
## FORMAT REMINDER
Your output MUST include this exact block:
\`\`\`yaml
step_output:
  status: completed|failed
  outputs:
    key: value
\`\`\`
Previous attempt did not include this block.
```

## Acceptance Criteria

- [ ] AC1: Parse failures (null output) tratados separadamente de execution failures (status: failed)
- [ ] AC2: Parse failure causa retry automatico com format reminder no prompt (max 2 retries por default)
- [ ] AC3: `max_retries_per_phase` configuravel no workflow YAML (campo `global_error_handling`)
- [ ] AC4: Contador `state.parse_retries[step_id]` rastreia retries por step
- [ ] AC5: Apos esgotar retries, parse failure segue fluxo normal: `on_failure` se definido, senao ABORT
- [ ] AC6: Format reminder adicionado ao prompt apenas nos retries (nao no primeiro spawn)
- [ ] AC7: Execution log registra eventos `parse_failure_retry` com attempt number
- [ ] AC8: Final Report inclui parse failures e retries na secao de erros

## Complexity

**T-shirt size:** S (Small)
**Estimativa:** Bifurcar handle de null vs failed, adicionar retry loop com counter, format reminder template.

## Scope

**IN:**
- `.aios-core/development/tasks/run-workflow-engine.md` — separar parse/execution failures, retry com reminder
- State field `parse_retries`
- Format reminder template

**OUT:**
- Nao alterar subagent-step-prompt.md (format reminder so no retry)
- Nao implementar retry para execution failures (ja tem on_failure routing)
- Nao alterar modo step-by-step (ja oferece opcoes ao usuario)

## Risks

- Format reminder pode nao ser suficiente para subagentes que consistentemente produzem output fora do formato esperado (ex: modelo com tendencia a texto livre). Mitigacao: max 2 retries por default, abort apos esgotar.
- Retry loop adiciona latencia ao workflow. Cada retry eh um novo spawn completo do subagente. Mitigacao: retry conta no timeout do step (se 16.2 implementado).
