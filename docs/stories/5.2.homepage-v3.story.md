## Story

**I want** que a Home exiba dois cards (Novo Template + Abrir Projeto) com descrições e um botão Bibliotecas,

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED

### Design Assessment

- **Coupling: LOW.** `HomePage.vue` depende de `Button`, `BibliotecasModal`, `FullWidthLayout`, `useSessionStore`, `useMappingStore`, `useLayoutStore` e `useGenerationStore`. A dependência nos quatro stores para o reset em `startNew()` é necessária e explícita — não há acoplamento oculto. `BibliotecasModal` é gerenciado via prop `show-bibliotecas` no `FullWidthLayout` e evento `@open-bibliotecas`, mantendo o componente pai desacoplado da implementação interna do modal.
- **Cohesion: HIGH.** O componente tem responsabilidade bem definida: tela de entrada com duas ações (nova migração / abrir projeto). As três funções do `<script setup>` — `startNew()`, `triggerFilePicker()` e `onFileSelected()` — são pequenas, diretas e sem lógica transversal. A delegação do estado de navegação via Pinia stores (em vez de props ou eventos globais) é o padrão correto para Vue 3 + Pinia.
- **Patterns:** Composition API com `ref` e funções inline — correto para a complexidade do componente. O padrão de hidden `<input type="file" ref="fileInput">` disparado por `triggerFilePicker()` é a abordagem canônica para file pickers customizados em Vue 3, com `input.value = ''` para reset correto. A prop `show-bibliotecas` no `FullWidthLayout` para sinalizar a disponibilidade do botão de Bibliotecas é uma solução limpa que evita duplicar lógica de header em cada página que usa esse layout. Tailwind utility classes sem scoped CSS é consistente com o padrão adotado no Epic 5.
- **Scalability:** Componente de entrada sem lógica computacional pesada. O reset de quatro stores em `startNew()` é operação O(1) e não apresenta risco de escala. A leitura de arquivo JSON com `file.text()` + `JSON.parse()` é synchronous-blocking para arquivos grandes, mas é aceitável dado que projetos salvos são pequenos JSONs de estado de aplicação — não documentos raw.

### Issues Found

**[LOW] `session.$reset()` + `session.$patch({ analysisCompleted: true })` em `onFileSelected` — bypass intencional do guard sem validação de schema**
- `HomePage.vue` linha 95-96: a sequência `session.$reset()` seguida de `session.$patch({ analysisCompleted: true })` força a passagem do guard de `/editor` sem validação da estrutura do projeto carregado. O bypass é intencional (documentado nas Completion Notes) e aceitável para o escopo do Epic 5, mas cria um estado inconsistente: o `sessionStore` terá `analysisCompleted: true` mas `jobId: null`, `pdfFile: null`, etc. O Editor precisará tratar essa condição na Story 5.4+.
- Severity: LOW (intencional, documentado, Epic 8 traz restauração completa)
- Ação sugerida para @dev (Epic 8): adicionar validação de schema Zod/Valibot ao carregar projeto antes de aplicar ao store.

**[LOW] Validação de JSON limitada a `typeof data === 'object'`**
- `onFileSelected` linha 91: a validação `!data || typeof data !== 'object'` aceita arrays (`Array.isArray(data) === true` mas `typeof [] === 'object'`), objetos vazios e qualquer JSON com chave arbitrária. Um arquivo `.json` corrompido mas sintaticamente válido é aceito sem feedback diferenciado. Impacto: zero para o Epic 5 dado que a restauração completa não está implementada; relevante apenas quando o Epic 8 implementar a restauração.
- Severity: LOW

### Technical Debt Registered

- TD-5.2-001: `onFileSelected` — implementar validação de schema do projeto JSON antes de `session.$patch` (Epic 8 — story de restauração de estado).
- TD-5.2-002: Documentar formalmente o invariante de estado inconsistente `{ analysisCompleted: true, jobId: null }` para que Story 5.4 (TemplateEditor) trate o caso "projeto carregado via arquivo" vs "análise recém-concluída via pipeline".

### Decision Log

- A remoção de `useProject` e a implementação direta do file picker com `<input ref>` é correta para o escopo da story: `useProject` seria over-engineering para uma operação de leitura de arquivo simples neste estágio.
- O `AppHeader` gerenciado via `FullWidthLayout` (em vez de importado diretamente) é a decisão arquitetural correta: evita duplicação de header em todas as páginas e centraliza a lógica de header no layout.
- A assimetria de variantes (`primary` para "Novo Template" / `secondary` para "Abrir Projeto") é uma decisão de hierarquia visual intencional e bem fundamentada: criar nova migração é a ação principal, abrir projeto é secundária. Sem concern arquitetural.
- `startNew()` reseta os quatro stores explicitamente (`session.$reset()`, `mapping.$reset()`, `layout.$reset()`, `generation.$reset()`) em vez de usar um store agregador ou evento global — decisão pragmática correta para o estágio atual do projeto.

### Status

APPROVED. `HomePage.vue` é um componente de entrada limpo, coeso e com acoplamento baixo. A implementação segue corretamente os padrões do projeto (Composition API, Tailwind, Pinia, Vue Router). Os dois issues encontrados são de baixa severidade, intencionais e devidamente documentados para o Epic 8. A cobertura de testes (11 testes cobrindo `startNew`, `onFileSelected` e modal wiring) é adequada para o escopo. Story pronta para Done.
