## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment

- **Coupling: LOW.** `router/index.ts` depende apenas de `@/stores/session` via lazy import dentro do guard (`await import('@/stores/session')`), evitando dependência circular no bootstrap. `AnalyzingPage.vue` depende de `FullWidthLayout`, `ProgressBar`, `useSessionStore` e do módulo de constantes externo `analyzingPageConstants.ts` — todas dependências justificadas e de baixo risco. `TemplateEditor.vue` e `EditorLayout.vue` são shells sem lógica, acoplamento zero.
- **Cohesion: HIGH.** A separação de `PIPELINE_BLOCKS`, `TOTAL_STAGES` e `getStageIndex` em `analyzingPageConstants.ts` é uma decisão arquitetural correta: `<script setup>` não permite `export` nomeados, e externalizar as constantes facilita reutilização e teste isolado. `AnalyzingPage.vue` concentra exclusivamente a lógica de visualização SSE e gestão de estado de progresso — responsabilidade única bem definida. `EditorLayout.vue` é um layout puro com `<slot />`, coeso por definição.
- **Patterns:** Padrão lazy-loading de rotas via `() => import(...)` seguido corretamente para todas as quatro rotas. Navigation guards usam lazy import de store para evitar inicialização prematura do Pinia, padrão correto em Vue Router 4/5. `AnalyzingPage.vue` segue padrão Composition API com lifecycle hooks (`onMounted`/`onUnmounted`) para abertura e fechamento de SSE — sem memory leaks. `closeSSE()` limpa `reconnectTimer` e `eventSource` em todos os paths de saída (cancel, unmount, reconnect manual). `EditorLayout.vue` e `TemplateEditor.vue` respeitam convenção de shell com comentário de responsabilidade de story futura (5.4).
- **Scalability:** A detecção de conclusão do pipeline via sentinela `stage === TOTAL_STAGES && status === 'completed'` é uma decisão de design consciente — a constante `TOTAL_STAGES = 28` em `analyzingPageConstants.ts` cria um acoplamento estrutural com o backend (se o número de stages mudar, o frontend precisa ser atualizado). Para o volume previsto (documentos financeiros/fiscais, pipeline fixo de 28 stages), a abordagem é adequada e pragmática.

### Issues Found

**[LOW] Guard de `/editor` redireciona para `/` (Home) ao invés de `/upload`**
- `router/index.ts` linha 43: `return { name: 'home' }` quando `analysisCompleted !== true`. O AC8 da story não especifica o destino do redirect, mas o QA identificou (issue #2) que redirecionar para `/` pode confundir o usuário que chega diretamente via URL — o fluxo natural seria retornar a `/upload`. A inconsistência com o guard de `/analyzing` (que redireciona para `'upload'`) reforça que o destino mais intuitivo seria `/upload`. Impacto: UX baixo; sem impacto funcional.
- Severity: LOW
- Ação sugerida para @dev: avaliar se `return { name: 'upload' }` é mais correto para o guard do editor.

**[LOW] `AnalyzingPage.vue` excede escopo de shell placeholder do AC5**
- O componente entregue é uma implementação SSE completa com pipeline visualization, exponential backoff, cancel, reconnect e estimativa de tempo — enquanto AC5 pede apenas `<div class="analyzing-page"><h1>Analisando documentos...</h1></div>`. O código é correto e forward-compatible (será necessário para Story 5.4), mas cria uma divergência de escopo documentada. Nenhum impacto funcional — a funcionalidade entregue é exatamente o que o Epic precisa.
- Severity: LOW (escopo, não qualidade)

### Technical Debt Registered

- TD-5.1-001: Avaliar mudança de `return { name: 'home' }` para `return { name: 'upload' }` no guard de `/editor` — redirecionamento mais intuitivo para o usuário que tenta acessar o editor sem análise completa.
- TD-5.1-002: `TOTAL_STAGES = 28` em `analyzingPageConstants.ts` é acoplamento estrutural com o backend — considerar mecanismo de descoberta dinâmica do total de stages via API em iteração futura (low priority dado pipeline fixo).

### Decision Log

- A externalização das constantes do pipeline em `analyzingPageConstants.ts` é correta: permite que testes unitários importem `PIPELINE_BLOCKS` e `getStageIndex` diretamente sem montar o componente Vue.
- O lazy import de `useSessionStore` dentro de `router.beforeEach` (`await import('@/stores/session')`) evita o problema de circular initialization no Vite — decisão correta e documentada no comentário inline do guard.
- A abordagem de sentinela SSE (detectar conclusão via `stage === TOTAL_STAGES && status === 'completed'` em vez de evento `done` nomeado) é uma adaptação pragmática ao comportamento atual do backend — aceitável, mas deve ser revisada se o backend evoluir para emitir evento `done` explícito.
- `TemplateEditor.vue` e `EditorLayout.vue` como shells com scoped CSS mínimo (flexbox básico) é a decisão correta para Story 5.1: evita retrabalho e estabelece a estrutura de layout para Story 5.4.

### Status

APPROVED_WITH_NOTES. A reestruturação de rotas está arquiteturalmente sólida: lazy-loading correto, guards com lazy import de store, shells bem delimitados com comentários de responsabilidade. O único concern arquitetural real é o destino do redirect no guard do `/editor` (TD-5.1-001), de baixa severidade. A implementação adiantada de `AnalyzingPage.vue` é bem-vinda e forward-compatible. A story pode avançar para Done.
