# Story 40.8 — Backend Async & State Unification

## Status: Done

## Descricao

Resolver o split-brain de state management (CC-001) e migrar para clientes async. Job state vive em 3 locais (in-memory, Redis, Supabase) sem garantia transacional. Decisao arquitetural validada: Redis como source of truth primario com write-behind para Supabase, in-memory reduzido a cache de leitura. Adicionalmente, migrar Supabase SDK e Redis client para async.

## Dev Notes

- **Redis SSOT (DB-008):** RedisJobStore now uses `redis.asyncio.from_url()` for all operations. All methods are `async`. Read cache (`_cache` dict) provides fast access during pipeline execution; Redis remains authoritative.
- **DB-017 Guard:** Both `RedisJobStore.save_job()` and `SupabaseStorageGateway.save_result()` check current status before writing. Terminal statuses (`cancelled`, `failed`) cannot be overwritten to `completed`.
- **Write-behind (FEATURE_DUAL_WRITE):** When `FEATURE_DUAL_WRITE=true`, `RedisJobStore.save_job()` fires a background task to persist completed results to Supabase. Fire-and-forget: failures are logged, not propagated.
- **DB-007 (asyncio.to_thread):** All SupabaseStorageGateway sync SDK calls wrapped with `asyncio.to_thread()` to avoid blocking the event loop.
- **InMemoryJobStore:** Also converted to async API for interface consistency. Used in dev/test mode.
- **Backward compatibility:** `_pipeline_jobs` dict in analyze.py still serves as the process-local working copy during pipeline execution (SSE events, cancel flags). Redis persists the final state.
