# Story 5.3: UploadPage v3 — Multi-PDF, XSD Obrigatório e Hints Contextuais

## Status
Ready for Review

## Story
**As a** operador da ferramenta,
**I want** fazer upload de múltiplos PDFs (1 obrigatório, 3-5 recomendado), um XSD (obrigatório) e opcionalmente um arquivo de dados (XML/JSON), com hints contextuais me guiando,
**so that** eu possa fornecer todos os inputs necessários para o pipeline de análise.

## Acceptance Criteria
1. Três dropzones: PDFs (múltiplos, 1 obrigatório), XSD (single, obrigatório), Data (single, opcional XML/JSON)
2. Dropzone PDF mostra lista de arquivos com botão 🗑️ remover e contagem "📊 N PDFs (recomendado: 3-5)"
3. Campo de input para nome do template no topo
4. Hint quando sem arquivos: "Envie ao menos 1 PDF + XSD para continuar"
5. Hint quando 1 PDF apenas: "💡 Adicionar mais PDFs melhora a detecção de variações"
6. Hint quando PDF+XSD sem dados: "💡 Adicionar dados reais melhora a detecção de tipos e formatos"
7. Hint quando PDF+dados sem XSD: "💡 Adicionar o XSD permite validar campos obrigatórios"
8. Botão "Iniciar Análise" desabilitado até ao menos 1 PDF + XSD carregados
9. "Iniciar Análise" chama backend API POST /api/upload e navega para /analyzing
10. "← Voltar" retorna à Home
11. Upload rejeita PDFs maiores que 50MB por arquivo e XSD/Data maiores que 10MB, com mensagem de erro descritiva ("Arquivo excede o tamanho máximo de {limite}")
12. Progresso de upload exibido: barra de progresso por arquivo durante o envio ao backend (XMLHttpRequest.upload.onprogress ou fetch com ReadableStream)
13. `npm run build` passa

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment

- **Coupling:** LOW. `UploadPage.vue` é um componente de página auto-contido que depende apenas de três contratos bem definidos: `useSessionStore` (Pinia), `useRouter` (Vue Router) e `ProgressBar` (atom). O único contrato externo é o endpoint `POST /api/upload` — endereçado via `VITE_API_URL` env var, não hardcoded. A decisão de implementar o dropzone multi-PDF inline (em vez de reutilizar `FileDropzone`, que aceita apenas `File|null`) é correta e está documentada nas Completion Notes: não força o componente atom a suportar um modo que não é seu propósito.
- **Cohesion:** HIGH. O componente tem responsabilidade única e bem delimitada: capturar inputs de arquivo + emitir um upload para o backend. A lógica de hints está encapsulada em `currentHint` (computed), a validação de tamanho em `validatePdfSize` / `validateOtherSize`, e o upload em `startAnalysis`. Nenhuma lógica de negócio do pipeline vaza para este componente.
- **Patterns:** Padrões Vue 3 Composition API seguidos corretamente: `ref` para estado mutável, `computed` para derivações (sem efeitos colaterais), event handlers nomeados por convenção (`on{Event}{Target}`). BEM CSS scoped. O uso de `XMLHttpRequest` em vez de `fetch` é justificado pelo AC-12 (`upload.onprogress`) — decisão correta e documentada. `VITE_API_URL` com fallback para string vazia segue o padrão do projeto.
- **Scalability:** O componente escala adequadamente para o caso de uso: upload de até ~5 PDFs × 50MB cada. Não há state global desnecessário — os arquivos ficam em `ref` local até o clique em "Iniciar Análise". A deduplicação por nome (`existingNames` Set) é O(n) para n PDFs, aceitável para n ≤ 10.

### Issues Found

**[LOW] XHR sem `abort()` na desmontagem do componente**
- Confirmado pelo QA (Issue #3). Se o usuário clicar "← Voltar" durante o upload, o XHR continua ativo e o callback `xhr.onload` ainda tentará executar `session.jobId = ...` e `router.push('/analyzing')` após o componente já ter sido desmontado. Não causa crash (Vue Router é tolerante a pushes pós-desmontagem), mas é tecnicamente um memory leak e um comportamento inesperado.
- Severity: LOW
- Fix sugerido: adicionar `const xhrRef = { current: null }` e `onUnmounted(() => xhrRef.current?.abort())`.

**[LOW] XHR sem `timeout` para uploads lentos**
- Confirmado pelo QA (Issue #4). Upload de 5× 50MB em conexão lenta pode travar indefinidamente sem feedback diferenciado. O `isUploading` bloqueia o botão mas não há escape do estado de loading.
- Severity: LOW
- Fix sugerido: `xhr.timeout = 120_000` + `xhr.ontimeout = () => { uploadError.value = 'Timeout ao enviar. Tente novamente.'; isUploading.value = false }`.

**[OBSERVATION] `currentHint` não cobre o estado `hasPdf && !hasXsd && !hasData` (PDF sem XSD, sem dados)**
- Ao adicionar somente PDFs (sem XSD e sem dados), `currentHint` retorna `null` — sem hint exibida. O AC-4 cobre apenas "sem arquivos", não este estado intermediário. Não é um bug (está dentro do spec), mas é uma lacuna de UX notável: o usuário adicionou PDFs mas não recebe orientação sobre o próximo passo (adicionar XSD). O QA não apontou isso como issue — o spec está correto — mas vale registrar como melhoria futura de UX.
- Severity: LOW (gap de UX, não de design)

### Technical Debt Registered
- TD-5.3-001: Adicionar `xhr.abort()` em `onUnmounted` para evitar callbacks após desmontagem do componente.
- TD-5.3-002: Adicionar `xhr.timeout` configurável (recomendado: 120s) com handler `ontimeout` para uploads lentos.
- TD-5.3-003: Avaliar hint adicional para estado `hasPdf && !hasXsd && !hasData` — guiar o usuário a adicionar o XSD como próximo passo obrigatório.

### Decision Log
- A implementação de dropzone inline customizado para multi-PDF (em vez de adaptar `FileDropzone`) é a decisão correta de design: não força o atom a suportar `File[]`, que não é seu contrato original. A decisão está documentada nas Completion Notes e é consistente com atomic design — átomos têm contratos fixos e componentes de página podem implementar comportamentos compostos.
- O uso de `XMLHttpRequest` (não `fetch`) é obrigatório para `upload.onprogress` — sem API equivalente no `fetch` + `ReadableStream` no contexto de upload. Decisão correta e alinhada com AC-12.
- `sizeErrors.value = errors` (reset a cada batch) em vez de concatenação é a correção correta do Issue #2 do QA — semanticamente mais correto: erros de tamanho são sobre o batch atual, não histórico acumulado.
