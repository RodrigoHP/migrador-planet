# Story 5.8: Bloco 3: Layout Intelligence — Alinhamento, Multi-Example, Estabilidade e Variantes

## Status
Ready for Review

## Story
**As a** bloco do pipeline,
**I want** alinhar layouts entre PDFs, analisar múltiplos exemplos para distinguir labels de valores dinâmicos, classificar estabilidade de elementos e detectar variantes,
**so that** o motor de matching tenha inteligência estrutural de alta qualidade.

## Acceptance Criteria
1. Stage 8 — Layout Alignment: normalizar diferenças de coordenadas entre múltiplos PDFs; com 1 PDF: auto-align (trivial)
2. Stage 9 — Multi-Example Analysis: comparar documentos para detectar labels (texto que não muda) vs valores dinâmicos (texto que muda); com 1 PDF: Vision AI assume inferência
3. Stage 10 — Stability Classification: classificar cada elemento como stable (mesma posição/conteúdo em todos docs), variable (mesma posição, conteúdo diferente), ou absent (ausente em alguns docs)
4. Stage 11 — Variant Detection: detectar campos opcionais (presentes em alguns docs), seções condicionais (grupo de campos com mesmo padrão de presença), tabelas dinâmicas (contagem variável de linhas)
5. Stage 12 — Normalization: normalizar padrões detectados em metadados estruturados para matching
6. Todos os 5 estágios registrados no orchestrator, emitindo SSE progress
7. Output enriquece LayoutTypes com: labels[], dynamic_fields[], stability_map, variants[], conditional_sections[]
8. Com 1 PDF: estágios executam com confiança reduzida, flag "single document — reduced accuracy"
9. Testes cobrem: detecção label vs valor, classificação de estabilidade, detecção de variantes, fallback de 1 PDF

## Dev Notes

### Multi-Example Analysis — DIFERENCIAL CHAVE
- Esta é a funcionalidade que diferencia o sistema de ferramentas simples
- Com 3-5 PDFs, a precisão aumenta significativamente:
  - "Cliente: João" vs "Cliente: Maria" → "Cliente:" = label, valor = dinâmico
  - Com 1 PDF, não há como confirmar — usa heurísticas

### Heurísticas para 1 PDF
- Texto terminando em `:` → provavelmente label
- Texto em negrito/maior → provavelmente título ou label
- Texto numérico ou com formato (CPF, data, moeda) → provavelmente valor
- Texto curto adjacente a texto formatado → provavelmente label

### Seções Condicionais
- Campos adjacentes com mesmo padrão de presença formam um grupo
- Exemplo: "Avalista", "CPF Avalista", "Endereço Avalista" — todos presentes ou todos ausentes
- Gera `<!-- ko if: avalista -->` no template Knockout

### Classificação de Estabilidade → Confidence Scoring
- Dados de estabilidade alimentam o cálculo de confiança na Story 5.11
- Elementos `stable` → alta confiança no mapeamento
- Elementos `absent` → necessitam atenção do operador

### Variant Detection → MultiDoc Analyzer UI
- Variantes detectadas alimentam a UI do MultiDoc Analyzer (Epic 9)
- Operador pode revisar e confirmar variantes no editor

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: MEDIUM — Os 5 stages (12-16) estão corretamente desacoplados entre si via context dict. O acoplamento mais relevante é o Stage 16 (Normalization) que lê 5 chaves privadas distintas (`_element_labels`, `_stability_map`, `_variants`, `_conditional_sections`, `intelligence_metadata`) produzidas pelos stages 12-15. Essa dependência implícita aumenta a fragilidade de manutenção (mesmo problema identificado em 5.7).
- Cohesion: HIGH — Cada stage tem responsabilidade singular bem definida. Stage 13 (análise comparativa multi-doc) e Stage 14 (classificação de estabilidade) são especialmente bem separados, dado que poderiam ter sido colapsados em um único stage. A separação facilita testes independentes e evolução futura.
- Patterns: StageRegistry pattern correto. O padrão de `intelligence_metadata` como dict no context para propagar flags de single_document é adequado. A decisão de Stage 16 re-serializar `layout_types` no context é correta — garante que o estado persistido no context sempre reflita o estado processado mais recente.
- Scalability: O algoritmo de comparação bbox em Stage 13 é O(n²) por cluster (n = blocos na mesma posição entre documentos). Para documentos com poucos PDFs e densidades típicas de layout, isso é aceitável. O risco emerge se o sistema for usado com dezenas de PDFs com centenas de blocos por página — monitorar.

### Issues Found
- [medium] **`lt._intelligence` via atribuição direta (linha 132 de `intelligence_normalization.py`)** — O QA identificou este padrão. Diferente de `_centroid` e `_cluster_skeletons` (resolvidos em 5.7), `_intelligence` ainda é atribuído via `lt._intelligence = intel` diretamente em vez de usar o campo declarado no dataclass. O campo `_intelligence: Optional[Dict[str, Any]]` já está declarado em `layout_type.py` (linha 186), portanto a atribuição é tecnicamente válida. O issue real é cosmético: o código não usa `dataclasses.fields()` para atribuição, mas o resultado é idêntico. Nenhuma ação obrigatória, mas verificar se `lt._intelligence = intel` atribui ao campo declarado ou cria um novo atributo de instância. Se Python 3.12 com `@dataclass` sem `__slots__`, a atribuição direta funciona corretamente.
- [low] **Heurística de 30 chars como threshold para classificação de label em single-PDF** — O threshold fixo de 30 caracteres em `_analyse_cluster_single_pdf` é uma magic constant sem justificativa documentada. A heurística de "texto curto com `:` = label" é razoável, mas o valor 30 é arbitrário. Adicionar um comentário explicando a origem do threshold (comprimento típico de um label de formulário em documentos brasileiros).
- [low] **Adjacência de 30pt para `conditional_section` em `variant_detection.py`** — Threshold hardcoded. Documentar a justificativa (30pt ≈ 2 linhas de texto em fonte 12pt) para facilitar ajuste futuro.

### Technical Debt Registered
- O padrão de campos internos `_*` no dataclass `LayoutType` continua crescendo (agora `_centroid`, `_cluster_skeletons`, `_intelligence`). A decisão de acrescentar campos de orquestração ao modelo de domínio foi correta como solução imediata, mas cria technical debt de longo prazo. **Threshold de ação:** se uma 4ª story adicionar mais campos internos ao `LayoutType`, criar um `LayoutTypeContext` wrapper separado. Registrado para monitoramento.
- O bbox O(n²) em Stage 13 deve ser documentado explicitamente com um comentário `# O(n²) — acceptable for < N PDFs × M blocks` com os valores concretos de N e M que o sistema suporta, para guiar futuras decisões de otimização.

### Decision Log
- Separação Stage 13 (Multi-Example) + Stage 14 (Stability): decisão arquitetural correta. Multi-example analisa *comparação entre documentos*; stability analisa *padrão de presença ao longo do tempo*. São dimensões ortogonais que merecem stages separados.
- Flag `single_document/reduced_accuracy` propagada via `intelligence_metadata` no context: padrão correto. Permite que downstream stages (especialmente o Matching Engine em 5.11) ajustem seu comportamento sem acoplar ao número de PDFs processados.
- `confidence: "inferred"` para labels detectados em single-PDF: decisão semântica importante. Diferencia confirmação multi-documento (alta confiança) de inferência heurística (baixa confiança), permitindo que a UI apresente indicadores visuais adequados ao operador.
- Stage 16 como "normalização terminal" do bloco: decisão arquitetural sólida. Centraliza a serialização do estado de intelligence em um único ponto, evitando que estados parciais sejam persistidos no context por stages individuais.
