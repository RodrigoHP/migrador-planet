# Story 10.14: Bug — Tela de carregamento não mostra progresso em tempo real

## Status
Ready

## Story
**As a** operador,
**I want** que a tela de carregamento mostre cada estágio do pipeline sendo executado em tempo real (running → completed),
**so that** o usuário veja o progresso estágio a estágio, e não um flash final com todos os estágios verdes de uma vez.

## Problema Diagnosticado

### Causa Raiz
Em `AnalyzingPage.vue` `onMounted()`, o fluxo atual é:
```
1. await startPipeline()  → POST /api/analyze → pipeline START (cria task assíncrona)
2. connectSSE()           → EventSource conecta DEPOIS do pipeline já estar rodando
```

O `asyncio.create_task(_run_pipeline(job_id))` inicia o pipeline **imediatamente** após o POST retornar. Porém o `EventSource` leva uma viagem de rede adicional para conectar. Nesse intervalo, os primeiros estágios já completaram e colocaram eventos na `asyncio.Queue`.

Quando o generator `_event_generator` finalmente começa a consumir, `queue.get()` retorna imediatamente para todos os eventos buffered (queue não-vazia). O navegador recebe todos em sequência rápida → Vue batcha as atualizações de reatividade → todos os estágios ficam verdes de uma vez.

### Solução: Event Log com Replay
Substituir `asyncio.Queue` por uma lista `event_log` como fonte de verdade:
- `_run_pipeline` faz append na lista + sinaliza um `asyncio.Event`
- `_event_generator` lê da lista começando do índice 0 (replay de eventos passados) e aguarda novos com `asyncio.Event.wait()`
- Clientes que conectam tarde recebem todos os eventos históricos antes dos novos
- Sem race condition: list.append() é thread-safe no CPython GIL

## Acceptance Criteria

1. Após o fix, ao carregar a AnalyzingPage, os estágios aparecem progressivamente (running azul → completed verde), não todos de uma vez
2. `backend/routers/analyze.py`: `_pipeline_jobs[job_id]` contém `event_log: list` e `new_event: asyncio.Event` em vez de `event_queue: asyncio.Queue` (ou em adição, como compatibilidade)
3. `_event_generator` inicia a partir do índice 0 do `event_log`, replaya eventos passados, depois aguarda `new_event` para novos eventos
4. `_run_pipeline` usa `_emit_event(job_state, event)` helper que faz: `event_log.append(event)` + `new_event.set()`
5. Clientes que conectam **após** o pipeline completar ainda recebem todos os eventos históricos + event `pipeline_completed`
6. Race condition coberta: se evento é adicionado após o generator verificar `idx < len(log)` mas antes de `new_event.wait()`, o generator o processa sem perder (re-check após `clear()`)
7. `pytest backend/tests/` passa sem erros

### Helper Sugerido
```python
def _emit_event(job_state: Dict[str, Any], event: Optional[Dict[str, Any]]) -> None:
    """Append event to log and signal waiting generators."""
    job_state["event_log"].append(event)
    if event is None:
        job_state["pipeline_done"] = True
    job_state["new_event"].set()
```

### Generator Novo (Pattern)
```python
async def _event_generator(job_id: str) -> AsyncIterator[str]:
    job_state = _pipeline_jobs.get(job_id)
    if job_state is None:
        yield json.dumps({"error": "job not found"})
        return

    idx = 0
    while True:
        log = job_state["event_log"]
        if idx < len(log):
            event = log[idx]
            idx += 1
            if event is None:  # sentinel
                break
            yield json.dumps(event)
        else:
            new_event = job_state["new_event"]
            new_event.clear()
            # Re-check after clear to avoid race
            if idx < len(job_state["event_log"]):
                continue
            if job_state.get("pipeline_done"):
                break
            await new_event.wait()
```
