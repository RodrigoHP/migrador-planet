# Story 44.1 — SPIKE: Re-avaliação do Stage 1 Layout Clustering

## Status: Ready

## Tipo

**Spike de pesquisa** — produz relatório empírico e recomendação, não código de produção. Resultado alimenta decisão futura sobre manter/trocar/complementar stack atual de clustering.

## Contexto

Stage 1 (`backend/services/stages/stage1_layout_clustering.py` + submódulos em `stage1_clustering/`) é a **fundação** do pipeline. Se um cluster está errado, Stage 2 processa só o representative, Stage 3 compara instâncias com estruturas diferentes, Stage 5 gera template vazio/inconsistente — tudo sem aparecer nas métricas finais.

### Audit empírico (2026-04-12) sobre boleto

Stack atual entregou clusters aparentemente corretos no boleto (`Corporate.Boleto.Convenio.pdf`), mas:
- **1 PDF é baseline frágil** — não testamos casos de borda
- Não temos **ground truth** cross-template
- Não sabemos onde o baseline **falha silenciosamente**
- Componentes como pHash e similarity manual são tech de 2010s — em 2026 temos alternativas layout-aware

## Objetivo

Executar **ablation study** contra ground truth manual cobrindo 3 dimensões independentes:

1. **Feature extraction** (como representar a página)
2. **Similarity metric** (como medir distância entre páginas)
3. **Visual cross-check** (como validar clusters usando imagem renderizada)

Produzir relatório quantitativo + recomendação: manter, trocar ou complementar cada componente.

## Decision Framework

Recomendação por componente baseia-se em:

| Critério | Threshold para "trocar baseline" |
|---|---|
| ARI melhoria | ≥ +0.10 absoluto |
| Homogeneity melhoria | ≥ +0.05 |
| Casos de borda que baseline perde | ≥ 2 dos 3 documentados |
| Custo operacional (tempo/memória) | < 2× baseline |
| Manutenibilidade | subjetivo — modelo HF mantido vs código manual |

**Resultados possíveis:**
1. **Baseline é ótimo** — nenhuma alternativa bate thresholds → manter, documentar
2. **Alternativa domina** — troca recomendada → criar story de implementação
3. **Alternativa complementa** — usar como 2ª opinião (ex: CLIP como cross-check adicional) → criar story de integração híbrida
4. **Resultado inconclusivo** — ampliar ground truth, repetir spike

## Dev Notes

### Estrutura do runner

```python
@dataclass
class ClusteringRun:
    feature: str       # F0..F4
    similarity: str    # cosine | geometry
    clustering: str    # graph | hdbscan | dbscan | spectral | agglomerative
    visual_check: str  # V0..V4
    seed: int

# Para cada run:
# 1. Compute features for all pages (cached)
# 2. Compute similarity matrix
# 3. Run clustering algorithm
# 4. Run visual check
# 5. Compare predicted clusters vs GT labels
# 6. Record metrics
```

### Feature extraction — notas técnicas

- **LayoutLMv3:** input = bounding boxes + tokens + image patches. Output = embedding por página. Pre-trained em RVL-CDIP.
- **CLIP:** render página → PIL Image → `model.encode_image()`. Embedding 512-dim.
- **DINOv2:** mesma pipeline do CLIP. Self-supervised, sem viés de rotulagem.
- **Nougat/Donut:** output token-level; agregar via mean pooling. Optional.

### Clustering algorithms — notas

- **HDBSCAN** (`hdbscan` package): aceita distance matrix via `metric='precomputed'`. Não requer `eps`. Emite `-1` para outliers.
- **DBSCAN** (`sklearn`): requer `eps` — tunar via grid search.
- **Spectral** (`sklearn`): bom para manifolds. Requer número de clusters `n_clusters`.
- **Agglomerative** (`sklearn`): hierarchical, `linkage='ward'` default.
