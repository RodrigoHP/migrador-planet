## Descrição

No pipeline atual, o Stage 3.1 (multi_example_analysis.py) usa a heurística estatística "único texto por posição = label" para boletos processados individualmente (single-PDF). Isso causa misclassificação de blocos de VALOR como labels, que depois são emparelhados incorretamente em Stage 3.3, gerando pares inválidos para o Gemini.

**Impacto medido (job f6fd4a39, boleto Corporate.Boleto.Convenio.pdf):**

- Confidence score: **45/100** (human_review_required)

## Dev Notes

### Contexto do Bug

A função `_smart_classify` em `multi_example_analysis.py` calcula score base 0.5 e aplica weights dos patterns:
- Pattern match → `+weight` (positivo = empurra para dynamic)
- `ends_colon` → `-0.4` (empurra para label)
- `short_no_digits` → `-0.2` (texto <20 chars sem dígitos, empurra para label)

Para "RUA PARAIBUNA 456":
- Nenhum pattern regex match (não tem data, moeda, CNPJ, CEP, barcode, decimal)
- `short_no_digits` NÃO dispara (tem dígitos em "456")
- Score = 0.5 → incerto (nem `>= 0.7` nem `<= 0.3`) → `is_likely_dynamic = None`
- Com `None` retornado, Stage 3.1 mantém "label"
- spaCy NER não retorna LOC para "PARAIBUNA 456" de forma consistente

Para "237" (código numérico):
- Nenhum pattern match (não é decimal com ponto, não é CEP 8 dígitos, não é CNPJ)
- `short_no_digits` NÃO dispara (tem dígitos)
- Score = 0.5 → incerto → `is_likely_dynamic = None` → mantém "label"

### Fix Proposto

**`constants.py`** — adicionar ao `_DYNAMIC_PATTERNS`:
```python
(r"^(?:RUA|AV\.?|AVENIDA|TRAVESSA|AL\.?|ALAMEDA|ROD\.?|RODOVIA|PRACA|PC|ESTRADA|EST)\s", "street_address", 0.85),
(r"^\d{1,8}$", "pure_number", 0.65),
```

Com estes dois patterns:
- "RUA PARAIBUNA 456": match `street_address` → `+0.85` → score 1.35 → clamp 1.0 → `is_likely_dynamic=True`
- "237": match `pure_number` → `+0.65` → score 1.15 → clamp 1.0 → `is_likely_dynamic=True`
- "0": match `pure_number` → `+0.65` → score 1.15 → clamp 1.0 → `is_likely_dynamic=True`

### Atenção: Regressões Potenciais

Pattern `^\d{1,8}$` pode interferir com labels numéricos legítimos (ex: numeração de seção "1", "2"). Avaliar durante implementação se weight 0.65 é suficientemente conservador ou se requer exclusão de casos como single-digit headers. Se necessário, ajustar para `^\d{2,8}$` (2+ dígitos) para excluir "1", "2" que podem ser labels de seção.

### Threshold `_smart_classify`

```python
# multi_example_analysis.py linhas 175-179
if score >= 0.7:
    return True, score, signals   # likely_dynamic
elif score <= 0.3:
    return False, score, signals  # label
else:
    return None, score, signals   # uncertain → chamador mantém label
```

Com o pattern `street_address` (weight=0.85), qualquer endereço com prefixo legradouro vai ultrapassar 0.7. Com `pure_number` (weight=0.65), todos os números puros vão ultrapassar 0.7.
