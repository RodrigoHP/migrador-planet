# Story 48.4 — SPIKE: Validar Stage 1 Clustering + Stage 3.1 Dynamic/Static com Input Multi-Sample

## Status: Ready

## Descrição

Validar end-to-end os dois primeiros stages do pipeline com input real multi-sample (3+ PDFs do mesmo template via Railway API). Este é o teste central do Pilar B: verificar que Stage 1 agrupa corretamente e Stage 3.1 distingue dinâmico de estático.

**O que está sendo testado (nunca validado antes):**
- **Stage 1:** 3 instâncias do mesmo template → 1 cluster por layout distinto (não 3 clusters por instância)
- **Stage 3.1 (Multi-Example Analysis):** campos `data_vencimento`, `valor_boleto`, etc. marcados `likely_dynamic`; campos `banco_nome`, labels fixos marcados `label`/`static`

## Acceptance Criteria

- [x] **AC1:** Pipeline processa 3+ PDFs do mesmo template sem crash — status `completed` na Railway API
- [x] **AC2:** Stage 1 — número de layouts detectados = número de layouts distintos do template (ex.: boleto Corporate de 1 página → 1 layout, não 3)
- [x] **AC3:** Stage 3.1 — campos que mudam entre instâncias (do ground truth de 48.3) estão marcados `likely_dynamic` no output do pipeline — accuracy ≥ 80%
- [x] **AC4:** Stage 3.1 — campos fixos (labels, texto estático) não estão marcados `likely_dynamic` — falso-positivo rate ≤ 20%
- [x] **AC5:** Relatório comparando Stage 3.1 output vs ground truth de 48.3 salvo em `docs/reports/epic-48/stage31-validation-{tipo}.json`
- [x] **AC6:** Pelo menos 2 tipos de documento validados (ex.: boleto + relatório)

# Script de validação multi-sample

job_ids = submit_multi_pdf(pdfs=["boleto_jan.pdf", "boleto_fev.pdf", "boleto_mar.pdf"])

ground_truth_dynamic = load_ground_truth("docs/reports/epic-48/ground-truth-multisample-boleto.json")
