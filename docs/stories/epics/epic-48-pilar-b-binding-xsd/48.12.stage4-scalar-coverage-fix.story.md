# Story 48.12 — Stage 4: Corrigir Scalar Coverage — Prompt Regression + E2E Multi-Cliente

## Status: Ready

## Descrição

A validação E2E run em 2026-04-25 revelou `scalar_coverage = 31.2%` (10/32 campos), abaixo do gate ≥ 80% exigido para desbloquear o Epic 49.

Dois root causes identificados por investigação:

**Root Cause 1 — Regressão no prompt Gemini (`_BATCH_MATCH_PROMPT`):**
O Fix B do commit `4e6694e` adicionou instruções ultra-conservadoras ao prompt Gemini Flash que fizeram o LLM retornar `score=0.0` para campos dinâmicos válidos como `TELEFONE`, `E-MAIL`, `INSCRIÇÃO`, `NomeCliente`. O threshold `MINIMUM_MATCH_THRESHOLD = 0.4` não tem efeito real (scores são bimodais: 0.0 ou ≥ 0.5), portanto a causa é o bloqueio de scores no próprio LLM.

**Root Cause 2 — Test set com mesmo cliente (confound Stage 3.1):**
Os 3 PDFs de validação (`PosicaoConsolidada.pdf`, `PosicaoConsolidada2.pdf`, `PosicaoConsolidada3.pdf`) são todos do mesmo cliente (TELMA). O Stage 3.1 usa comparação multi-sample para distinguir dinâmico de estático — quando todos os samples têm o mesmo nome/telefone/e-mail, esses campos são classificados como **estáticos** e não priorizados para binding XSD no Stage 4.

A solução correta é: (a) restaurar um prompt Gemini balanceado, e (b) usar 4 PDFs de clientes distintos no E2E, de modo que Stage 3.1 classifique nome/telefone/e-mail como **dinâmicos**.

## Notas de Implementação

### AC1 — Refinamento do `_BATCH_MATCH_PROMPT`

O prompt atual (post Fix B) adicionou estas instruções problemáticas que causam abstensão excessiva:

```python
# REMOVER ou suavizar estas linhas do prompt:
# "Only map a pair when you are confident there is a semantically meaningful match."
# "If no XSD field is a good match, set score to 0.0 and path to null"
# "Do NOT invent or force a mapping when none exists — unmapped is better than wrong."
# "Static header/footer text, instructions, or body paragraphs should receive score 0.0."
```

**Abordagem recomendada:** Manter a rejeição de texto estático puro (parágrafos de carta, instruções), mas distingui-los explicitamente de campos de dados com label. Exemplo de redação balanceada:

```
Regras de mapeamento:
- Campos com label explícito (ex: "TELEFONE:", "E-MAIL:", "Certificado/") → mapear mesmo com confiança parcial
- Valores de data, número, CPF, valor monetário → mapear quando há candidato XSD compatível
- Texto corrido de carta/instruções/rodapé → NÃO mapear (score 0.0)
- Se o valor do campo é claramente estático (mesmo em todos os documentos) → score 0.0
```

### Por que o Root Cause 2 é resolvido indiretamente

Com 4 PDFs de clientes distintos:
- `PosicaoConsolidada.pdf` → cliente TELMA
- `PosicaoConsolidada2.pdf` → cliente diferente
- `PosicaoConsolidada3.pdf` → cliente diferente
- `PosicaoConsolidada4.pdf` → cliente diferente

O Stage 3.1 (`multi_example_analysis.py`) compara os valores dos campos entre os PDFs. Campos como `NomeCliente`, `ClienteTelefone`, `ClienteEmail`, `EnderecoRua` vão variar → classificados como **dinâmicos** → priorizados para binding XSD no Stage 4.

Este é o comportamento correto do pipeline para um test set adequado.
