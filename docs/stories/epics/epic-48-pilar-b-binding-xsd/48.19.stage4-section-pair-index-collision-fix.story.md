# Story 48.19 — Fix: Stage 4 pair_index index-collision entre seções (RC-G)

## Status: Done

## Descrição

RCA confirmado via teste unitário (2026-04-25): `_step_4_5_field_matching` perde os candidatos LLM de todas as seções exceto a última, porque:

1. Cada seção gera uma chamada LLM independente com `_llm_batch_match_scoped`.
2. O prompt instrui o LLM com `"pair_index (int): index of the pair (0-based)"` — ambíguo.
3. O Gemini interpreta `0-based` como posição dentro do grupo local (0, 1, 2) em vez de usar o campo `index` do JSON (que é `original_index`).
4. `all_results.update(batch)` sobrescreve as chaves 0, 1, 2 da seção anterior quando a nova seção também retorna pair_index 0, 1, 2.
5. Em Pass 1, `all_results.get(i, [])` para `i >= len(última_seção)` retorna `[]`.

**Evidência direta (E2E job run 2026-04-25 22:29):**
- `scalar_coverage = 0.32` (8/25 pares mapeados)
- INSCRIÇÃO, TELEFONE, FORMA DE PAGAMENTO, E-MAIL → todos `candidates=[]`
- Layout B tem 5+ seções nomeadas → 5 chamadas LLM → 4 delas sobrescritas

**Teste confirmatório** (`backend/tests/unit/services/stages/stage4_mapping/test_section_pair_index.py`):
- 2 seções × 3 pares; mock LLM retorna pair_index posicional
- `test_second_section_pairs_get_candidates` → **FAIL**: par 3 chega com `candidates=[]`
- `test_first_section_pairs_get_candidates` → **FAIL**: nem todos os 6 pares têm candidatos

- [ ] **AC2:** Testes confirmatórios `test_section_pair_index.py` — ambos passam após o fix.

## Implementação Técnica

### Modificação em `_step_4_5_field_matching` (section_matching.py, dentro do `for section_name, group in section_groups.items()`)

**Antes (linhas ~466-481):**
```python
pairs_json = [
    {
        "index": p["original_index"],
        "label": p.get("label_text", ""),
        "value": p.get("value_text", ""),
        "detected_format": p.get("detected_format"),
    }
    for p in group
]

if openrouter_client:
    batch = await _llm_batch_match_scoped(pairs_json, scoped_paths, section_context, openrouter_client)
else:
    batch = _fuzzy_batch_match(pairs_json, scoped_paths)

all_results.update(batch)
```

**Depois:**
```python
_local_idx_map: dict[int, int] = {}
pairs_json = []
for _pos, _p in enumerate(group):
    pairs_json.append(
        {
            "index": _pos,
            "label": _p.get("label_text", ""),
            "value": _p.get("value_text", ""),
            "detected_format": _p.get("detected_format"),
        }
    )
    _local_idx_map[_pos] = _p["original_index"]

if openrouter_client:
    batch = await _llm_batch_match_scoped(pairs_json, scoped_paths, section_context, openrouter_client)
else:
    batch = _fuzzy_batch_match(pairs_json, scoped_paths)

# Remapear pair_index local (0,1,2...) → original_index antes do update
batch = {_local_idx_map.get(k, k): v for k, v in batch.items()}
all_results.update(batch)
```

### Por que funciona

- LLM sempre recebe `index: 0, 1, 2...` dentro do grupo local → sem ambiguidade
- `_local_idx_map` converte de volta para `original_index` antes de `all_results.update()`
- Seções diferentes têm `original_index` únicos (pares 0-2, 3-5, etc.) → sem colisão

## Evidência do Bug

```
Layout B — 5 seções nomeadas:
  "Seção Posição Consolidada..."   → 2 pares  original_index [0,1]
  "Seção Dados do cliente"         → 6 pares  original_index [2..7]
  "Seção ENDEREÇO DE RELACIONAM."  → 5 pares  original_index [8..12]
  "Seção Contribuição"             → 7 pares  original_index [13..19]
  "Seção Certificado/" (×2)        → 6+ pares original_index [20..25]

Com bug: all_results após 5 updates = apenas {0..5} da última seção
→ all_results.get(6, []) ... get(25, []) todos retornam []
→ xsd_field_path = "" para todos
```

## Riscos

- **R1 (baixo):** `_fuzzy_batch_match` também recebe `pairs_json` com `index: _pos` — mas o fuzzy fallback usa `idx = pair.get("index", i)` (linha ~200), então o remap pós-batch continua necessário. Já está coberto pelo `batch = {_local_idx_map.get(k, k): v ...}`.
- **R2 (baixo):** Se `_llm_batch_match_scoped` retornar `pair_index` fora do range [0, len(group)-1], o `_local_idx_map.get(k, k)` preserva o valor original — sem crash, apenas sem match.
