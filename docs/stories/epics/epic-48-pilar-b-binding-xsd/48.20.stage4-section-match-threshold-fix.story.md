# Story 48.20 — Fix: Stage 4 SECTION_MATCH_MIN_SCORE spurious match (RC-H)

## Status: Done

## Descrição

Descoberto durante validação E2E pós RC-G (2026-04-26): `scalar_coverage = 0.64` mesmo com pair_index collision corrigido. Análise dos campos unmapped revelou `dbg_scoped_count=4` para TELEFONE, FORMA DE PAGAMENTO, E-MAIL e ENDEREÇO — todas em seções que receberam apenas 4 XSD paths ao invés de flat_paths(68).

**Root cause (RC-H):** `_section_xsd_similarity` com `SECTION_MATCH_MIN_SCORE=0.3` permitia matches espúrios por `count_score`. Quando seção e nó XSD têm o mesmo número de filhos (count_ratio=1.0), o peso de 0.3 elevava o score total acima do threshold mesmo com baixa similaridade de nome.

Exemplo concreto: "Seção Dados do cliente" (4 campos) → `DadosParcelasAVencer.DadosParcelasAVencer` (4 filhos) com score=0.5564. Os 4 paths expandidos (NumeroCertificado, DataVencimento, MesAVencer, ValorTotal) não contêm FormaPagamento → Gemini retorna `candidates=[]`.

**Fix:** elevar `SECTION_MATCH_MIN_SCORE` de `0.3` para `0.65`, exigindo similaridade de nome genuína antes que count contribua. Com este threshold, todas as seções de PosicaoConsolidada (onde nomes de seção não correspondem a nomes XSD) caem para flat_paths(68) e o Gemini encontra os paths corretos.
