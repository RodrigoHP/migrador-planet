# Story 45.3 — CI Tier Separation: GitHub Actions + Medição AC5

## Status: Ready

## Descrição

O Epic 45 entregou a infraestrutura de separação de tiers (markers, Makefile, xdist) mas o `ci.yml` ainda roda `pytest tests/ -q` sem markers — ignorando completamente o que foi construído. Esta story fecha os dois débitos em aberto:

1. **Medir o tempo real** de `make test-integration` com xdist (AC5 pendente da 45.2)
2. **Atualizar o CI** para usar os tiers separados com a estratégia correta

A estratégia do CI (unit bloqueia PR / integration quando e como) é decidida **após** a medição — não antes. Implementar sem medir seria repetir o erro que o Epic 45 veio corrigir.

## Acceptance Criteria

- [ ] **AC1 — Medição baseline:** executar `time make test-integration` localmente (ou em ambiente com LLM mocks desabilitados via `OPENROUTER_API_KEY=test-key`) e registrar o tempo real com xdist. Documentar no Dev Agent Record.

- [ ] **AC2 — Estratégia definida com base na medição:**
  - Se `make test-integration` ≤ 10 min → ambos os jobs rodam em todo PR (unit + integration bloqueantes)
  - Se `make test-integration` entre 10-35 min → unit bloqueia PR; integration roda em push para main (não bloqueia PR mas visível)
  - Se `make test-integration` > 35 min → unit bloqueia PR; integration como job nightly/manual separado

- [ ] **AC3 — `ci.yml` atualizado:**
  - Job `backend-tests-unit`: `pytest -m unit -q --tb=short` — roda em todo PR, bloqueia merge
  - Job `backend-tests-integration`: conforme AC2, com `OPENROUTER_API_KEY=test-key STORAGE_MODE=local`
  - Remover `--ignore=tests/test_pipeline_benchmark.py` (agora controlado por `-m unit`)

- [ ] **AC4 — CI verde:** pipeline passa com os novos jobs no GitHub Actions

- [ ] **AC5 (45.2 fechado):** marcar AC5 da story 45.2 como `[x]` com o tempo medido registrado

- [ ] **AC6 — EPIC-45.md atualizado:** adicionar story 45.3 na tabela, critério "CI separado por tier" marcado como atingido

## Dev Notes

### CI atual (linha 58) — o que muda

```yaml
# ANTES
- name: Run tests
  env:
    STORAGE_MODE: local
    OPENROUTER_API_KEY: test-key
  run: python -m pytest tests/ -q --ignore=tests/test_pipeline_benchmark.py --tb=short

# DEPOIS (exemplo com estratégia B — integration em push main)
- name: Backend Tests — Unit (fast, every PR)
  env:
    STORAGE_MODE: local
    OPENROUTER_API_KEY: test-key
  run: python -m pytest -m unit -q --tb=short

- name: Backend Tests — Integration (push to main only)
  if: github.event_name == 'push'
  env:
    STORAGE_MODE: local
    OPENROUTER_API_KEY: test-key
  run: python -m pytest -m "unit or integration" -q -n auto --tb=short
```

### Como medir AC1 localmente

```bash
cd backend
OPENROUTER_API_KEY=test-key STORAGE_MODE=local time python -m pytest -m integration -q -n auto --tb=short 2>&1 | tail -10
```

O `OPENROUTER_API_KEY=test-key` desabilita chamadas LLM reais (os testes mocam ou skipam quando a key é inválida). Registrar: N testes, tempo total, workers usados.

### Detecção de falhas de integration sem bloquear PR

Se estratégia B ou C: falhas de integration aparecem no GitHub Actions como job com warning/falha visível na aba Actions, mas não bloqueiam o merge. A equipe vê o sinal e abre fix antes do próximo PR. O `main` pode ter integrations quebrando por 1 ciclo mas unit tests garantem que a lógica central está ok.
