# Story 5.13: AnalyzingPage — Tela de Progresso com 8 Blocos, SSE e Auto-Navegação

## Status
Ready for Review

## Story
**As a** operador da ferramenta,
**I want** ver uma tela dedicada de progresso mostrando os 8 blocos de análise com 27 estágios, barra de progresso, resumo parcial e tempo estimado,
**so that** eu saiba que a análise está progredindo e possa cancelar se necessário.

## Acceptance Criteria
1. Tela mostra título "Analisando documentos..."
2. 8 blocos listados com estágios: completed, in progress (animado), pending
3. Barra de progresso com porcentagem (calculada por estágios completed/total)
4. Resumo parcial atualiza em tempo real: "PDFs: N documentos | Páginas: N | Layouts detectados: N"
5. Tempo estimado exibido e atualizado
6. Botão "Cancelar" chama POST /api/analyze/{job_id}/cancel e navega de volta para /upload
7. Conexão SSE via composable useSSE (já existe)
8. Ao completar pipeline, auto-navega para /editor (sem ação do operador)
9. Em falha do pipeline, mostra mensagem de erro com opção de retry ou voltar
10. Reconexão SSE automática: se conexão cair, tentar reconectar até 3 vezes com backoff (1s, 2s, 4s); se falhar, exibir "Conexão perdida" com botão "Reconectar"
11. `npm run build` passa

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: LOW. `AnalyzingPage.vue` depende de: `FullWidthLayout`, `ProgressBar`, `useSessionStore`, e as constantes de `analyzingPageConstants.ts`. O EventSource é criado diretamente na página (Opção B escolhida), sem passar por um composable intermediário — aceitável dada a especificidade do comportamento de reconexão com backoff. `analyzingPageConstants.ts` é exportado como arquivo separado, o que é arquiteturalmente correto para dados estáticos de pipeline.
- Cohesion: HIGH. A página tem responsabilidade única e bem delimitada: exibir progresso em tempo real via SSE e reagir a eventos do pipeline. Lógica de SSE, handlers de UI e estado reativo estão claramente separados dentro do `<script setup>`.
- Patterns: Vue 3 Composition API usada corretamente. `computed` para `progressPct`, `completedCount`, `estimatedTime` e `hasRunningStages` — correto para dados derivados. `onUnmounted` para cleanup do EventSource evita memory leaks. O padrão de reconexão com exponential backoff (1s/2s/4s, max 3 tentativas) é consistente com o padrão adotado no backend.
- Scalability: O `stagesStatus` como `Map<number, StageStatus>` (não array) é a escolha correta para updates pontuais sem re-renderização de toda a lista. O EventSource direto (sem polling) é adequado para pipelines de até ~30 minutos.

### Issues Found

**[MEDIUM] `TOTAL_STAGES = 27` em `analyzingPageConstants.ts` diverge do backend que tem 28 stages**
- O backend implementou 28 stages (Story 5.12 adicionou Stage 28). O frontend usa `TOTAL_STAGES = 27` para calcular `progressPct = completedCount / 27 * 100`. Quando o Stage 28 completar, `progressPct` excede 100% (100%+ = 28/27 * 100 ≈ 103.7%) — ou se Stage 28 não emitir progresso, o progresso nunca atingirá 100% antes do evento `done`.
- Além disso, o Bloco 8 em `PIPELINE_BLOCKS` lista apenas 3 stages ("Confiança", "Consistência", "Template Draft") mas o backend tem 4 stages no Bloco 8 (Stages 25, 26, 27, 28 — sendo Stage 28 o Pipeline Result).
- Severity: MEDIUM (discrepância funcional visível ao operador)
- Ação necessária para @dev: atualizar `TOTAL_STAGES = 28` e adicionar "Pipeline Result" ao bloco 8 em `analyzingPageConstants.ts`.

**[MEDIUM] SSE `done` event listener depende de evento nomeado não emitido pelo backend**
- A linha 309 (`eventSource.addEventListener('done', ...)`) aguarda um evento SSE com `event: done`. O backend (`sse_starlette`) emite eventos sem campo `event:` por padrão (apenas `data:`), conforme identificado pelo QA e corrigido para os eventos de progresso (mudando para `addEventListener('message', ...)`). Porém, o evento `done` ainda usa listener nomeado. Se o backend emite o sentinel `done` também sem `event:`, este listener nunca será chamado e a auto-navegação para `/editor` nunca ocorrerá.
- Esta é uma inconsistência arquitetural derivada do fix parcial: o FAIL-1 foi corrigido para eventos de progresso mas potencialmente não para o evento `done`.
- Severity: MEDIUM (depende da implementação exata do sentinel no backend)
- Ação necessária para @dev: verificar como o backend emite o evento `done` (com ou sem `event:` field) e garantir que o frontend trate corretamente — seja via `addEventListener('done', ...)` se `event: done` for emitido, ou via campo `status` no payload JSON do evento `message`.

**[LOW] Testes Vitest não cobrem fluxo SSE funcional**
- Confirmado pelo QA. O `MockEventSource` está implementado no spec mas não é usado para testar o comportamento real: atualização de status de stage ao receber evento `message`, auto-navegação ao receber `done`, tratamento de erro. Os 14 testes são de snapshot/estrutura apenas.
- Severity: LOW (cobertura de teste, não de design)
- Ação sugerida para @dev: adicionar testes SSE funcionais em Sprint futura.

**[LOW] Stale comment herdado do backend**
- `analyze.py` diz "27-stage pipeline" (deveria ser 28) — herdado da Story 5.12, já registrado como TD-5.12-002.

### Technical Debt Registered
- TD-5.13-001 (CRITICAL para entrega): Atualizar `TOTAL_STAGES = 28` e adicionar Stage 28 ("Pipeline Result") ao Bloco 8 em `analyzingPageConstants.ts`.
- TD-5.13-002: Verificar e garantir que o listener de evento `done` corresponde ao formato real emitido pelo backend.
- TD-5.13-003: Adicionar testes Vitest cobrindo fluxo SSE funcional (emissão de `message`, `done`, reconexão com backoff).

### Decision Log
- A escolha de Opção B (EventSource direto na página, sem composable) para SSE é arquiteturalmente justificada: a lógica de reconexão com backoff e o gerenciamento de estado de pipeline são específicos desta página, e forçar isso num composable genérico adicionaria complexidade sem reuso. A decisão é correta.
- `analyzingPageConstants.ts` como arquivo separado do componente é a abordagem correta: permite importar constantes em testes sem instanciar o componente Vue inteiro.
- Usar `Math.pow(2, reconnectAttempts) * 1000` para backoff (resultando em 1s/2s/4s) está alinhado com o padrão de retry do backend — coerência de contrato bem observada.

### Status
APPROVED_WITH_NOTES, condicionado à correção de TD-5.13-001 por @dev antes do merge. O mismatch `TOTAL_STAGES = 27` quando o backend tem 28 stages causará exibição incorreta de progresso (>100% ou nunca 100%) visível ao operador. A verificação do evento `done` (TD-5.13-002) deve ser confirmada. Após essas correções, a story está aprovada para Done.

### Issues Found

**FAIL-1 (Crítico): Mismatch entre evento SSE do backend e listener do frontend**
- O backend (`analyze.py`, `_event_generator`) emite eventos SSE como strings puras via `yield json.dumps(event)`. A biblioteca `sse_starlette` encapsula isso como `data: {...}\r\n\r\n` **sem** campo `event:`. Isso significa que o `EventSource` do browser dispara o evento padrão `message`, **não** `step`.
- O frontend (`AnalyzingPage.vue` linha 259) faz `eventSource.addEventListener('step', ...)` — esse listener **nunca será chamado** com a implementação atual do backend.
- Consequência: a tela de progresso permanecerá estática em 0%, blocos nunca atualizam, resumo parcial nunca preenche, auto-navegação para `/editor` nunca ocorre.
- **Correção necessária** (uma das opções):
  - Opção A (backend): alterar `_event_generator` para `yield ServerSentEvent(data=json.dumps(event), event="step")` para todos os eventos de progresso, e `ServerSentEvent(data="", event="done")` para o sentinel.
  - Opção B (frontend): mudar `addEventListener('step', ...)` para `addEventListener('message', ...)`, e ajustar o listener `done` para usar o campo `status` do JSON em vez de evento nomeado.

**CONCERN-1 (Minor): `handleRetry` faz POST /api/analyze sem body**
- `handleRetry` (linha 391) chama `fetch(API_BASE + '/api/analyze', { method: 'POST' })` sem `job_id` no body. O endpoint `POST /api/analyze` requer `AnalyzeRequest { job_id: str }` — a chamada vai falhar com 422. A lógica de retry precisa incluir o `job_id` no body JSON.

**CONCERN-2 (Minor): Testes não cobrem SSE flow**
- Nenhum teste verifica que ao emitir evento `step` o status dos estágios muda, ou que ao emitir `done` ocorre `router.push('/editor')`. O `MockEventSource` está implementado corretamente no spec, mas não é usado para testar comportamento SSE. Testes existentes são de snapshot/estrutura apenas.

**CONCERN-3 (Minor): Stale comment no backend**
- `analyze.py` linha 71 diz "Execute the full 27-stage pipeline" — deve ser 28 estágios (herdado da Story 5.12).
