# Story 5.7: Bloco 2: Layout Discovery — Skeletons, Clustering, Fingerprints e Registry

## Status
Ready for Review

## Story
**As a** bloco do pipeline,
**I want** construir skeletons de layout, clusterizar páginas por similaridade, selecionar representantes, gerar fingerprints e verificar o registry de layouts,
**so that** o sistema identifique Layout Types e possa reutilizar templates conhecidos.

## Acceptance Criteria
1. Stage 3 — Skeleton Builder: criar LayoutSkeleton por página (text blocks + bounding boxes, candidatos a tabela, zonas de layout, grid info)
2. Stage 4 — Page Clustering: KMeans sobre feature vectors (num_blocks, avg_font_size, table_count, text_density, header_height_ratio) → clusters de layout
3. Stage 5 — Representative Selection: selecionar melhor página representante por cluster (de PDFs diferentes quando múltiplos)
4. Stage 6 — Fingerprint Generation: gerar assinatura estrutural { tableCount, columnCount, headerBlocks, bodyZoneRatio, footerPresent } + hash
5. Stage 7 — Registry Lookup: consultar layout_registry no Supabase; se match → retornar template_id existente (pular para mapping); se sem match → continuar
6. Todos os 5 estágios registrados no orchestrator, emitindo SSE progress
7. Output: LayoutTypes[] com { cluster_id, name, representative_page, fingerprint, page_count, pages[] }
8. Para PDFs grandes (500+ páginas), processar apenas ~5-10 representantes por cluster
9. Se Supabase layout_registry estiver inacessível, Registry Lookup é ignorado (skip) com warning SSE "Registry indisponível — layout tratado como novo"; pipeline continua normalmente
10. Testes cobrem: precisão do clustering, geração de fingerprint, registry lookup hit/miss, registry offline

## Dev Notes

### Bibliotecas
- scikit-learn para KMeans clustering
- numpy para feature vectors
- hashlib para SHA-256 de fingerprints

### Supabase layout_registry
```sql
CREATE TABLE layout_registry (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  fingerprint_hash TEXT UNIQUE NOT NULL,
  fingerprint JSONB NOT NULL,
  template_id UUID REFERENCES templates(id),
  created_at TIMESTAMPTZ DEFAULT now()
);
```

### Nomes de Layout Type
- Auto-gerados com base nas características detectadas:
  - Muitas tabelas → "Transações" ou "Extrato"
  - Poucos blocos grandes → "Capa" ou "Resumo"
  - Grid complexo → "Detalhamento"
  - Footers proeminentes → "Rodapé Legal"

### Cenários de PDFs
- 1 PDF com poucas páginas → provavelmente 1 Layout Type
- 1 PDF com muitas páginas → múltiplos Layout Types (capa, corpo, resumo)
- Múltiplos PDFs → melhor clustering por ter mais data points de variação

### Otimização para PDFs Grandes
- PDFs com 500+ páginas: amostrar ~50 páginas para clustering
- Atribuir restantes ao cluster mais próximo sem recalcular
- Selecionar ~5-10 representantes por cluster para análise detalhada

### Issues Found

1. **[medium] Atributos dinâmicos em dataclass (type safety)** — `representative_selection.py` linhas 205-206 e `fingerprint_generation.py` linha 122: `lt._centroid` e `lt._cluster_skeletons` são atributos ad-hoc anexados a instâncias de `LayoutType` (dataclass). Isso viola o contrato do dataclass, dificulta serialização futura e pode causar `AttributeError` se acessados fora do contexto esperado. O código usa `getattr(..., [])` como proteção em `fingerprint_generation.py`, o que é defensivo, mas a raiz do problema permanece.
   - **Sugestão:** Declarar `_centroid` e `_cluster_skeletons` como campos opcionais no dataclass, ou criar um `LayoutTypeContext` wrapper que carregue esses dados de orquestração.
   - **suggested_owner:** dev

2. **[low] ConvergenceWarning do KMeans não suprimido em testes** — `test_page_clustering_similar_pages` e `test_end_to_end_single_pdf_few_pages` emitem 9 warnings de convergência em runtime (`Number of distinct clusters found smaller than n_clusters`). Isso ocorre porque o código itera todos os k candidatos incluindo valores maiores que o número de clusters reais. Não falha os testes, mas polui o output de CI.
   - **Sugestão:** Adicionar `warnings.filterwarnings` nos fixtures ou usar `n_init="auto"` em versões mais recentes do sklearn, ou adicionar verificação prévia de unicidade de features antes de tentar k > n_unique.
   - **suggested_owner:** dev

3. **[low] Naming inconsistency (story vs. implementação)** — A story descreve estágios como "Stage 3–7" na AC (numeração relativa ao bloco), mas a implementação usa stage numbers 7–11 (numeração global do pipeline). O comentário no `skeleton_builder.py` diz "Stage 7 (Block 3)" mas a story title diz "Skeleton Builder" como "Stage 3". Não impacta funcionalidade mas pode gerar confusão em manutenção.
   - **suggested_owner:** sm

4. **[low] Test 11 (register_bloco3) hardcoda `pipeline.total_stages == 28`** — O teste em linha 643 assume que o pipeline tem exatamente 28 stages. Se outros blocos adicionarem stages no futuro, este assertion falhará sem relação com a Story 5.7. Isso é um issue de fragilidade de teste, não de implementação incorreta.
   - **suggested_owner:** dev
