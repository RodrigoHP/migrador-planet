## Story

**As a** tech lead / architect,
**I want** a structured evaluation (spike) comparing pgvector + embeddings vs the current LLM text-only approach for field matching,
**so that** we can make a data-driven GO/NO-GO decision on whether to invest in semantic embedding infrastructure.

## Acceptance Criteria

4. - [x] Decisao: GO (implementar) / NO-GO (manter LLM text-only) com justificativa

## Dev Notes

- O matching atual usa Gemini Flash (LLM text-only) no stage de field matching do pipeline
- pgvector eh extensao PostgreSQL para vetores — Supabase oferece suporte nativo
- Modelos de embedding candidatos: OpenAI `text-embedding-3-small` (barato, rapido), `text-embedding-3-large` (mais preciso), Cohere `embed-v3`, ou modelos open-source (sentence-transformers)
- Este spike eh investigacao pura — o resultado pode ser NO-GO e isso eh perfeitamente valido

### Completion Notes List
- Decisao: **NO-GO** — pgvector + embeddings nao justifica implementacao

- Alternativas recomendadas: cache de matchings, prompt engineering, few-shot
