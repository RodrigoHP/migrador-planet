# Story 10.16: Bug — Confiança e Cobertura sem carregamento

## Status
Ready for Review

## Story
**As a** operador,
**I want** que os indicadores de Confiança e Cobertura no header do editor mostrem valores reais (ex: "87%", "3/10"),
**so that** em vez de "Confiança --%"  e "Cobertura --%", o usuário veja métricas reais da análise realizada.

## Problema Diagnosticado

### Sintoma
Header do editor mostra "Confiança --%"  e "Cobertura --%"  mesmo após pipeline completar com sucesso.

### Causa Raiz — Type Mismatch confidence_scores
O backend (Stage 25) escreve `context["confidence_scores"]` como estrutura plana:
```python
context["confidence_scores"] = {
    "factors": {"layout_stability": 0.7, "anchor_detection": 0.5, ...},
    "global_score": 0.72,
    "local_weighted_average": 0.68,
    "score_method": "weighted_average",
    "status": "review_recommended",
    "thresholds": {"approved": 0.95, "review_recommended": 0.80}
}
```

O frontend `confidenceStore.loadConfidence()` espera `Record<string, ConfidenceFactors>` **keyed por layoutId**:
```typescript
function loadConfidence(data: Record<string, ConfidenceFactors>) {
    // Itera entries: [["factors", {...}], ["global_score", 0.72], ...]
    // NENHUMA entry tem key = layoutId real
    for (const [layoutId, factors] of Object.entries(data)) {
        map.set(layoutId, factors)  // map.set("factors", {...}), map.set("global_score", 0.72)
    }
}
```

O display no header lê `confidenceByLayout.get(activeLayoutId)` → `undefined` → "--%" .

### Causa Raiz — Type Mismatch coverage
O backend (Stage 27) escreve `context["template_draft"]["coverage"]` como:
```python
{"fields": {"mapped": 3, "total": 10}}
```

O frontend `coverageStore.loadCoverage()` espera `Record<string, CoverageData>` **keyed por layoutId**:
```typescript
// Itera: [["fields", {"mapped": 3, "total": 10}]]
// Nenhuma entry tem key = layoutId real
for (const [layoutId, coverage] of Object.entries(data)) {
    map.set(layoutId, coverage)  // map.set("fields", {mapped: 3, total: 10})
}
```

O display lê `coverageByLayout.get(activeLayoutId)` → `undefined` → "--%" .

## Acceptance Criteria

1. Após análise, o header do editor exibe Confiança com valor numérico (ex: "72%") em vez de "--%"
2. Após análise, o header do editor exibe Cobertura com valores numéricos (ex: "3/10" ou "30%") em vez de "--%"
3. `confidenceStore.confidenceByLayout` tem pelo menos uma entry acessível pelo `activeLayoutId` atual
4. `coverageStore.coverageByLayout` tem pelo menos uma entry acessível pelo `activeLayoutId` atual
5. **Opção A (preferida — backend):** `pipeline_result.py` transforma `confidence_scores` para `{layoutId: {factors, global_score, status}}` keyed por layout_id real; e `coverage` para `{layoutId: {fields: {mapped, total}}}` keyed por layout_id real
6. **Opção B (alternativa — frontend):** Stores aceitam tanto formato flat quanto keyed, armazenando o flat como `"global"` key
7. A opção escolhida não quebra outros componentes que usam os stores
8. `pytest backend/tests/` passa sem erros

## Dev Notes

### Solução Aplicada (Opção A — Backend)

`pipeline_result.py` já continha a implementação correta em `_get_confidence_scores()` e `_get_coverage()`:

- **`_get_confidence_scores()`**: detecta o formato plano do Stage 25 (presença de chave `"factors"`), extrai os fatores e `global_score`, cria um `ConfidenceFactors`-compatible dict com `overall` em 0-100 (inteiro), e o key para cada `layout_types[*].id`. Fallback para key `"global"` quando não há `layout_types`.

- **`_get_coverage()`**: lê `template_draft["coverage"]["fields"]`, calcula `percentage`, cria `CoverageData`-compatible dict, e o key para cada `layout_types[*].id`. Fallback para `"global"`.

Foram adicionados 15 testes em `backend/tests/test_pipeline_result.py` cobrindo todos os cenários (AC #3, #4, #5, #7, #8).

### confidence_scores — Formato Atual vs Esperado

**Atual (backend Stage 25):**
```python
{
    "factors": {"layout_stability": 0.7, ...},
    "global_score": 0.72,
    "score_method": "weighted_average",
    "status": "review_recommended",
    "thresholds": {...}
}
```

**Esperado pelo confidenceStore:**
```typescript
// Record<string, ConfidenceFactors>
{
    "layout-0": { layout_stability: 0.7, ... },   // keyed by layoutId
    "layout-1": { layout_stability: 0.8, ... },
}
```

### coverage — Formato Atual vs Esperado

**Atual (backend Stage 27):**
```python
{
    "fields": {"mapped": 3, "total": 10}
}
```

**Esperado pelo coverageStore:**
```typescript
// Record<string, CoverageData>
{
    "layout-0": { fields: { mapped: 3, total: 10 } },  // keyed by layoutId
}
```

### LayoutId Format
Verificar qual formato o backend usa para `layout_types[*].id`. Provavelmente um dos:
- `"cluster_0"`, `"cluster_1"`
- `"layout-0"`, `"layout-1"`
- UUID
O `activeLayoutId` no frontend deve bater exatamente com esse formato.

### Onde o Header Lê Confiança/Cobertura
Provavelmente em algum computed que faz:
```typescript
const confidence = confidenceStore.confidenceByLayout.get(layoutStore.activeLayoutId)
const pct = confidence ? Math.round(confidence.global_score * 100) : null
```
Se `confidenceByLayout` não tem entry para `activeLayoutId` → `null` → "--%" .
