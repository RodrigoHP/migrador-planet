# Story 5.4: Pipeline Orchestrator + SSE — Coordenação de 27 Estágios em 8 Blocos

## Status
Ready for Review

## Story
**As a** sistema backend,
**I want** um orquestrador de pipeline que coordene 27 estágios em 8 blocos lógicos com eventos SSE de progresso,
**so that** o frontend possa exibir progresso em tempo real e o pipeline execute de forma confiável.

## Acceptance Criteria
1. Endpoint POST /api/analyze aceita job_id e inicia pipeline assincronamente
2. GET /api/analyze/{job_id}/progress retorna stream SSE
3. Formato de eventos SSE: `{ block: number, stage: number, stage_name: string, status: "running"|"completed"|"failed", progress_pct: number, summary: object }`
4. Pipeline executa 8 blocos sequencialmente, estágios dentro de blocos sequencialmente
5. Cada estágio tem: name, block_id, execute() method, estimated_duration
6. Pipeline cancelável via POST /api/analyze/{job_id}/cancel
7. Ao completar, resultado armazenado e acessível via GET /api/analyze/{job_id}/result
8. Em falha, detalhes do erro incluídos no evento SSE e armazenados
9. Stage registry permite adicionar/remover estágios
10. Testes cobrem: ordem de execução, formato SSE, cancelamento, tratamento de erros

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment

- **Coupling:** LOW. A separação entre `backend/models/pipeline.py` (definição de dados: `StageDefinition`, `BlockDefinition`, `PipelineDefinition`, `StageRegistry`) e `backend/routers/analyze.py` (lógica HTTP + execução do pipeline) é arquiteturalmente correta. O executor em `_run_pipeline` acopla-se a `PipelineDefinition` via `default_registry.build_pipeline()` — um contrato estável. Cada estágio acopla-se apenas a `context: Dict[str, Any]` — sem dependências diretas entre estágios. O canal de comunicação entre executor e stream SSE via `asyncio.Queue` isola completamente os dois fluxos assíncronos.
- **Cohesion:** HIGH. `models/pipeline.py` contém exclusivamente definições de estrutura de dados e o registry — sem lógica HTTP. `routers/analyze.py` contém exclusivamente os endpoints e a lógica de execução do pipeline. `_make_event` é um helper de formatação SSE com responsabilidade única. `_evict_stale_jobs` é utilitário de manutenção do estado in-memory, isolado e testável.
- **Patterns:** Padrão de plugin/registry (`StageRegistry.register_stage` / `remove_stage`) segue o princípio Open/Closed: o pipeline pode ser estendido com novos estágios sem modificar o executor. O uso de `asyncio.Event` para cancellation flag é idiomático em Python asyncio. O sentinel `None` na queue para sinalizar fim do stream SSE é padrão correto para generators assíncronos. `_pipeline_tasks: Set[asyncio.Task]` com `add_done_callback(_pipeline_tasks.discard)` é o padrão recomendado pela documentação Python para prevenir GC prematuro de tasks.
- **Scalability:** O design in-memory é adequado para o MVP e para uso single-tenant (tool de migração, não SaaS multi-usuário). O TTL de 1h com `_evict_stale_jobs()` resolve o memory leak para uso contínuo. Para escala horizontal (múltiplos workers FastAPI), o estado in-memory exigiria migração para Supabase jobs table — já previsto nas stories subsequentes e documentado como INFO no gate QA.

### Issues Found

**[LOW] `TMP_BASE = Path("/tmp/jobs")` hardcoded**
- Confirmado pelo QA (Issue #5). O path `/tmp/jobs` não existe em Windows, tornando os testes de integração dependentes de filesystem específicos de OS. O test_pipeline.py contorna isso com `tempfile.TemporaryDirectory()` nos testes que precisam do filesystem, mas o `start_analyze` endpoint falhará em desenvolvimento local no Windows se `/tmp/jobs` não existir.
- Severity: LOW
- Fix sugerido: `TMP_BASE = Path(os.environ.get("PIPELINE_TMP_BASE", tempfile.gettempdir())) / "jobs"`.

**[LOW] `job_id` sem validação de formato UUID**
- Confirmado pelo QA (Issue #4). `TMP_BASE / job_id` em `Path.__truediv__` aceita qualquer string, incluindo `../../../etc/passwd`. Em ambiente de desenvolvimento sem autenticação, o risco é baixo — mas `pathlib.Path` em Python não sanitiza automaticamente path traversal.
- Severity: LOW
- Fix sugerido: validar `uuid.UUID(job_id, version=4)` com try/except antes de construir o path.

**[OBSERVATION] Inconsistência de contagem entre title e implementação (27 vs 28 estágios)**
- O title da story e a tabela em Dev Notes listam 27 estágios, mas a implementação em `build_default_registry()` registra 28 (Stage 28 = "Pipeline Result" no Bloco 8). A docstring de `_run_pipeline` foi corrigida para "28-stage pipeline" (Fix #3 do QA), mas o título da story e AC4 ainda mencionam "27 estágios". Não é um issue arquitetural — a implementação está correta e os testes validam 28. É um problema de documentação a ser endereçado pelo @sm/@po.
- Severity: INFO (documentação)

### Technical Debt Registered
- TD-5.4-001: Tornar `TMP_BASE` configurável via env var `PIPELINE_TMP_BASE` com fallback para `tempfile.gettempdir()`.
- TD-5.4-002: Adicionar validação UUID4 no `job_id` recebido pelo `POST /api/analyze` para prevenir path traversal.
- TD-5.4-003: Migrar `_pipeline_jobs` in-memory para Supabase jobs table quando a story de persistência for implementada (previsto em stories subsequentes do Epic 5).
- TD-5.4-004: Corrigir title e AC4 da story para refletir 28 estágios (tarefa @sm/@po).

### Decision Log
- A escolha de `asyncio.Queue` como canal entre `_run_pipeline` (producer) e `_event_generator` (consumer) é correta para SSE em FastAPI + asyncio: isola o executor do transport layer, permite que múltiplos consumers conectem ao mesmo stream, e garante que eventos não sejam perdidos se o cliente desconectar e reconectar antes do pipeline terminar.
- O sentinel `None` na queue (em vez de uma flag de encerramento separada) é idiomático e evita race condition entre verificação de flag e consumo de eventos.
- O design de stubs (`execute()` retorna `{}` por padrão) para todos os 28 estágios é arquiteturalmente correto para esta story: fornece o scaffolding do pipeline sem exigir implementação real — cada stage stub será substituído por implementações reais nas stories 5.5–5.12.
- `_evict_stale_jobs()` chamado em `start_analyze` (não em background task periódica) é a escolha correta para MVP: evita overhead de scheduler e o cleanup ocorre naturalmente com uso normal da API.
