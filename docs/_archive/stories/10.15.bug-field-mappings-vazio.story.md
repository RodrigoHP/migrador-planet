# Story 10.15: Bug — Editor sem campos (field_mappings vazio)

## Status
Done

## Story
**As a** operador,
**I want** que o editor mostre os campos extraídos do PDF na aba Campos após a análise,
**so that** em vez de "0 de 0 campos mapeados" e "Nenhum campo disponível", o usuário veja a lista de campos identificados no documento.

## Problema Diagnosticado

### Sintoma
Aba Campos mostra "0 de 0 campos mapeados" e "Nenhum campo disponível".
O canvas mostra o conteúdo do PDF corretamente (parsed_documents tem dados), mas `result.field_mappings` chega vazio `[]` ao frontend.

### Causa Raiz — Stage 23 (Field Matching)
`backend/services/stages/field_matching.py` itera apenas sobre text_blocks com `semantic_label == 'value'` para criar mapeamentos. Se nenhum block tiver este label, `context["field_mappings"]` permanece `[]`.

O Stage que atribui semantic_labels é o Stage 9/10 (Semantic Analysis). Se este stage atribui labels como `"text"`, `"paragraph"`, `"body"` em vez de `"value"` / `"label"`, o Stage 23 não encontra blocks elegíveis.

### Causa Raiz — Type Mismatch (frontend)
Mesmo que `field_mappings` chegue com dados, há um mismatch de chaves:
- Backend escreve: `{"pdf_text": str, "label_text": str, "xsd_field_path": str, ...}`
- `FieldMappingEntry` frontend espera: `{name: str, path: str, type?: str, ...}`
- `mappingStore.loadPipelineFields(entries)` usa `entry.name` (undefined) e `entry.path` (undefined)

## Acceptance Criteria

1. Após upload de PDF sem XSD, a aba Campos mostra pelo menos os campos/valores extraídos do PDF (mesmo sem `xsd_field_path`)
2. Stage 23 produz mapeamentos para todos os text_blocks com conteúdo, não apenas os com `semantic_label == 'value'`:
   - Se nenhum block tem `semantic_label == 'value'`, Stage 23 trata TODOS os blocks não-header/não-footer como candidatos
   - Cada block com texto não-vazio gera uma entrada em `context["field_mappings"]`
3. `_make_mapping()` retorna dict com chaves que o frontend espera — ou a alternativa: pipeline_result.py transforma o formato antes de retornar
4. `result.field_mappings` no JSON final tem chaves `name` e `path` (ou `pdf_text`/`xsd_field_path` e o frontend é atualizado para ler essas chaves)
5. `mappingStore.loadPipelineFields()` usa as chaves corretas — consistência backend↔frontend verificada
6. Com PDF de boleto/documento sem XSD: aba Campos exibe ≥ 1 campo
7. `pytest backend/tests/` passa sem erros

### Type Mismatch — Chaves Backend vs Frontend
Backend (`_make_mapping` em `field_matching.py`):
```python
return {
    "pdf_text": str,       # ← chave atual
    "label_text": str,
    "xsd_field_path": str, # ← chave atual
    ...
}
```

Frontend (`FieldMappingEntry` em `pipeline.types.ts` — verificar):
```typescript
interface FieldMappingEntry {
  name: string   // ← espera "name", não "pdf_text"
  path: string   // ← espera "path", não "xsd_field_path"
  type?: string
  status?: string
  isOptional?: boolean
}
```

**Opção A (preferida):** Adicionar `"name"` e `"path"` em `_make_mapping()` como aliases:
```python
return {
    "pdf_text": pdf_text,
    "label_text": label_text,
    "name": label_text or pdf_text,   # ← alias para frontend
    "xsd_field_path": xsd_field_path,
    "path": xsd_field_path,           # ← alias para frontend
    ...
}
```

**Opção B:** Transformar em `pipeline_result.py` antes de retornar `result_json`.

**Opção C:** Atualizar `mappingStore.loadPipelineFields()` para usar `pdf_text`/`xsd_field_path`.

Escolher a opção mais simples e consistente.

### Arquivo de Mapping Store
`frontend/src/stores/mapping.ts` — verificar `loadPipelineFields()`:
```typescript
function loadPipelineFields(entries: FieldMappingEntry[]) {
  this.fields = entries.map((entry, index) => ({
```
