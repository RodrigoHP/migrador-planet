# Story 17.2 — Archaeologist Agent

## Story
**Como** investigador que busca a causa raiz de um bug,
**Quero** que o sistema automaticamente responda "o que mudou?" antes de perguntar "por que?",
**Para** que a investigacao comece com dados objetivos (diffs, timelines, dependency changes) em vez de especulacao.

## Status
Done

## Context

### Problema

Hoje o RCA comeca com 5 Whys — perguntando "por que?" desde o inicio. Isso leva a especulacao sem dados. A tecnica mais eficaz para regressoes ("funcionava antes") eh **Change Analysis**: mapear sistematicamente o que mudou entre o estado bom e o estado ruim.

Estudos mostram que Change Analysis resolve ~70% dos bugs tipo regressao quando aplicado como primeiro passo. Meta (Facebook) usa exatamente essa abordagem no DrP: heuristica que filtra milhares de changes para 5 candidatos.

### Inspiracao

- **Change Analysis** (tecnica classica): "O que mudou?"
- **Meta DrP + HawkEye**: Heuristica + LLM ranking de changes
- **FaR-Loc** (2025): RAG funcional para localizacao de falhas com AST-level search
- **git bisect**: Change Analysis automatizado

### Design Proposto

**Archaeologist Agent** — coleta dados ANTES da analise causal:

```
Input: classificacao do Classifier + sintomas

Coleta automatica:
  1. GIT FORENSICS
     - git log --since="last known good" — commits recentes
     - git diff main...HEAD — mudancas na branch
     - git blame {arquivo do erro} — quem mudou o que
     - Dependency diff: package.json/requirements.txt changes

  2. TIMELINE RECONSTRUCTION
     - Commits ordenados por data
     - Config changes (se rastreadas)
     - Deploy events (se disponiveis)
     - Correlacao: "erro comecou em {data}, estes commits sao de {data-1}"

  3. CHANGE RANKING
     - Para cada change, calcular relevancia:
       - Proximity: toca arquivo do stack trace? (+3)
       - Recency: quao recente? (+2 se <24h)
       - Scope: quantos arquivos tocou? (+1 se >5)
       - Author: mesmo autor de changes problematicos anteriores? (+1)
     - Ranking: top 5 changes mais suspeitos

  4. BLAST RADIUS MAPPING
     - Para cada change suspeito: que outros arquivos/modulos dependem?
     - Import chain analysis
     - "Se esse change causou o bug, o que mais pode estar afetado?"

Output:
  archaeology:
    changes_analyzed: 47
    top_suspects:
      - commit: "abc123"
        message: "refactor: extract helper function"
        relevance_score: 8
        reason: "Toca arquivo do stack trace, <24h, 6 arquivos"
        files: [...]
      - commit: "def456"
        ...
    timeline:
      first_symptom: "2026-03-29T10:00:00Z"
      suspect_window: "2026-03-28T14:00:00Z — 2026-03-29T09:00:00Z"
      commits_in_window: 12
    blast_radius:
      affected_modules: [...]
      affected_tests: [...]
    dependency_changes:
      added: []
      removed: []
      updated: [{name: "lodash", from: "4.17.20", to: "4.17.21"}]
```

## Risks

- Git forensics pode ser lento em repositorios grandes (1000+ commits na janela de analise). Mitigacao: limitar `--since` a 7 dias por default, configuravel.
- Change ranking heuristico pode falhar para bugs latentes (causa introduzida ha semanas, trigger recente). Mitigacao: se nenhum change suspeito no top 5, expandir janela e alertar investigador.
- Blast radius via import analysis pode ser incompleto para dependencias dinamicas (reflection, dynamic imports). Mitigacao: documentar limitacao, aceitar analise estatica como v1.

### Scoring de Relevancia

| Fator | Pontos | Criterio |
|-------|--------|----------|
| Proximity | +3 | Toca arquivo mencionado no stack trace ou erro |
| Recency | +2 | Commit < 24h antes do primeiro sintoma |
| Scope | +1 | Change toca > 5 arquivos |
| History | +1 | Autor tem historico de changes problematicos |
| Dependency | +2 | Atualiza dependencia externa |
