# Story 15.8 — Bug: Auth rejeita token ES256 — migrar validação para JWKS

## Story

**Como** dono da plataforma autenticado via Google OAuth,
**Quero** que o backend aceite meu token JWT corretamente,
**Para** que a rota de upload (e todas as rotas protegidas) não retornem 401 em produção.

## Status

Done

## Context

### Problema

A rota de upload na Railway retorna `401 {"detail":"Invalid token: The specified alg value is not allowed"}`.

**Causa raiz diagnosticada pelo @devops:**

O `backend/middleware/auth.py` valida tokens com `algorithms=["HS256"]`, mas o Supabase emite tokens com algoritmo **ES256** (ECDSA P-256). Isso foi confirmado decodificando o header do JWT em produção:

```json
{"alg": "ES256", "kid": "1e3c0db9-55a0-42b7-bfbc-13753672e7e7", "typ": "JWT"}
```

HS256 usa um secret compartilhado (simétrico). ES256 usa par de chaves pública/privada (assimétrico) — a chave pública é obtida via endpoint JWKS do Supabase.

### Estado Atual

**`backend/middleware/auth.py` (linha 49-54):**
```python
payload = jwt.decode(
    token,
    secret,                    # ← JWT secret — inválido para ES256
    algorithms=["HS256"],      # ← rejeita ES256
    audience="authenticated",
)
```

**`backend/requirements.txt`:**
```
PyJWT>=2.8.0    # ← sem suporte a chaves EC (precisa de [crypto])
```

### Solução

1. Trocar `PyJWT>=2.8.0` por `PyJWT[crypto]>=2.8.0` para habilitar suporte a chaves ECDSA
2. Substituir validação via secret por validação via `PyJWKClient` apontando para o endpoint JWKS do Supabase
3. JWKS URL derivada da `SUPABASE_URL` já presente no backend: `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`
4. Cache do JWKS com TTL para evitar round-trip em cada request

**Nota:** `PyJWT` já inclui `PyJWKClient` — nenhuma dependência nova, apenas ativar o extra `[crypto]`.

**Nota sobre testes:** `backend/conftest.py` já configura `AUTH_DISABLED=true` — nenhum teste existente precisa mudar.

### Scope — IN vs OUT

**IN SCOPE:**
- `backend/requirements.txt`: `PyJWT[crypto]`
- `backend/middleware/auth.py`: substituir `_decode_token()` para usar JWKS + ES256
- Variável de ambiente: `SUPABASE_URL` (já existe no Railway para storage)
- Remover dependência de `SUPABASE_JWT_SECRET` (não mais necessária para auth)

**OUT OF SCOPE:**
- Mudanças no frontend
- Mudanças nos testes (conftest já desativa auth)
- Mudanças em outros middlewares ou routers
- Suporte a múltiplos algoritmos simultâneos

## Technical Notes

**PyJWKClient com cache:**
```python
import jwt
from jwt import PyJWKClient

_jwks_client: PyJWKClient | None = None

def _get_jwks_client() -> PyJWKClient:
    global _jwks_client
    if _jwks_client is None:
        supabase_url = os.environ.get("SUPABASE_URL")
        if not supabase_url:
            raise HTTPException(status_code=500, detail="Server misconfiguration: SUPABASE_URL not set.")
        jwks_url = f"{supabase_url.rstrip('/')}/auth/v1/.well-known/jwks.json"
        _jwks_client = PyJWKClient(jwks_url, cache_jwk_set=True, lifespan=3600)
    return _jwks_client

def _decode_token(token: str) -> Dict[str, Any]:
    client = _get_jwks_client()
    try:
        signing_key = client.get_signing_key_from_jwt(token)
        payload = jwt.decode(
            token,
            signing_key.key,
            algorithms=["ES256", "RS256"],
            audience="authenticated",
        )
        return payload
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expired.")
    except jwt.InvalidTokenError as exc:
        raise HTTPException(status_code=401, detail=f"Invalid token: {exc}")
```
