# Story 11.1 — Consolidar pipeline canônico — deprecar jobs.py legacy

## Story
**Como** desenvolvedor do sistema,
**Quero** que exista um único pipeline de processamento canônico (analyze.py — 28 etapas),
**Para** eliminar a confusão entre dois sistemas paralelos e garantir que todos os componentes frontend consumam o mesmo backend.

## Status
Done

## Context
O audit técnico identificou dois sistemas de pipeline em paralelo:
1. **Legacy (jobs.py):** `POST /api/jobs` → `GET /api/progress/{id}` (SSE via job_manager.py) — 3 etapas simples
2. **Novo (analyze.py):** `POST /api/analyze` → `GET /api/analyze/{id}/progress` (SSE replay buffer) — 28 etapas

O `useSSE.ts` conecta ao sistema legacy. `AnalyzingPage.vue` usa o novo. Nenhum componente usa os dois consistentemente.

## Acceptance Criteria

1. **Audit de dependências** — Todos os usos de `POST /api/jobs` e `GET /api/progress/{id}` estão mapeados no frontend e backend.
2. **Remoção ou deprecação** — `routers/jobs.py` e `routers/progress.py` são removidos OU marcados como `@deprecated` com warning no log e prazo de remoção documentado.
3. **Rota única** — A única rota de pipeline ativa é `POST /api/analyze` + `GET /api/analyze/{id}/progress`.
4. **Testes** — Todos os testes existentes para jobs.py adaptados ou removidos; testes para analyze.py passando.
5. **Frontend limpo** — Nenhum componente frontend referencia `/api/jobs` ou `/api/progress/` (exceto em testes de regressão explicitamente marcados como legacy).

## Dev Notes

### Ponto de atenção
O `job_manager.py` usa `asyncio.Queue` para SSE — diferente do replay buffer do `analyze.py`. Verificar se algum componente do editor depende do formato de evento `{event: str, data: dict}` do job_manager antes de remover.

### Formato SSE legacy vs novo
- **Legacy:** `event: step`, `data: {"step": str, "pct": int}`
- **Novo:** `data: {"block": int, "stage": int, "stage_name": str, "status": str, "progress_pct": float, "summary": {}}`
