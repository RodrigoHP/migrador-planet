# Story 6.3: StructureTree Auto-Populated — Árvore Hierárquica do Documento

## Status
Done

## Story
**As a** operador,
**I want** ver a árvore hierárquica de estrutura do documento (Document > Header > Flow > Footer > elementos) auto-populada a partir da análise do pipeline, com ícones de tipo e indicadores de binding,
**so that** eu compreenda a estrutura detectada do meu documento.

## Acceptance Criteria
1. Organism StructureTree renderiza a árvore a partir de `templateStore.documentTree`
2. Nós exibem: ícone de tipo (📄 Document, 📦 Seção, 🔤 Texto, 📋 Tabela, 📊 Gráfico, 🖼 Imagem), nome e binding (ex.: `→ {{cliente}}`)
3. Elementos opcionais marcados com badge ⚠
4. Árvore é expansível/colapsável (clique no pai expande/colapsa filhos)
5. Clicar em um nó atualiza `inspectorStore.selectedNode` e `editorStore.selectedElementId`
6. Nó selecionado é destacado visualmente
7. Cada Layout Type tem sua própria árvore — trocar Layout Type no toolbar atualiza a árvore
8. Árvore suporta profundidade mínima de 5 níveis (Document > Section > Container > Table > Row > Cell)
9. Seções vazias exibem texto placeholder
10. Árvore com 200+ nós mantém performance aceitável: scroll suave, expand/collapse sem lag perceptível (<100ms); considerar virtualização se necessário
11. `npm run build` passa

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: LOW. StructureTree é consumer do templateStore e dispatcha para inspectorStore — sem acoplamento a outros componentes. StructureTreeNode é molecule pura sem dependências de store diretas, recebendo dados via props — correto para um componente recursivo reutilizável.
- Cohesion: HIGH. StructureTree = orquestração da árvore + integração com stores. StructureTreeNode = renderização de um único nó com lógica de toggle. Separação clara de responsabilidades.
- Patterns: Componente recursivo com StructureTreeNode como bloco construtivo é o padrão canônico para árvores em Vue 3. `flatNodes` Map do templateStore (Story 6.1) para O(1) lookup por ID é a decisão arquitetural que torna a seleção eficiente. Estado de `expandedNodes` como `Set<string>` local ao StructureTree é correto — é estado efêmero de UI, não precisa de store.
- Scalability: Adequado para documentos financeiros típicos (10-200 nós). Para documentos com >1000 nós, virtualização de lista será necessária — registrado como TD.

### Issues Found

**[LOW] Ausência de virtualização para grandes árvores**
- Para documentos com 1000+ nós (ex.: relatórios muito detalhados), o componente renderiza todos os nós no DOM.
- Severity: LOW — domínio esperado é 10-200 nós para documentos financeiros/fiscais. Não é um problema para MVP.

### Technical Debt Registered
- TD-6.3-001: Virtualização de lista para árvores com >1000 nós (target Epic 9).
- TD-6.3-002: Drag & drop para reordenar nós na árvore (target Epic 7 editing features).
- TD-6.3-003: Teste e2e com Playwright para validar performance real de expand/collapse (<100ms).

### Decision Log
- Componente recursivo via molecule StructureTreeNode (em vez de render function recursiva) permite customização visual por nível via CSS scoped e slots — decisão correta para manutenibilidade e extensibilidade no Epic 7.
- Estado de expand/collapse é `Set<string>` local ao StructureTree — correto para estado efêmero de UI. Não persistir no store evita poluição de estado global com dados puramente visuais.
- Reset de seleção ao trocar Layout Type (`inspectorStore.clearSelection()` no watcher de `activeLayoutId`) é correto — previne estado inválido onde o nó selecionado pertence a um layout diferente do ativo.

### Status
APPROVED_WITH_NOTES. StructureTree bem projetado, integração correta com templateStore e inspectorStore. TD-6.3-001 (virtualização) é o único item relevante para escalabilidade futura — low priority para o domínio atual de documentos financeiros.
