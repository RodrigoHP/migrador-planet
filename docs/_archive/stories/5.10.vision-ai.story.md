# Story 5.10: Bloco 6: Vision AI — Segmentação Visual e Interpretação via GPT-4o

## Status
Ready for Review

## Story
**As a** bloco do pipeline,
**I want** usar Vision AI (GPT-4o) para analisar screenshots das páginas para segmentação visual e interpretação, com validação self-check,
**so that** o sistema identifique elementos visuais que a extração de texto sozinha não consegue detectar.

## Acceptance Criteria
1. Stage 16 — Visual Segmentation: enviar screenshots para GPT-4o via OpenRouter, identificar regiões (header, body, footer, sidebar, table area, chart area, image area)
2. Stage 17 — Visual Interpretation: para cada região, GPT-4o descreve conteúdo e sugere estrutura (ex: "tabela com 3 colunas", "gráfico de barras", "logo da empresa")
3. Stage 18 — Self-Check: validar consistência entre output do Vision AI e output da extração de texto; reprocessar página se inconsistências significativas
4. Chamadas API via OpenRouter (chave API única, multi-provider)
5. Fallback: se Vision AI falhar ou timeout, continuar pipeline com análise text-only (confiança reduzida)
6. Rate limiting e lógica de retry para chamadas API
7. Todos os estágios registrados no orchestrator, emitindo SSE progress
8. Output enriquece cada página com: visual_regions[], visual_interpretations[], consistency_score
9. Configuração `VISION_AI_ENABLED` (env var, default: true): quando false, bloco Vision AI é inteiramente ignorado (skip) com warning SSE "Vision AI desabilitado via configuração"; pipeline continua com confiança reduzida
10. Custo estimado por job exibido no evento SSE de conclusão do bloco: "Vision AI: {N} chamadas, ~${custo_estimado}"
11. Testes cobrem: integração API (mock), comportamento de fallback, lógica de self-check, modo desabilitado

## Dev Notes

### OpenRouter API
- Compatível com OpenAI SDK — usar pacote `openai` Python com custom base_url
- Modelo: `openai/gpt-4o` para tarefas de visão
- Base URL: `https://openrouter.ai/api/v1`
- Header adicional: `HTTP-Referer` (identificação do app)

### Configuração do Cliente
```python
from openai import AsyncOpenAI

client = AsyncOpenAI(
    api_key=os.environ["OPENROUTER_API_KEY"],
    base_url="https://openrouter.ai/api/v1",
)

response = await client.chat.completions.create(
    model="openai/gpt-4o",
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "Analyze this document page..."},
            {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{b64_image}"}}
        ]
    }],
    response_format={"type": "json_object"}
)
```

### Prompt Engineering
- Solicitar output em JSON estruturado
- Incluir contexto: "Este é um documento financeiro/bancário/fiscal"
- Pedir coordenadas de bounding box normalizadas (0-1) ou em pixels

## Architect Review

**Reviewer:** Aria (System Architect)
**Date:** 2026-03-17
**Status:** APPROVED_WITH_NOTES

### Design Assessment
- Coupling: LOW. `openrouter_client.py` expõe apenas `get_client`, `chat_with_vision`, `load_image_as_base64` e `format_cost_summary`. Os três stages consomem estas funções via import local dentro dos executors, evitando coupling em module-level. O contexto de pipeline (Dict) é o único contrato de runtime entre stages.
- Cohesion: HIGH. Cada stage tem responsabilidade única e bem delimitada: Stage 20 = segmentação, Stage 21 = interpretação por região, Stage 22 = scoring de consistência + retry. O cliente OpenRouter está corretamente isolado em módulo próprio.
- Patterns: O padrão StageRegistry está seguido com fidelidade — `register()` substitui o stub via `remove_stage` + `register_stage`. O padrão de fallback gracioso (vision_unavailable → continua pipeline) está implementado de forma consistente nos três stages. O pattern de emit_progress com bare-except está correto para não bloquear o pipeline.
- Scalability: A decisão de processar apenas páginas representantes (1-5 chamadas/job, não uma por página) é correta e está implementada. O retry com exponential backoff no `_call_with_retry` suporta picos de rate-limit sem degradar o sistema.

### Issues Found

**[MEDIUM] Stage 21 duplica a lógica de _find_screenshot presente em Stage 20**
- `visual_interpretation.py` implementa `_find_screenshot` com lógica idêntica à `_screenshot_path_for_page` de `visual_segmentation.py`. Isso viola DRY e cria risco de divergência futura. A função deveria residir em `openrouter_client.py` ou em um utilitário compartilhado de bloco (ex: `backend/services/stages/vision_utils.py`).
- Severity: MEDIUM (débito técnico — não bloqueia entrega atual)
- Ação sugerida para @dev: consolidar em Sprint futura.

**[LOW] Timeout de rede (asyncio.TimeoutError) não é retentado em `_call_with_retry`**
- Confirmado pelo QA. O comportamento é defensivo, mas pode surpreender: um timeout de 30s na primeira tentativa resulta em falha imediata em vez de retry. Dado que o timeout é 30s e os delays de retry são 1s/2s/4s, adicionar `asyncio.TimeoutError` ao bloco de retry seria seguro e mais robusto.
- Severity: LOW
- Ação sugerida para @dev: Sprint futura.

**[LOW] Inconsistência de numeração de stages nos ACs**
- ACs 1-3 referenciam "Stage 16", "Stage 17", "Stage 18" mas a implementação correta usa Stages 20-22. Impacto: zero no código, confusão potencial em rastreabilidade de requisitos.
- Severity: LOW (documentação)

### Technical Debt Registered
- TD-5.10-001: Consolidar `_find_screenshot` / `_screenshot_path_for_page` em utilitário compartilhado de visão.
- TD-5.10-002: Estender `_call_with_retry` para tratar `asyncio.TimeoutError` como exceção retriável.
- TD-5.10-003: Corrigir numeração de stages nos ACs 1-3 (Stage 16/17/18 → Stage 20/21/22).

### Decision Log
- A escolha de usar `openai` SDK com `base_url` customizada para OpenRouter é a abordagem correta e recomendada — evita criar um cliente HTTP próprio e garante compatibilidade com atualizações futuras do protocolo.
- Vendoring de `openai` em `backend/vendor/` + `conftest.py` para sys.path é aceitável dado o contexto de projeto sem gestão de dependências via requirements instalado — resolve o problema de importação em testes sem overhead.
- Processar apenas páginas representantes (um por LayoutType) é decisão arquitetural deliberada e correta para controle de custo.

### Status
APPROVED_WITH_NOTES. Design sólido, padrões do projeto respeitados, fallback robusto implementado. Issues são não-bloqueantes. Débito técnico principal (duplicação de `_find_screenshot`) deve ser endereçado em Sprint futura antes que o bloco Vision seja estendido.
