# Story 21.10 — Escalation Criteria Codificados para @architect

## Story
**Como** investigador identificando um problema potencialmente estrutural,
**Quero** criterios claros e codificados para decidir quando escalar para @architect,
**Para** que problemas estruturais nao sejam ignorados por falta de definicao operacional.

## Status
Done

## Context

### Problema
O workflow menciona "escalacao para @architect se problema estrutural" mas "estrutural" nao tem definicao operacional. Cada investigador decide subjetivamente. Resultado: problemas que precisam de redesign sao tratados com band-aids, ou problemas simples sao escalados desnecessariamente.

### Design
4 criterios codificados (qualquer 1 = escalar):
1. **Scope amplo**: bug afeta 3+ modulos/stages (nao localizado)
2. **Design pattern**: root cause eh uso incorreto de um design pattern (nao implementacao)
3. **Interface change**: fix requer mudanca de interface/contrato entre componentes
4. **Barrier systemic**: barrier analysis mostra falha em 4+ camadas de defesa

Acao: gerar escalation prompt estruturado com evidencia de qual criterio foi atingido.

## Acceptance Criteria
- [ ] 4 criterios de escalacao definidos e documentados no investigate.md
- [ ] Fase 5 (Barrier Analysis) avalia criterios automaticamente apos analise
- [ ] Quando criterio atingido: gerar escalation prompt com evidencia
- [ ] Escalation prompt inclui: criterio atingido, evidencia, impacto estimado, sugestao de acao
- [ ] Em modo YOLO: escalar automaticamente (nao ignorar)
- [ ] Workflow YAML atualizado com condicao de escalacao
- [ ] Documentacao inclui exemplos de quando escalar e quando NAO escalar

## Scope
**IN:** Criterios, Fase 5 do investigate.md, escalation prompt, workflow YAML
**OUT:** Resposta do @architect (responsabilidade dele)
